# Access 权限目录目标设计

状态：目标设计，尚未实施。本文拥有机构与 Workforce 两组权限代码、归属、组合和目录一致性。各业务能力拥有具体动作的资格、结果和历史；目录项不能替代所属能力的规则。

## 范围与用权

机构角色只能组合机构权限，Workforce 角色只能组合 Workforce 权限。每项权限只授权其列出的办理范围，不推导另一项权限。本人办理依据当前账户及对应业务条件，不能把它写成默认角色的权限。管理入口还须复查当前会话、账户、适用授权、角色及目标关系；取得权限本身不免除等级或目标确认要求。

机构与 Workforce 分别拥有封闭目录。完整代码在程序中固定，由迁移安装到 `access.capabilities`。`id` 为非空稳定文本主键，非空 `scope` 明确区分 institution 与 workforce，运行身份只有读取权。`(id, scope)` 唯一，并供角色权限及历史条目组合引用，防止跨组引用。权限集合按精确代码及 scope 核对，不以字符串前缀推断归属。权限代码与 schema 表名属于不同命名空间。

| 机构代码                           | 授权范围                                                                                                                          |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `institution.roles`                | 维护较低等级的机构角色并读取定义与变更历史                                                                                        |

| `institution.affiliations.read`    | 读取他人政治面貌；范围见[人员政治面貌](../center/affiliation.md)                                                                  |

政治面貌的查看与更正分别组合进机构角色。角色定义、指派和权限变更历史只保存权限代码，不保存资料值。普通业务身份不因能运行运维工具而取得目录权限。

Scheduling 的具体权限代码尚未定义。Rota 已确认的 D-034 要求由 Nucleus 的全局 `Permission` 目录持有代码，并按确切操作确定代码。它与本文两组目录的整合边界留待 Scheduling 接入设计；不得预造宽泛的排班管理权限。

## 系统角色与维护

机构“普通账户”和 Workforce“普通成员”均无权限。机构“系统管理员”与 Workforce“管理员”分别持有本组目录全集；目录增加权限时须在同一维护事务中补齐对应 full 角色及其变更历史。运行身份不能改写或删除目录，已被角色定义历史引用的代码不得删除。功能尚未交付时，目录内存在权限不意味着存在可办理入口。

权限代码在程序中用封闭枚举表示，输入反序列化、数据库取列、输出序列化共用准确映射。未知代码、跨组代码和目录与枚举集合不一致均为错误，不按前缀接纳未来权限。启动须核验两组目录的准确集合、各自唯一的默认角色以及 full 角色权限恰为本组全集；失败时不开放依赖它们的注册、准入或管理入口。

## 验收

逐项验证代码、范围和动作归属。以运行身份验证两组目录只读、跨组外键和未知代码拒绝。双向比较枚举与目录：枚举多出分支和数据库多出代码都须失败。验证默认角色无权限、full 角色权限完整，以及新增目录项时同事务补齐 full 角色。权限读写分离、失权和跨能力误授权以相应业务入口验证；当前没有这些执行结果。
