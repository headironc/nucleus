# Access 角色与指派目标设计

状态：目标设计，尚未实施。本文拥有机构与 Workforce 的角色定义、等级、当前指派、永久历史、管理用权及原结果。权限代码由[权限目录](capabilities.md)拥有，管理入口共同的候选与拒绝顺序见 [Access 管理 HTTP](http.md)。Workforce 授权的建立、暂停和结束各有独立业务结果，本文只规定它们与角色的关系。

## 业务结果与不变量

机构与 Workforce 各自定义角色，不能跨范围组合权限或比较等级。角色由名称、本组权限集合和 1 至 1000 的整数等级组成，等级越大越高。较高等级本身不授予权限。机构“普通账户”和 Workforce“普通成员”各为等级 1、无权限的默认角色；机构“系统管理员”和 Workforce“管理员”各为等级 1000、持本组目录全集的 full 角色。其他角色为等级 2 至 999 的自定义角色，可以同级，同级不能互相管理。四个系统角色不可由业务入口修改或删除。

每个正式账户恰有一个当前机构角色；每份未结束 Workforce 授权恰有一个当前领域角色。不在角色外逐人授予权限，也不给角色预设失效期。注册在开户事务内建立“普通账户”的首条指派；领域授权建立时一并建立选定角色和首条指派。账户注销和领域授权结束删除相应当前角色关系，不伪造一次角色更换；历史永久保留。账户暂停阻止两组用权，领域暂停只阻止相应领域用权；恢复按当时的当前角色及定义判断。重新注册是新人员，重新取得“普通账户”。

首次系统初始化由运维操作者以本人完整实名资料，在同一维护事务建立人员、实名版本、账户、四个系统角色及创建历史，并将本人首条机构指派设为“系统管理员”。之后该角色的指派与换下仍只由 [Access 运维动作](../operations/access.md)办理。普通 HTTP 入口不能借用迁移身份。

角色定义是活引用。修改后全部当前持有人立即按新定义用权，未使用邀请码也按当前定义重新判断；已完成办理和当时的权限历史不能被改写。指派整个角色，不把角色权限复制成个人当前授权。当前用权只从事务内复核的账户、适用领域授权、当前角色及其定义推导，机构权限与领域权限不能互换，不能缓存成跨事务授权令牌。

## 管理资格

机构角色维护要求 `institution.roles`，机构指派要求 `institution.assignments`；领域内角色维护要求 `workforce.roles`，指派要求 `workforce.assignments`。维护与指派权分别判断，不能互相代替，也不能使办理人取得所选角色的业务权限。办理他人不得以本人为目标；办理人当前等级必须严格高于对象同范围等级，不能以其他范围等级替代。

创建角色时，选定等级须严格低于办理人，全部权限须由办理人当前持有。修改只能针对办理人等级严格高于的角色，修改后等级仍须严格低于办理人；新增权限须由办理人持有，移除权限不受此限。名称、等级和权限均未变化时拒绝修改。删除只针对等级更低且没有当前持有人或有效邀请码的自定义角色；历史不删除，已删除的名称可复用。

更换角色时，对象当前角色等级和所选角色等级均须严格低于办理人，所选角色的全部权限须由办理人持有。选默认角色同样如此；同角色不写空指派。领域内更换要求目标有未结束授权，允许目标处于领域暂停状态，但不解除暂停、重建授权或改变申请。直接准入及邀请码选角色时也使用所选角色等级与权限包含规则。旧确认中的角色定义或目标指派即使改走又改回，也必须拒绝。

角色创建、修改、删除和更换不要求人工理由。操作必须保存实际办理人当时的实名版本，不能用当前账户资料重新解释旧记录。原办理人后来失权、退出或注销，不撤回他人合法取得的当前角色。

`institution.workforce` 是跨范围管理入口：用办理人的机构权限与机构等级判断，不要求办理人持有 Workforce 角色或所选领域权限，不比较领域等级。它可以维护 Workforce 角色，为机构等级更低且满足共同准入条件的账户建立授权及首条指派，或更换已有授权中的角色；修改角色须高于该角色全部当前持有人的机构等级。它可以指派或换下 Workforce“管理员”，领域内入口不能这样办理。它不授权 Workforce 业务办理、邀请码、领域暂停恢复或结束，也不能办理本人。机构“系统管理员”的指派与换下只经停机运维入口，不经 HTTP 入口。

## 当前事实与历史

目标表归 `access` schema，以封闭 `scope` 区分 institution 与 workforce。`roles` 保存当前名称、等级和修订，`permissions` 保存当前权限集合；权限目录与角色通过包含 scope 的组合引用防止跨范围混用。角色名称在同一 scope 的现存角色中唯一。名称去首尾空白、按 NFC 规范化后为 1 至 64 个 Unicode 标量且不含控制字符。`level` 为 smallint，系统等级在各范围唯一，普通角色无权限，full 角色恰含本范围目录全集。系统角色保护由运行身份的数据库限制承担。

| 表             | 关键列与引用                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `roles`        | `id`、`scope`、`name`、`level`、当前 `change_id`                                                                          |
| `permissions`  | `role_id`、`scope`、`capability_id`；同范围角色与权限目录                                                                 |
| `changes`      | `id`、`role_id`、`scope`、`action`、`name`、`level`、`operator_id`、`changed_at`、`operation_id`                          |
| `entries`      | `change_id`、`scope`、`capability_id`；固定当次权限集合                                                                   |
| `holders`      | 机构角色当前持有人：账户 `id`、`person_id`、当前 `role_id`、最后 `assignment_id`；账户与人员组合引用 Identity             |
| `members`      | Workforce 角色当前持有人：Grant `id`、`person_id`、当前 `role_id`、最后 `assignment_id`；组合引用 Grant 与 Workforce 角色 |
| `appointments` | 机构指派历史：`id`、`person_id`、`role_id`、`operator_id`、`revision_id`、`assigned_at`、`sequence`、`operation_id`       |
| `assignments`  | Workforce 指派历史：上述事实及固定 `grant_id`；人员必须属于该 Grant                                                       |

身份列使用 PostgreSQL `uuid` 类型；时间为 `timestamptz`，顺序为正整数 `bigint`。`operator_id` 和 `revision_id` 引用固定实名版本，后者须与持有人属同一人员。上述列均非空。当前关系的 scope 由所属表固定，并受同范围组合外键保护。`changes` 和两类指派历史的角色 ID 是可删除角色的匹配值，不引用当前 roles；这使角色删除后历史仍可解释。

每次创建、修改、删除在同一事务追加 `changes`；创建和修改的完整权限集合另追加 `entries`，删除变更不带 entries。变更固定独立 UUID、角色 ID、动作、当时名称与等级、办理人实名版本、时间和 Operation-Id，scope 固定权限范围。首条必须是创建，删除后不能再追加；修改必须改变定义，同一角色时间严格递增。当前 roles 与 permissions 必须等于最新未删除变更及 entries，删除时最新变更为 delete 且不再有当前 roles。运行身份不可更新或删除历史。角色删除后，旧变更仍能解释当时的定义及权限。

`holders` 和 `members` 是当前关系：机构以账户 ID 为主键并绑定人员，领域以 Grant ID 为主键并绑定人员与领域。两者分别引用当前角色及 `appointments`、`assignments` 中最后一条相同持有者、相同角色的指派；提交时核对每个正式账户和未结束授权恰有一行。更换角色在同一事务追加对应指派历史并更新当前关系的 `role_id` 与 `assignment_id`。角色仍有当前持有人时，外键拒绝删除。领域授权结束或账户注销才删除适用当前关系；暂停不删除。

每条指派历史固定独立 UUID、人员、角色 ID、办理人及持有人当时实名版本、时间、该持有者的正整数顺序和 Operation-Id；领域另固定 Grant ID。机构按 `(person_id, sequence)`、领域按 `(grant_id, sequence)` 唯一。首条机构指派与账户建立同事务保存；首条领域指派与 Grant 的办理人、人员版本、时间、顺序及操作标识一致。新指派角色须不同于上一条；当前行必须指向最后一条指派。历史不引用可删除的当前 roles，永久保留。持有期从本条指派至下一条指派、授权结束或账户注销；当时权限由该期角色在当时的变更历史解释。

角色修改与指派使用同一角色协调，避免确认时序含混。新指派时间须晚于所选角色最近一次修改，新修改时间须晚于该角色最近一次指派；同一时刻冲突和时钟回退使整个事务失败。初始化中先创建系统角色再于同一事务时间建立首条指派是唯一允许的同时间例外。跨行配对与来源关系在提交时核对，不能只写当前行或只写历史。

## 原请求与读取

角色创建、修改、删除以永久变更行及其 entries 作为原完成；更换角色以永久指派作为原完成。按 Operation-Id 查原事实，核对原办理人、动作、目标、确认的变更或指派，以及规范化名称、等级和权限集合；同键异输入返回 `409 request_mismatch`。成功原结果返回那次角色定义或变更、那次指派，不能用当前角色替代。新办理按当前资格和业务条件接纳。数据库提交结局不明时，按[原操作恢复](../architecture.md#未知提交)结束原执行、取得原操作锁并读取原事实。

管理页面先取得精确手机号候选及目标确认，固定账户、人员、实名版本、定位手机号、当前指派 ID；领域指派另固定 Grant ID。写入时复查确认及当前资格。目标不在可办范围时不泄露身份，返回 `404 target_unavailable`；目标变化为 `409 target_changed`，角色变更为 `409 role_changed`。本人可读当前角色；有相应权限者可读角色、变更历史及指派历史。历史按当时时点解释定义，分页按共同 HTTP 契约；原结果可以按 Operation-Id 过滤读取。角色写入成功使用 `200` 或 `201` 的标准 JSON `code` 封套。

名称冲突为 `409 role_name_taken`，删除仍在使用的角色为 `409 role_in_use`，定义未变或指派相同角色为 `409 state_conflict`。名称、等级、权限代码或重复权限无效为 `422 invalid_input`。授权或数据库依赖故障为 `503 dependency_unavailable`；提交结局仍待核对时为 `503 outcome_unknown`。仅凭维护权或指派权访问另一项入口为 `403 permission_denied`。

角色响应为 `{ id, kind, name, level, permissions, changeId }`，权限按代码排序；`kind` 从等级推导，不是可写输入。创建正文为 `name`、`level`、`permissions`，修改另带确认时的 `changeId`，删除只带该确认。指派所选角色为 `{ id, changeId }`；变更历史含动作、定义、办理人脱敏身份和时间，指派历史含持有人、指派时的角色、办理人脱敏身份和时间。Workforce 写入正文以 `entry=domain` 或 `entry=institution` 明确授权来源，服务端不自动择优。

| 机构路由                                                                | 作用                                                           |
| ----------------------------------------------------------------------- | -------------------------------------------------------------- |
| `GET /accounts/current/role`                                            | 本人当前机构角色                                               |
| `GET /roles`、`GET /roles/changes`                                      | 有权者分页读取定义与变更，可按角色或 Operation-Id 过滤变更     |
| `POST /roles`、`PUT /roles/{id}`、`DELETE /roles/{id}`                  | 创建、携带 `change_id` 修改或删除机构角色                      |
| `POST /assignments/candidates`、`POST /assignments`、`GET /assignments` | 精确定位候选、提交目标确认与选定角色、分页读取含初始指派的历史 |

| Workforce 路由                                                                                        | 作用                                                             |
| ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `GET /workforce/current/role`、`GET /workforce/grants/{id}/role`                                      | 本人或有权管理者读取当前领域角色；授权已结束为 `404 role_absent` |
| `GET /workforce/roles`、`GET /workforce/roles/changes`                                                | 依适用权限分页读取定义与变更，可按角色或 Operation-Id 过滤变更   |
| `POST /workforce/roles`、`PUT /workforce/roles/{id}`、`DELETE /workforce/roles/{id}`                  | 以 `entry=domain` 或 `entry=institution` 选择相应授权来源        |
| `POST /workforce/assignments/candidates`、`POST /workforce/assignments`、`GET /workforce/assignments` | 精确定位、确认更换、分页读取含首条的指派历史                     |

角色创建成功为 `201`，修改和删除为 `200`；更换角色为 `201`。列表按等级降序、名称和 ID 排序；角色变更按时间倒序，单个持有人指派按顺序倒序。删除返回原变更，原请求恢复不返回后来同名的新角色。

## 客户端呈现

管理页面展示并确认修改后的完整角色定义和更换时所选角色的完整内容。`kind` 只读，页面不提供系统角色修改删除或“系统管理员”的业务指派入口；Workforce“管理员”只在机构入口可选。角色维护权不开放指派编辑，指派权不开放定义编辑。当前权限页读取当前角色，但页面状态不能代替提交事务内的复核。

## 验收

从空库初始化与注册验证四个系统角色、当前行和首条指派的共同提交。覆盖严格等级、权限包含、同级、自我管理、独立维护与指派权、机构跨范围入口、系统角色保护、有持有人或有效邀请码时删除拒绝。并发验证角色改走又改回、目标指派改走又改回、角色修改与新指派的时间交错。用运行身份验证当前与历史配对、跨人和跨领域引用、系统角色不可改、历史不可改、注销及结束后历史保留。验证原请求回读旧事实而非当前定义，以及同键异输入拒绝。当前没有这些执行结果。
