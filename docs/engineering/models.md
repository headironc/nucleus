# 模型选择与协作

本文拥有 Nucleus 的模型选择、升级、委派、报告接纳和接续约束。采用基线为 [agents 的模型政策（657629e）](https://github.com/silence-force/agents/blob/657629ec7489b4c6817935fc5d078b639a28bee9/delivery/policy/models.md)，采用其中的有界完整执行、授权复用和原证据接纳要求。通用约束及其[静态验收场景](https://github.com/silence-force/agents/blob/657629ec7489b4c6817935fc5d078b639a28bee9/tests/scenarios/rules.md#模型选择与接续)随该基线采用。项目继续维护自己的默认映射、实现者安排和补充审查偏好。

本文及其仓库内引用是团队、CI 和托管审查的项目规则来源，不依赖个人 Codex 目录。采用上游新版本前审阅差异，在本文统一维护默认值和项目补充；个人安装更新不自动覆盖项目决定。[交付规则](delivery.md)继续拥有实施切片、持续授权和分支流程，各业务专题继续拥有业务决定。

## 稳定原则

- 按工作涉及的业务判断、职责边界、影响和不确定性选择模型，不按文件数量或代码行数判断。
- 复杂工作优先由同一主代理连续负责业务理解、职责设计、核心实现和结果接纳。
- 模型分工同时适用于主代理和受委派任务，不要求创建子代理或预建调度框架。主代理在已有授权与工具能力内选择模型、安排委派和处理升级，用户不必手动分配子任务。
- 遵守用户明确的模型选择、适用的项目覆盖和更高优先级指令。下列默认值不能覆盖它们。

核心边界检查继续按[设计与实施边界](delivery.md#设计与实施边界)和[结构核对](verification.md#结构核对)执行。先区分已确认事实、推断与缺失决定，再核对事实所有者、完整流程和新增概念的当前消费者。普通可逆技术选择由执行者处理，不新增逐步审批。

## 当前默认映射

下表是可维护的使用默认值，不是官方能力保证，也不证明模型或档位可用。模型更新只在此维护映射，不改写稳定原则。

| 工作                                                         | 使用偏好         | 模型标识      | 推理档位 |
| ------------------------------------------------------------ | ---------------- | ------------- | -------- |
| 复杂业务规则、职责设计，以及内核、授权、事务、并发和恢复边界 | Astra High       | `gpt-6-astra` | `high`   |
| 补齐证据后仍未解决的具体规则冲突、重大设计取舍或难解缺陷     | Astra Extra High | `gpt-6-astra` | `xhigh`  |
| 已确认设计、已有清晰模式的普通功能、页面和适配               | Sol High         | `gpt-6.1-sol` | `high`   |
| 文案、格式转换等边界明确、结果容易核对的机械修改             | Luna High，可选  | `gpt-6-luna`  | `high`   |

## 升级条件

- Luna 任务涉及调用链理解或多处行为影响时，交给 Sol High。涉及关键业务或职责判断时，直接交给 Astra High。
- Sol 遇到事实所有权、状态规则、授权顺序、事务边界或恢复责任的新判断时，交给 Astra High。先完成关键判断，再扩展依赖这些判断的实现。
- Astra High 先补齐权威规则并追踪实际调用链。仍有规则冲突、未决重大取舍、无法解释的失败，或同类修复反复失效时，先指出具体矛盾或证据缺口，再升到 Extra High。重新检查原假设，避免只增加推理强度而重复原假设。问题澄清后回到常规档位。
- 缺失业务决定仍由用户确认，不能用模型升级代替决定或覆盖已确认规则。升级不扩大[实施切片](delivery.md#实施切片)、[有效授权](delivery.md#连续交付与授权)或工具权限。

## 运行限制

以实际工具接口支持的模型、档位和切换机制为准。区分请求的模型与已核实的运行身份。实际模型或档位无法核实时保留未知，不从主代理、审查者等角色推断。文字指令或任务安排不证明模型已经切换；子任务使用另一模型也不表示主会话已切换。

通过可用且已授权的机制接回或改派升级任务。主会话无法切换，或所需模型与档位不可用时，说明限制及已核实的运行信息。仅在接续确实依赖用户操作时请求处理。其余工作在现有环境与授权内继续，采用替代方案时说明实际选择，不能静默替换用户明确指定的模型。等待必要决定或切换时，继续不受影响的工作。

不为模型偏好自动修改客户端配置或扩大工具权限。模型选择不授予模型、服务或额外操作的访问权。

## 职责与委派

原始授权绑定、原句柄等待和稳定候选接纳沿用所采用的[通用委派规则](https://github.com/silence-force/agents/blob/657629ec7489b4c6817935fc5d078b639a28bee9/delivery/policy/models.md#delegation-and-acceptance)。本节保留项目的实现者安排和审查偏好。

等待与结果接续另采用 [agents 的委派与接纳要求（10ed57fc）](https://github.com/headironc/agents/blob/10ed57fc8a7354df99a0c8c1dcdb9b0270fd6337/delivery/policy/models.md#delegation-and-acceptance)。增量范围仅限三项：按实际动作约束顺序，按具体下游动作判断正式输入就绪，以及跟进原负责人实际接续。既有通用采用基线、项目模型映射、交付授权与最终验收要求不变。

### 双机职责

采用本机与 `dev` 双机开发时，按下表分工。主机名 `dev` 不代表目标分支；分支和操作仍按[有效交付授权](delivery.md#连续交付与授权)核实。

| 负责人           | 完整责任                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------- |
| 本机客户端负责人 | 网站、小程序、设计与实际图形验证；完成所属实现、受影响检查、缺陷修复及已授权的 Git、PR 和交付收尾               |
| `dev` 后端负责人 | Rust 业务、HTTP、数据库及后端夹具；完成所属实现、受影响检查、缺陷修复及已授权的 Git、PR 和交付收尾              |
| 总协调           | 协调目标、接口、依赖和集成顺序，安排实际业务验收并接纳原始证据；主动读取两端原消息及结果，不依赖 `dev` 主动回传 |

总协调不代作者搬运源码、编码、运行测试或做具体代码审查。下文的主代理实现和验证责任由对应任务负责人承担。负责人在自己的绑定工作区完成开发流程，按[双机集成](delivery.md#双机开发与集成)交付准确修订。所需宿主能力由所属负责人依[验证责任](verification.md#双机验证与能力缺口)落实；主机缺工具不把整个实现责任交给另一端。

### 任务与 PR 责任

主代理负责当前片的交付。先核对规则、实际实现、依赖和影响，再确定实施边界。主代理汇总验证、处理审查发现，并核对发布条件。委派后，交付责任仍由主代理承担。

每个 PR 明确一名负责推进更新、等待 CI 与审查、完成合并收尾的执行者。其他参与者可并行调查或审查，但不并发推送同一头分支或重复发起入队、合并。转交时交清当前候选、未决发现、活动运行或队列条目，以及下一步动作。接手者先回读这些目标，再按[分支流程](delivery.md#分支测试与提升)接续。记录复用该任务或 PR，不另建跟踪系统。

每片默认由一个实现者写入，主代理或受委派的子代理均可承担。子代理只承担边界明确的调查、实现或验证任务。派发时绑定准确基线、权威规则入口、唯一结果、排除范围和验收要求，同时限定工作区、可写范围及允许的操作。委派不扩大已有授权。执行者先读取适用规则和实际调用链，不只依赖任务摘要。

优先并行处理互不依赖的只读任务。共享规则或同一事务的实现由一个实现者负责。确需且已授权并行写入时，为各任务分配独立 worktree。主代理接纳结果前读取实际差异、验证证据及剩余问题，不能只看代理总结、测试数量或绿色检查。集成后的候选按受影响范围验证，分别通过的任务不自动证明组合正确。

审查沿已核实的现有路线取证，覆盖、发现处置和证据复用遵守[仓库审查规则](../../AGENTS.md#commits-and-review)。额外审查仅针对具体风险、覆盖缺口或明确的项目及用户要求，不为每片增加固定轮次。自检按自检报告。模型名称、代理身份、角色数量和上下文隔离都不证明判断独立或结果正确。

关键职责争议或覆盖缺口确需补充审查时，优先使用 Astra High。关闭审查者对作者对话的继承。只传准确候选与基线、审查范围、权威规则入口和操作边界，不传作者结论。审查者读取实际材料，报告具体缺陷及依据。无法隔离上下文时说明限制；隔离上下文仍可能保留模型共有的盲点。此安排不新增每片必经的审查关卡。

## Claude Code 与 DeepSeek 委派

Claude Code 可在本机或已授权的开发主机上调用 DeepSeek。任务拆分时主动识别其可交付的有界完整结果，按风险、任务要求、验收标准和实际工具支持安排委派。路线可用且材料与操作已授权时，将适任结果交给它完整执行。范围包括分析、设计、初步审查、代码和文档编辑、测试及修复。

负责人先落实必要的业务、授权、事务、并发和恢复判断，确认实施边界与设计。随后委派适任的完整实现结果，连同相关测试、文档和修复。负责人保留关键判断、验收与交付责任；任务复杂或保留这些责任，本身不构成收回全部实现的理由。具体能力、工具支持或拆分内聚职责的成本使委派不适任时，说明原因并沿可用的已授权路线继续。

负责人选择任务、受支持的模型与档位以及收回时机。按用户偏好和已知资源选择执行宿主，保留绑定的候选与写者所有权。这条路线补充当前默认映射，不要求每项任务调用，也不设定委派比例；不为增加使用量制造工作或重复有效检查。

起始偏好为 `deepseek-flash[1m]`、effort `low`，服从用户选择及已核实的运行支持。按任务推理需要选择受支持的模型与档位；执行授权本身不证明模型能力。此偏好来自上游有限本地试用，不是通用能力保证。服务范围和 Figma 专用路线分别见[调用边界](claude-code.md#服务输入与运行边界)与[设计路线](claude-code.md#设计路线导航)。

复用用户对该流程的常设授权，核对覆盖的项目、材料、服务商和操作。范围内换任务、换会话或再次调用不要求重复确认。一次特定材料授权仍限于该材料与操作；采用本政策不授予任意外发权限。只为缺失授权或实际扩围补充确认，其余工作继续。宿主审批仍有效，拒绝后按明确原因处理。不自行增加金额上限或逐次计费确认，用户另有要求时遵守。

按[职责与委派](#职责与委派)绑定任务，另明确宿主、真实工作区、分支及候选中的相关未提交改动。调用前读取[调用契约](claude-code.md)。材料包含权威要求、准确候选与基线，以及任务依赖的完整调用链，排除秘密和无关内容。缺少调用方或失败处理材料时补齐；无法补齐则缩小任务并说明缺口，不能把未提供的代码当作不存在。只读与执行的工具及宿主权限边界按调用契约处理。

报告按[职责与委派](#职责与委派)接纳，保留原发现、模型与输入来源及覆盖限制。执行结果须核对实际差异、产物、受影响行为和匹配候选的检查后接纳。主代理逐项对照要求和执行链核实可行动发现，独立推导并核对建议用例的预期。拒绝误报时保留原分类、原因和证据，不悄悄改写报告。调用成功不建立完整候选审查覆盖，也不授予合并权。复用有效检查，不增加固定审查轮次。

失败或输出不完整时，按[结果与恢复规则](claude-code.md#结果失败与恢复)诊断并决定接回。有效的已有证据仍按实际覆盖范围复用。

权限模式、实际生效证据与正常审批转交统一按[调用契约的权限规则](claude-code.md#工具与权限)执行。

## 恢复与交接

切换模型、交接、换会话或恢复压缩后的上下文时，先核对实际工作区、分支、远端及相关基线的准确提交。多个 worktree 共享远端引用，其他任务的 fetch 也会推进本地的 `origin/dev`。先按本片实际采用的基线判断差异，再核对目标分支的新变化，不能将两者混为本片改动。规则、授权与证据的读取沿用所采用的[通用接续要求](https://github.com/silence-force/agents/blob/657629ec7489b4c6817935fc5d078b639a28bee9/delivery/policy/models.md#continuity-and-evidence)。

交接复用现有任务和 PR 记录，补充剩余工作及无法从 Git 还原的决定。业务规则仍在所属文档维护，不另建重复进度台账。引用验证时保留候选、基线、检查范围、结果和限制。按[验证边界](verification.md#证据与自动化)复用输入未变的有效证据；输入变化或新证据使结果失效时，补做受影响检查。切换模型本身不是重跑检查的理由。

对无法核实的授权或完成状态保留未知，仅对依赖部分补充确认或验证，继续不受影响的工作。目标、批次或单片授权的接续遵守[连续交付与授权](delivery.md#连续交付与授权)，模型政策不改变其范围和条件。

模型分工的效果以业务规则与职责边界的人工纠正、切片返工评估。复用任务与 PR 中的具体证据，不新增统计台账。测试通过与模型名称都不替代业务和结构判断。文档约束指导执行，CI 与分支保护负责已配置的强制检查；两者都不保证上下文无损或生产验收通过。验收输入和预期见[模型行为场景](model-scenarios.md)。
