# 审查关卡契约

旧 CI 与审查准入部署已退役。本文下列章节保留旧部署的协议、原操作恢复及状态历史解释，不是当前平台配置或日常合并要求。工作流原件保存在[离线夹具](../../tools/fixtures/retired-workflows/README.md)，用于保留代码的回归。本次清理不重新绑定历史操作，不删除其记录，也不授权启动旧控制器。当前检查和合并入口分别见[验证边界](verification.md#检查范围)与[交付规则](delivery.md#审查关卡与证据复用)。

本文记录退役审查准入的机器契约与维护边界。核对原操作时，绑定原始部署和准确源码。重新部署或替换准入机制另行设计、授权和验收；候选不得自行指定可信身份或扩大自己的覆盖。

组织 App Cladiron（`cladiron[bot]`）核对 Codex 代码审查与安全审查的公开完成状态、准确候选和基线。它还核对发现标志、材料新鲜度、线程状态和必需检查，发布批准及 `Cladiron review gate`。`nucleus-review-gate:v4` 继续证明这些机器条件。关卡不判断逐项实质处置，也不证明供应商原报告完整；处置责任在[发现处理阶段](delivery.md#审查关卡与证据复用)完成。

## 保护配置与准入异常

`dev` 与 `main` 都以平台强制的准入结果决定能否合并。两者要求 PR、至少一项批准、推送后撤销旧批准、讨论解决、签名提交、严格检查策略，并禁止强推和删除。规则集不设 bypass。必需检查为 GitHub Actions（App ID `15368`）的 `docs`、`rust`、`website`，以及 Cladiron（App ID `3104501`，slug `cladiron`）的 `Cladiron review gate`。同名其他 App 或普通 commit status 不满足契约。控制器读取实际规则，缺少准确检查生产者或严格基线要求时不发布成功。

`dev` 使用下文的 squash 队列，支持独立 PR 与两层原生 stack；`main` 使用普通 merge commit，不配置队列。`main` 的专属检查绑定当前 PR、头提交、当前目标基线和最近重开事件。它沿用控制器的审查、批准、讨论和 CI 评估，并在发布前后复核。控制器同时读取实时 `main` 引用，避免 PR 元数据滞后时沿用旧基线。目标前进后，原审查记录不再满足直接路径；更新候选并完成新输入的审查后，流程重新给出结果。

`main` 还要求组织级必需工作流规则，仅匹配 Nucleus 的 `refs/heads/main`。来源固定为仓库 ID `1432619931` 的 `refs/heads/dev` 与 `.github/workflows/review-gate.yml`，不另用历史 SHA。`do_not_enforce_on_create` 为 `false`。控制器从生效规则核对这些绑定，缺失或改变时拒绝准入。私有来源仓库启用组织内 Actions 共享，组织内其他私有仓库因而可调用其工作流；这项访问范围由平台配置授权维护。

GitHub 在 PR 创建、提交更新和重开时要求一次新的必需工作流运行。控制器先写入并回读当前候选的等待检查，再评估审查条件。写入失败或控制器禁用时，运行失败。旧 PR 的同 SHA 成功检查因而不能代替新 PR 或重开后的执行。工作流成功只完成这道生命周期检查；最终准入仍取决于专属检查及其余保护。其他可变审查状态继续采用下文的异步失效边界。

无 bypass 是受信任的平台配置前提，由获授权的规则管理者维护。配置启用、变更和专项审计时，读取完整规则集并确认绕过名单为空；日常开发不增加人工检查。Cladiron 不具备规则集管理权限。[GitHub 仅向具有规则集写权限的调用者返回绕过名单](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset)，缺字段不能视为空名单。控制器不证明管理员无法更改或停用保护，也不以增加管理权限来获取这项保证。已知配置违背前提时，修复平台配置后再继续交付。

配置缺失、控制器不可用或覆盖不足时，暂停受影响的合并路径，按仓库流程缺陷修复。不保留由开发代理手工核验后放行的备用路径。修复必须落实到控制器、检查或平台规则；日常代理继续消费最终状态。修改远端保护、App 权限或启用变量仍遵守[操作授权](delivery.md#连续交付与授权)。仅合入源码不证明远端配置已经生效。

`Review gate` Actions 任务成功只表示本轮控制器执行完毕。审查等待或拒绝也可能正常结束该任务。平台必须消费指定 App 的专属检查，不以工作流颜色代替准入。已知的阻塞发现与证据矛盾仍由所属修复处理，不能通过解决线程或手工声明条件满足来放行。

## 个人 main 固定发布候选

个人晋级只适用于 private `headironc/nucleus`，固定仓库 ID `1432619931`、账户 ID `19648989` 和 Cladiron App ID `3104501`。可信源码已绑定实际操作记录与仓库规则身份；永久更新规则在迁移准备时保持 disabled、无 bypass。发布绑定不代表个人准入已启用，必须先完成本节的平台、凭据和实际验收。组织控制器仅在 `silence-force/nucleus` 运行；个人 `dev` 使用下节的独立 PR 入口，Cubic 接入及迁移另行交付。

切换时先停接新请求并启用同一永久更新规则，保持无 bypass。在阻写状态下核清在途终态、完成最终备份，再迁移并核对规则 ID、个人来源、Environment 和操作记录。目标凭据、保护前置及供应商覆盖满足后，仅为获准合并验收设置准确 Cladiron 的 PR-only 例外；验收成功后才恢复日常请求。Cladiron 的 Issues write 权限用于共用操作记录；修改共享 App 的权限前，必须交付其他消费者的权限兼容并核清影响，不能让其精确权限校验失效。

### 发布准备与准入

操作者固定已完成业务验收的 `dev` 提交 `D` 和当前 `main` 提交 `B`。先 fetch 并核对两条远端引用，再运行 `bun tools/release-candidate.ts D B release/NAME`，在新发布分支形成候选 `P`。工具只创建本地分支，不推送、不部署。`D` 已包含 `B` 时使用 `P=D`；否则用标准 Git 合并树创建签名提交，父提交顺序为 `[D,B]`。分支必须尚不存在，冲突和额外内容均停止准备。发布分支不承载独立业务修改，修复先进入 `dev` 并重新验收。

发布 PR 从同仓库 `release/...` 指向 `main`。准确 `P` 相对 `B` 取得正式代码、安全审查和 Docs、Rust、Halo CI。控制器沿用 Gate/Queue 的证据解析、事件基线、发现标志、新鲜度、讨论、批准及专属检查绑定。个人规则适配只替代组织必需生命周期工作流合同，其他共同条件继续执行。CI 绑定准确 PR、头提交、工作流、最新运行及 attempt；失败、取消、缺失或分页不完整都停止晋级。只执行候选的 CI 不持有 App 秘密。

入口在批准前核对 PR 身份、开放状态、目标与来源、当前 `B`、可信控制版本、`D/B/P` 关系和候选签名。`D` 必须属于可信 `dev` 的历史，`P` 必须包含 `B`，其树必须等于 `D/B` 的标准合并结果。发送前重新核对完整准入快照。后续 `dev` 推进不会扩大固定 `D`；`main` 推进会使原请求失效。

合并只允许 merge commit。结果 `M` 的有序父提交必须是 `[B,P]`，树与 `P` 相同，签名有效且可从当前 `main` 到达。下一次发布候选包含前次 `M`，因此支持连续晋级，无需将 `main` 回灌 `dev`。上述图形和机器检查不证明 `D` 已完成业务验收，操作者仍承担该判断。

### 可信来源、保护与凭据

手动运行 `Main promotion` 时选择受保护的 `dev`，只接受准确账户所有者发起及重触发的运行。环境、API 运行身份、源码 SHA 和当前 `dev` tip 必须一致。旧控制版本与其他 ref 拒绝。合并请求同时绑定 PR、完整 `D/B/P`，并明确声明该 `D` 已验收及本次晋级获准；重跑不能再次发送合并，恢复使用新的 `recover` 请求。

`main-promotion` Environment 必须只向可信 `dev` 提供 `NUCLEUS_PROMOTION_PRIVATE_KEY`。工作流按准确 workflow SHA 签出可信控制代码，先预检，再签发令牌；不签出或执行发布候选，不安装候选依赖。App 私钥从进程环境移除，令牌仅在本进程使用并遮盖日志，结束时撤销所有已知令牌。签发回执丢失时可能无法取得新令牌值，报告失败并依赖其有效期；不能声称该未知令牌已经撤销。

源码拥有账户、App、仓库及部署规则和记录对象身份，运行参数不能选择它们。签发器核对 private 仓库、默认分支、App 所有者、selected 安装、未挂起状态及准确权限。每个用途仅请求本仓库：审查令牌含 PR/Checks write 和 Contents/Statuses read；记录令牌含 Issues write；合并令牌含 Contents write 和 PR/Checks/Statuses read。各用途包含 Metadata read。Actions 历史由作业自己的只读令牌读取。签发前后安装变化时撤销全部已知令牌。原操作永久绑定当次 installation ID，重新安装后不能续写旧操作。

个人 `main` 保留共同严格检查、指定检查生产者、批准、Code Owner review、推送后撤销、讨论解决、签名及禁止强推和删除，且只允许 merge。永久 update-only 规则只给准确 Cladiron `pull_request` 例外；其他保护规则没有 bypass。`update_allows_fetch_and_merge` 只接受缺省或明确 `false`。控制器核对生效规则的准确 ID 集合、来源和 enforcement，拒绝其他部署或停用规则。

[GitHub 的 ruleset 读取合同](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset)只向具有规则写权限的调用者返回 bypass 名单。最小权限控制器不申请 Administration write。可见名单出现违背合同的内容时拒绝；字段省略不证明名单为空。配置负责人必须在启用、变更和专项审计时用授权管理身份核清完整名单、规则适用范围、真实 CODEOWNERS 及批准要求、个人账号权益、Environment、旧秘密持有点与旧运行/token 终态。只有上述前提成立，才能主张唯一写入入口；运行时绿灯不替代平台强制。

永久规则先以 disabled 登记准确身份，交付绑定后再置为 active、无 bypass，停止新请求并排空旧写入。迁移后核清同一规则持续执行及个人保护，再仅为获准验收加入 Cladiron PR-only 例外。规则、私钥、安装、操作 issue 与真实成功/拒绝验收均属于另行授权的启用工作；源码交付不执行这些动作。

### 一次发送与原操作恢复

晋级使用与关卡相同的仓库级串行锁。锁不承诺 FIFO，也不锁住 PR 编辑。固定 issue 由部署绑定稳定节点 ID 和编号，作为合并操作记录。控制器完整分页读取记录，校验 Bot、编辑痕迹和前后链；追加前后回读，响应丢失只核同一目标，不重复创建。记录异常或无法确认追加结果时不发送合并。

发送意图固定 PR 节点、`D/B/P`、树、生命周期、运行/attempt、控制版本、请求者和安装身份。发送前重查失败以 `not-sent` 结束；发送后只调用一次 merge。明确拒绝并回读未合并时记录失败；超时、取消、响应丢失或服务端失败都保留未知，阻止后继发送。恢复先核原运行准确身份且已经结束，再回读原 PR、提交图、树、签名和 `main` 可达性。只确认成功才补终态；未合并不等于未发送，继续阻止且不自动重试。

固定 issue 依赖受信持有者不在控制器外编辑或删除记录。GitHub 不强制 append-only，具备相关权限者可能改删；最后一条意图被删除时，剩余链可能仍完整，本实现不能保证发现。已知记录误删时关闭入口并核原执行，不能依据剩余链恢复日常写入。要求抵抗不可观测尾部删除时，必须另选具备可靠追加与保留保证的存储。

GitHub merge 只有期望 head 条件，没有基线和 PR 生命周期的整体 CAS。串行锁与发送前后回读不能使 retarget、关闭重开、新发现或管理员改配置与合并原子完成。已知变化停止本次晋级，发送后发现异常保留证据并停止后继写入；回读不能撤销已发生的效果。真实启用验收必须明确这一剩余边界。

## 个人 dev 严格同步 PR

`Dev admission` 只接受同仓库直接面向 `dev` 的独立 PR。当前目标提交为 `B`，候选为 `H`；`B` 必须是 `H` 的祖先，PR 元数据、实时目标及审查事件记录都绑定当前基线。候选签名有效，Docs、Rust、Halo 的准确 PR 工作流及最新 attempt 成功后，复用现有关卡核对正式代码和安全审查、发现、讨论及批准。个人路径不接受原生 stack，不读取或创建队列条目，也不复用旧基线的审查来放行新基线。依赖变更先上游、后下游逐 PR 交付；目标前进后同步候选并取得新覆盖。

PR 生命周期、审查通知和 CI 完成只触发自动评估。目标推送、定时及手动 `evaluate` 才遍历开放的 dev PR。关联选择沿既有通知语义；无关联 CI 只匹配来源仓库和分支，不扩大成全量评估。自动事件即使携带合并输入也不获得写入授权，评估只签发审查用途令牌。入口在批准前及专属检查发布后核对候选、保护和 CI；资格失效时将原候选检查置为失败并撤销批准。

账户所有者从受保护 `dev` 手动运行 `merge`，显式给出准确 PR 编号及完整 `H`，才请求一次 squash。运行者和重触发者均绑定账户所有者；重新运行旧 job 不能再发送合并。运行环境、workflow SHA、签出源码和实时 `dev` 必须一致。`pull_request_target` 的 API 运行头可以描述 PR 来源；可信控制版本仍由运行环境的目标 ref、workflow SHA、签出及实时 `dev` 共同核定。入口不执行候选代码或依赖。

部署统一由 `merge-deployment.ts` 拥有，同一仓库只有 dev/main 两个固定目标，各自绑定保护规则。个人 `dev` 保留与上节相同的严格检查、准确生产者、批准、Code Owner review、讨论、签名及禁止强推/删除，只允许 squash，禁止队列。永久 update-only 规则仅给 Cladiron PR-only 例外。完整 bypass、真实 CODEOWNERS、权益和旧秘密持有点仍由获授权的配置验收核清。`dev-admission` Environment 仅向可信 `dev` 提供 `NUCLEUS_DEV_PRIVATE_KEY`；源码不创建 Environment、Secret 或规则，部署绑定与平台实际启用分别验收。

自动评估、dev 合并和 main 晋级共享 `review-gate` 写锁。显式合并先恢复同一操作 issue 内的未终结发送，再自己完成准入，不持锁等待另一个 gate 作业。dev 意图采用 v2，绑定 PR 节点、`H/B`、树、生命周期、请求者、原 run/attempt、源码及 installation；读取器保留既有 main v1 记录。任何目标的未知发送都阻止另一目标发送，恢复核原入口和原运行终态，不重新提交请求。恢复模式不依赖新候选或当前准入保护已经通过。

结果提交必须只有父提交 `B`，树与 `H` 一致，签名有效且从 `dev` 可达。回执丢失后只回读原结果；不符时保留未终结意图。原 issue 的尾部删除限制、平台缺少整体 CAS，以及令牌清理的未知结果边界沿用上节。实际个人入口启用、错误来源拒绝、Secret 隔离与真实成功/恢复验收属于后续配置交付；本片的替身回归不证明这些平台条件已经生效。

## 控制器评估

Codex 评论、相关工作流完成、目标变化和手动触发进入同一个关卡队列。提交、评论和工作流完成仅核对关联 PR；工作流未带 PR 关联时，用上下文记录名称或来源仓库与分支定位，不扩大为全量复核。目标分支推送、定时和手动触发才读取全部开放 PR，逐个核对；某个 PR 读取失败不阻止其余 PR。批量核对不受任务矩阵上限约束。[审查活动通知](../../tools/fixtures/retired-workflows/review-activity.yml)响应行内评论的创建、修改与删除，也响应正式审查的提交、编辑与撤销。通知不读取密钥，其完成事件唤醒关卡。

通知先按 [GitHub 并发队列契约](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)合并尚未开始的重复运行。`main` 的创建、提交更新和重开运行使用各自运行 ID 分组，避免必需工作流被同 PR 的普通通知替换。其他带准确 PR 编号的 `pull_request_target` 使用该 PR 分组。PR 上 Codex Bot 的评论使用同组。工作流完成事件须为非 `merge_group`，且恰好关联一个带编号 PR，才使用该组。

目标分支推送、定时与手动触发共用全量复核分组。这些事件都在执行时读取全部开放 PR，不使用通知中的旧 PR 列表。队列 CI 完成通知按完整队列 ref 与 SHA 分组。通知须来自本仓库的 Rust、Docs 或 Halo 工作流，类型为 `merge_group`，分支以 `gh-readonly-queue/dev/pr-` 开头，且带 SHA。同一候选的三项 CI、重跑与不同结论共用分组；更换 ref 或 SHA 后分别处理。分组只合并通知，控制器仍回读准确运行、当前 entry 和全部必需检查。

Halo 完成后定向唤醒关联 PR 或队列候选，补齐状态变化后的复核。通知只定位目标，控制器重新读取当前证据，并按下节的[队列检查契约](#dev-队列检查)核对全部必需工作流与检查。

其他事件使用每次运行独有的分组，包括普通评论、空关联或多关联的非队列工作流，以及不满足上述字段条件的队列通知。分组不代替控制器对队列身份、提交图和审查证据的校验。

新通知只替换同组尚未开始的运行，不取消进行中的工作。所有已开始的运行仍经过全局作业锁串行写入和回读，包括采用旧工作流定义的运行。新分组不会追溯清理旧积压，也不保证实际处理延迟。控制器处理时重新读取当前候选及关闭、重开状态，不把事件快照作为当前状态。

关卡从默认分支运行 [`tools/review-gate.ts`](../../tools/review-gate.ts)，不执行候选代码。工作流在默认分支 checkout 后安装并核对仓库固定的 Bun 版本，再创建 App 令牌。控制器仅使用原生模块，无需安装依赖。工作流用仓库变量 `CLADIRON_CLIENT_ID` 与密钥 `CLADIRON_PRIVATE_KEY` 换取只限本仓库的短期令牌。读取 Actions 记录使用作业自己的只读令牌。

控制器与 [`dev 队列`](../../tools/review-queue.ts)使用 v4 的批准正文、绑定和证据摘要格式。整数身份保留完整精度，证据摘要保留未知字段及原始数值类型。时间支持 GitHub 与公开摘要使用的日历日期、`T` 分隔、秒和显式时区（`Z` 或 `±HH:MM`），可带小数秒。超过微秒的部分截断，材料先于完成的判断仍按整秒向下取整。此边界不承诺兼容原 Python 解析器接受的其他 ISO 时间写法。

检查运行按名称与 App 身份选择最大精确运行 ID。控制器合并各 commit status 的最新上下文结果。派生的 `name/app_id/passed` 事实按现有 `wire` 序列化值的字符串顺序排序，保留重复事实。API 枚举顺序变化不改变这组证据。真实结果、身份和条目增删仍参与稳定性核对。这个排序只用于派生检查事实，其他数组保留原有语义。

[基线记录](../../tools/fixtures/retired-workflows/review-context.yml)响应 PR 创建、提交更新、编辑、重开、关闭及草稿状态变化。GitHub 把事件中的 PR 编号、头提交、直接目标 SHA 与分支名固定到运行名称。该工作流不签出代码、不读取秘密。工作分支的生命周期通过该无凭据工作流完成事件唤醒默认分支关卡；有权限关卡的直接 PR 事件只接受 `dev/main`。关卡只接纳 `dev/main` 的独立 PR，以及下节限定的原生 stack。记录绑定当前 PR、头提交和目标分支，两项 Codex 审查在记录事件后完成。Actions API 的 `pull_requests` 字段会跟随当前引用变化，不能用它还原旧基线。直接合并路径还要求记录的目标 SHA 与当前 PR 基线一致。更换目标、缺少事件记录，或直接路径的目标前进后，先同步 PR 并等待新审查。启用后的 `dev` 队列按下文判断原审查输入是否保持有效。

只有创建和提交更新形成审查基线。其他生命周期运行以 `:notice` 结尾，仅触发当前状态复核。编辑说明或切换草稿状态不另立审查基线，也不使输入未变的历史覆盖产生歧义。

关卡还核对完整的目标变化和头分支重写记录。记录事件后换过目标，即使后来换回也要重新同步。目标分支必须禁止历史重写和删除，并要求解决讨论、在推送后撤销过时批准。撤销审查的额外角色限制必须明确关闭；启用或无法确认时，关卡不自动批准，也不扩大 App 权限。

历史强推不永久阻止新的候选。关卡通过 [GitHub 提交比较](https://docs.github.com/en/rest/commits/commits#compare-two-commits)核对每次强推前后的准确 SHA：当前头提交不得等于或属于任何强推前版本的祖先历史，且必须是最新强推后版本的严格后代。所有强推都须早于当前基线记录事件。满足这些条件才可继续核对新候选的审查和检查，不能只凭审查完成时间排除旧运行。比较使用祖先关系，不以分页提交列表是否包含某 SHA 作判断。分支删除或恢复、旧提交复用、记录后的强推、缺少提交或查询不完整时保持阻止，修复对应输入或流程后重新评估。

同秒内多次强推按完整时间线中的先后位置区分，只比较最后一次的替换版本。单次关卡运行内，相同仓库与准确 SHA 对的成功比较结果可复用；候选改变后重新比较。可变的时间线和其余批准证据仍在批准前后重新读取。

批准还要求两项审查的公开完成状态与头提交一致。两项汇总的 `has_any_findings` 必须是 Boolean，`has_unresolved_findings` 必须明确为 `false`。`has_any_findings=true` 可保留历史发现，不单独阻止批准。审查线程全部解决，必需检查通过。汇总从 GraphQL 读取原作者及最后编辑者；只有 Codex Bot 的原文或最后由该 Bot 编辑的正文可作证据。安全汇总保留的每条发现链接必须对应本 PR 的 Codex 根行内评论。当前头提交上的条目还须明确标记 `Resolved`。详情尚未加载、未知格式和无法对应的发现保持阻止。

同一头提交上的历史发现或正式审查不永久阻止批准。关卡读取当前头提交根评论的创建、更新时间，也读取 Codex 正式审查的提交、更新时间。这些时间必须完整、顺序有效，且严格早于两项公开完成时间。按秒比较，同秒视为顺序未确认；新材料不会因下一次轮询而自动成为有效历史。缺少可靠的审查类型与运行关联时，关卡采用两项完成时间中较早的一项。因此，迟到材料可能要求两项审查都更新完成时间。该比较只核对新鲜度，不证明某次审查逐项覆盖了材料或验证了处置。机器条件满足后可恢复批准。实质处置按[发现处理责任](delivery.md#审查关卡与证据复用)完成，不在日常合并时重复审计。

关卡在批准前重读评论、讨论、检查、规则、目标变化及 PR 版本。新建批准后再次核对同一范围；复用批准不执行这一轮全量取证。核对期间证据变化时撤销自己的批准。转为草稿、删除汇总和读取失败同样使批准失效。新建及复用批准都回读准确审查编号、App 身份、批准状态和头提交。关卡同时核对正文中的目标分支与基线，再核对当前 PR 版本。批准写入结果未知时，先在同一 PR 中定位本次新增且绑定一致的唯一批准，不重复写入。

同轮取证将同一 PR 的汇总评论、正式审查和讨论合并为 GraphQL 查询。每个连接独立分页，完成后退出后续查询。其他证据的 REST 读取和批量分页全部结束后，再独立读取基线历史并核对提交关系。部分返回或无法确认分页完成时，停止本轮取证。各轮重新读取可变证据；批准与检查的写入、回读及前后新鲜度核对继续串行执行。

汇总更新后，关卡核对当前证据，通过后只创建一次新批准。时间缺失或无效的旧批准不复用；当前汇总时间无法确认时停止自动批准。新建及复用批准的准确回读都核对前述汇总更新时间与批准时间的要求。旧提交的汇总和无关评论不影响当前批准的新鲜度。

撤销只处理关卡自己的批准，每次写入前核对 PR 仍开放。撤销响应失败时，仍回读同一审查编号的 `DISMISSED` 状态。结果未确认就报告失败，不重复撤销或继续批准。已发起的写入仍须完成原目标回读；随后关闭不能掩盖读取失败或未知结果。GitHub 不可用时也可能无法撤销，任务必须报告这个限制，不能声称批准已清除。

PR 关闭但未合并时，关卡停止审查取证与 review 写入，报告保留批准不适用于合并。保留 review 不代表撤销成功，也不能供下一次重开复用。启用专属检查后，关闭状态仍使准入检查不通过。重开后，普通复核根据最近事件识别旧批准并确认撤销。随后复查当前候选，新批准绑定该事件。漏掉重开通知不改变这一要求。关闭与重开通知只选择核对目标。当前事件绑定和证据未变时，复用有效批准，不重复撤销或重批。重开本身不要求再次运行模型审查，候选与基线未变的覆盖继续复用。

每次 PR 状态核对及最终批准确认都包含最近事件 ID。核对期间再次关闭并重开，即使头提交、基线和开放状态相同，原绑定仍会失效。已合并 PR 的批准只作历史记录，不再批准或撤销。整批 PR 共用一次基线历史读取；该记录不提供逐文件阅读证明。事件调度与撤销仍有延迟，事件查询和最终合并不是原子操作。当前远端流程不提供重开瞬间的强制拦截保证；队列的启用条件与剩余限制见下节。日常合并按[交付入口](delivery.md#审查关卡与证据复用)消费最终准入状态。关卡之外的已知新发现仍须处置。

讨论的解决与重新打开不产生评论事件，关卡每小时安排一次完整复核，也可手动触发。全量复核共享 App 的请求额度；单个 PR 的事件不会重复扫描整个仓库。串行队列保留最多 100 个等待任务，超额事件由后续完整复核补偿。平台调度可能延迟，这不是即时撤销保证；等待期间由目标分支的未解决讨论保护阻止合并。

## 两层原生 stack

接纳最终目标为 `dev`、同仓库的两层原生 stack 及其逐层合并后的剩余层。平台成员记录拥有 stack 身份、层顺序及 PR 关系。关卡核对完整成员集合，已合并成员只能组成前缀；关闭但未合并的成员不能充当已交付依赖。当前首个开放层必须直接面向 `dev`，其上层绑定准确父分支和父提交，且头提交延续父提交。普通工作分支之间的 PR 不自动成为 stack。规则从最终 trunk 读取，审查范围仍是各层相对直接父层的增量。

事件记录另固定 stack 编号、位置、大小和 trunk。[`pull_request_target` 使用默认分支的工作流](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)，包括目标为工作分支的上层 PR。Actions 运行的 `head_sha` 只用于按候选缩小历史查询范围，不能证明工作流来自父提交。候选修改的记录程序不能证明自身可信。新门禁先沿现有独立 PR 路径审查并合入受信 `dev`；随后 stack 才消费新契约。

批准与准入绑定 stack 身份、有序成员、直接父层和本层 head。PR 的 `baseRefOid` 是固定的审查差异基线，父分支当前提交由 `baseRef.target.oid` 与下层 head 共同确认。上层要求固定基线延续到当前父提交，且上层 head 延续当前父提交；父提交变化不能靠改写基线字段隐去。

下层的审查身份不包含上层 head，保留不受影响的下层证据。上层同时读取本层和当前父提交的事件记录，核对两者属于当前成员关系，并要求两项审查均晚于这两个事件。父层改变时，旧批准或平台保留批准不能代替新父提交的覆盖。改目标与重写历史仍按本层事件判断，不能借较晚的父层事件掩盖。原生成员关系可由无凭据生命周期通知建立记录；普通 PR 仍只接纳创建或提交更新记录。缺少记录时不批准，也不手工声明覆盖。

使用 [Stacks REST API](https://docs.github.com/en/rest/pulls/stacks) 关联已经建立的有序 PR，回读成员后分别取得准入。合并使用[异步接口](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously)，明确 `merge_action=merge_queue`、准确上层 SHA，且不绕过规则。保留返回的操作 UUID；未知结果先回读同一操作和所有成员，不重复提交。`enqueued` 仅表示入队，随后核对每个成员的实际合并结果。响应丢失且没有可回读 UUID 时，先查询原 PR 与队列状态；不能确定原操作结局时停止重试。原生 stack 不使用 auto-merge，也不以传统同步 merge 接口代替。

GitHub 负责依赖顺序及下层退出后的上层退出。项目控制器负责准确成员的审查准入与实际组合检查。两层可共用候选 SHA，或形成从当前 `dev` 经下层候选到上层候选的单父提交链。无依赖的开发和独立修复继续，只在真实代码或交付依赖处等待。当前支持不扩大队列并发，也不承诺任意多层或任意提交形状。

下层实际合并后，平台将下一开放层移向 trunk。关卡按平台当前成员、位置和大小重新绑定剩余层，保留的已合并前缀不再占用队列位置。目标或 head 改变后，必须取得对应可信事件及其后的正式审查；平台保留批准不能替代新输入的覆盖。部分合并不是整个 stack 已交付，最终仍逐层回读实际合并结果。

## dev 队列检查

本节描述启用后的队列契约。实际启用状态以 `dev` 生效规则和仓库变量的回读为准；启用时核对本节保证范围与有效授权。`main` 提升沿用现有流程。实现与发布依据见[检查刷新 #1199](https://github.com/silence-force/nucleus-archive-20261025/pull/1199) 及[基线分离 #1207](https://github.com/silence-force/nucleus-archive-20261025/pull/1207)。

`dev` 在[共同保护](#保护配置与准入异常)之外要求 GitHub 合并队列，只允许 squash。`strict_required_status_checks_policy` 继续启用，由实际队列候选验证当前目标。队列采用 `ALLGREEN`、`SQUASH`，`max_entries_to_build`、`max_entries_to_merge`、`min_entries_to_merge` 均为 `1`。实现读取当前生效规则，缺少队列时不发布成功。

PR 头提交上的专属检查核对入队的机器条件；队列合成提交上的同名检查重新核对实际候选。后者绑定仓库、PR、审查头提交、原审查基线、当前整合基线、最近重开事件、queue entry ID 与入队时间、队列 ref 及合成 SHA。它还要求两项审查与有效 Cladiron 批准、发现标志、材料新鲜度、讨论和必需检查满足上节契约。只从前置条件和证据比较中排除自身准确的检查名与 App ID，避免等待自己；其他必需检查照常执行。检查的机器覆盖范围与批准相同，不判断逐项处置或原报告完整。发现处理者按[交付规则](delivery.md#审查关卡与证据复用)在原线程记录处置。日常合并不再次审计这些记录。检查成功不消除已知阻塞。

审查基线 `Br` 来自该头提交 `H` 的受信事件记录，整合基线 `Bi` 来自实时 `refs/heads/dev`。PR 的 `baseRefOid` 可能尚未反映目标推进，不能代替后者。同一头提交出现多个不同的记录基线时，关卡拒绝选择其中一份。复用要求目标分支未变、`Bi` 延续 `Br` 的历史，且 `merge-base(Br,H)` 与 `merge-base(Bi,H)` 相同。固定 `H` 和差异起点使原 PR diff 保持不变。merge-base 改变时暂停自动复用，补齐新输入的审查覆盖。即使两份差异内容恰好相同，也按此处理。头提交、目标、审查内容、发现、讨论、保护与检查仍按上节核对。核对发现新的审查问题或矛盾证据时，停止本次放行。

有效批准始终绑定 `H`、`Br`、目标分支和最近重开事件，不改写为已审查 `Bi`。已撤销、事件不匹配或早于汇总更新的批准不能直接复用。关卡重新核对后才可写入新批准。项目采用原 PR 审查加新组合 CI 的队列验收政策。基线推进后，旧审查仅覆盖输入未变的 PR 差异。新的整合范围由绑定 `Bi` 的真实队列候选及其必需检查验证。CI 通过不证明所有语义交互均无缺陷，也不免除已知问题的处置。`main` 按[直接路径](#保护配置与准入异常)绑定当前基线；未启用队列的 `dev` 不提供备用合并路径。

GitHub 按 SHA、名称和 App 判断[必需检查](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)。`external_id` 与输出中的绑定、摘要供控制器核验和回读，平台不据此隔离 PR 或队列 entry。发布准入成功前，关卡分页读取全部开放 PR 的身份元数据，包含草稿和最终目标受保护的 stack 上层。当前头提交必须只属于本 PR，且不属于任何活动队列 entry。多个受保护 PR 共用头提交时全部保持未通过，不按处理顺序覆盖成功。队列合成 SHA 只允许当前组合的准确成员拥有，且不作为任一开放受保护 PR 的头提交。普通 PR 的组合仍只有一个 entry；两层共享 SHA 按下文同时绑定两份准入。查询不重新读取无关 PR 的审查内容；身份查询失败或不完整同样保持阻止。

独立 PR 保持首位单 entry 的 squash 路径。stack 按当前开放成员的原生顺序验证实际队列前缀。当前候选覆盖此前尚未合并的层，以及平台分配了相同 SHA 的成员；这些成员必须按顺序位于队首，并分别满足准入。逐一回读其准确 entry、PR 版本与审查快照，父子候选和整合基线在取证期间保持一致。所需成员未生成候选时等待，离队、身份变化或审查失败时保持阻止。尚未包含于本候选的未来层不参与当前组合判断，不要求串行队列提前生成上层候选。共享 SHA 仅允许被其准确覆盖的成员拥有，其他开放 PR 或 entry 不能借用。

GitHub 为 entry 生成当前目标与此前排队 PR 的组合，见 [GitHub 队列说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)。关卡从 [MergeQueueEntry 对象](https://docs.github.com/en/graphql/reference/pulls#mergequeueentry)读取所属仓库、队列、准确 PR、位置与候选。每段 entry head 必须等于本段队列 ref 与 CI run SHA。共同整合基线 `Bi` 始终等于实时 `dev`。独立 PR、首层候选和两层共享 SHA 候选的 entry base 与唯一父提交均为 `Bi`。

上层使用不同 SHA 时，entry base 与唯一父提交必须等于准确下层队列候选。关卡完整验证下层前缀的 entry、审查、所属成员、提交树及 CI；下层前缀仍直接延续 `Bi`。上层绑定下层完整快照，并在发布前后重新核对。下层失败或取消会阻止上层，尚未完成时上层保持等待。此路径最多包含一个下层前缀，不要求下层先合并才验证上层。

每段 stack 组合的树必须等于该段末层的审查头提交树。分支名中的 PR 编号只用于定位；有序成员、每层证据、entry 和组合 SHA 共同进入检查绑定。身份或图形不受支持时保持阻止。

独立 PR 的 `Bi` 已包含于 `H` 时，合成树必须等于 `H` 的树。目标前进且与 `H` 分叉时，组合树可包含目标变更，此时不再要求两树相等。stack 保持线性父子关系，其组合树等于对应末层的树。关卡依赖上述平台生成契约和准确 entry、ref、运行及提交图绑定，不自行构造替代候选。每个新候选重新运行必需检查；旧 SHA 的成功不适用于新候选。非队首的独立 PR、其他多成员组合、身份歧义或不支持的提交形状保持阻止。

状态明确为 `QUEUED` 且 head/base commit 均为 `null` 的 entry 表示候选尚未生成。此时刷新 PR 准入检查，等待真实队列 SHA，不以 PR 头提交代替合成提交。身份查询只跳过明确等待且 head 为 `null` 的队列候选；已有 SHA 的 entry 仍参与别名核验。读取本 PR 的完整 entry 时，字段缺失、部分为空或其他状态缺少提交会使核验停止。候选生成后执行完整绑定。

Docs、Rust 和 Halo 工作流响应 `merge_group: checks_requested`，在实际队列提交上运行。控制器要求三项工作流的准确运行齐备，按各自最新运行及重跑结果核对完成状态。缺失或未完成时等待，失败或取消时拒绝成功。PR 准入与队列候选还须通过上文绑定 App 身份的全部必需检查。

队列与 PR 共用[输入分类](verification.md#仓库与检查归属)。明确豁免的差异可跳过耗时 Rust 或 Halo 步骤，`rust` 汇总检查与 `website` 任务仍运行并报告结果。并发组分别绑定 PR 或队列 ref。带密钥的关卡不直接响应 `merge_group`，而由默认分支的 `workflow_run` 消费无权限 CI 完成通知，并回读准确运行。定时、目标分支变化及现有 PR 通知继续补偿漏事件。有权限工作流和脚本均取受信分支；不能只依靠 checkout 保护密钥，因为工作流版本由事件 SHA/ref 决定，见 [GitHub 工作流版本规则](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows)。

重复通知先由关卡核对当前队列成功是否仍适用。最新检查必须来自指定 App，且已完成并通过。关卡重新读取完整队列证据，核对原检查的绑定、正文与证据摘要，再回读准确 ID 和当前证据。两次证据一致、原检查仍为最新且全部条件通过时，保留原检查与批准，不写入新的等待状态。复用范围包含准确 PR、候选、entry、审查与整合基线。新的发现、检查结果变化、重入或读取失败均不能沿用旧成功。

无法复用成功时，关卡建立本次评估的等待检查。未入队 PR 在头提交上新建 `in_progress` 检查；已有合成 SHA 的 entry 在该 SHA 上新建等待检查。每次评估同时持有原 SHA、绑定与准确的 check run ID，后续完成及失效处理更新同一个目标。已完成检查保留为历史，不尝试将其恢复为等待态。同一 SHA 可有多个历史检查。更新前后均确认本次 ID 仍是该 SHA 上同名、同 App 检查中的最新 ID。发现更新的检查后，旧执行停止写入，不把结果覆盖到新评估。

取证或发布期间确认 PR 换头或候选状态变化时，按原绑定完成失败检查。同轮已持有的准入与队列检查分别按原目标收尾，随后结束本轮。新候选由后续评估处理。确认队列 entry 被移除或替换时，先使原检查失效，再为替换候选建立检查。收尾仍遵守最新 ID 保护与下文的未知写入回读边界；收尾失败时停止并报告，不能声称原检查已失效。

确认失败时使用 `failure`。等待检查建立后，取证中断保留等待状态。CI 尚未启动、未完成或仍在等待前序 entry 时继续等待。上游 CI 沿用必需检查的 `success`、`neutral`、`skipped` 通过规则。关卡自身只发布 `success`、`failure` 或等待状态，不用失败或通过终态表示等待。发布前后重新核对同一份候选、事件、entry 与审查证据，包括实时整合基线。变化或读取失败时，对本次 ID 发布 `failure` 并回读。批准评估中发生漂移也停止本次放行，按原批准目标执行撤销。这种保守失效可能导致出队。后续评估重新判断复用条件，不仅因漂移就要求新模型审查。外部写入结果未知时按下段停止，不保证失效写入已经生效。CI 正常完成及队列就绪状态推进不视为身份失效。检查正文保存绑定与证据摘要，`external_id` 保存版本化绑定摘要，不另建审批或处置台账。

检查 POST 或 PATCH 每次最多写入一次，随后回读同一目标。POST 响应未知时，从原 SHA 的完整检查列表定位唯一新增且绑定一致的检查，再读准确 ID；不重复 POST。PATCH 只操作已确认 ID，响应失败仍读该 ID。回读核对 App ID 与 slug、SHA、名称、绑定、输出、状态和结论。结果未知时停止，不声称检查已成功或已撤销。上节的批准写入与回读边界继续适用。

共享 Cladiron App 与组织安装已接受 Checks write，Nucleus 的短期令牌仍仅限本仓库。`DEV_REVIEW_QUEUE` 为 `true` 时，关卡请求 Checks write，执行 `dev` 队列和 `main` 准入检查。其他取值只请求 Checks read，旧批准路径不会发布专属检查，不构成可用的合并路径。启用时，在授权范围内核对实际保护，再将变量设为 `true`。验收失败时恢复本次规则和变量变更，并回读原目标。App 权限上限已更新不代表保护或准入已通过验收。

本契约采用当次核验与异步失效的保证范围。关卡在每次评估中核对当前证据。处理变化事件时，按既有规则刷新检查并撤销失效批准。事件处理、检查写入和 GitHub 合并分别发生。本契约接受以下剩余风险：

- 重入复用同一合成 SHA 时，平台可能在关卡刷新前消费旧成功。现有证据没有证明该情况发生，也没有排除它。同 SHA 场景保留为未覆盖项，不记为验收通过。
- 成功检查发布后出现新审查活动时，GitHub 可能先合并，失效处理随后才生效。发布前后回读不能使审查状态与合并成为原子事务。
- 新增发现的现有证据只覆盖 PR 准入成功与受阻队列，未覆盖队列成功之后的失效。复审运行期间的撤销不能证明最终发现独立触发撤销。

启用验收不要求证明每次重入都生成新 SHA，也不要求证明失效总能先于合并完成。上述风险不允许合并者复用已知失效的批准或检查。已知新发现、证据矛盾和缺失的处置证据仍阻止放行。合并授权、最终准入状态、分支保护与未知写入回读继续按[交付入口](delivery.md#审查关卡与证据复用)执行。

输入未变的有效验收直接复用，改变的条件按受影响范围补验。准确候选、运行与结果保存在对应 PR：[早期实验 #1200](https://github.com/silence-force/nucleus-archive-20261025/pull/1200)、[准入与恢复 #1201](https://github.com/silence-force/nucleus-archive-20261025/pull/1201)、[出队重入 #1203](https://github.com/silence-force/nucleus-archive-20261025/pull/1203)、[基线推进 #1205](https://github.com/silence-force/nucleus-archive-20261025/pull/1205)、[旧成功重入 #1208](https://github.com/silence-force/nucleus-archive-20261025/pull/1208)、[重排候选 A #1211](https://github.com/silence-force/nucleus-archive-20261025/pull/1211)、[重排候选 B #1212](https://github.com/silence-force/nucleus-archive-20261025/pull/1212)、[新增发现 #1213](https://github.com/silence-force/nucleus-archive-20261025/pull/1213)。
