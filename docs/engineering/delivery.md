# 业务交付顺序

状态：当前目标交付计划。[架构](../architecture.md)拥有共同机制，各业务专题拥有规则。本文维护实施切片、开发循环、交付授权、分支流程、业务里程碑、剩余交付范围及验收入口。模型选择、委派和接续由[模型政策](models.md)维护。阶段编号不决定迁移编号，也不代表实现已经完成。

## 设计与实施边界

新增能力或调整职责前，先结合现有整体架构设计结构。追踪现有消费者的输入、构造、调用和错误处理，区分当前实现与目标设计。从已确认的业务问题、参与者、用例、事实与不变量出发。明确事实与规则的所有者、模块职责、依赖方向及主要调用流程，再决定表和 API 字段。说明复用哪些已有能力，以及新增边界的依据。

设计同时覆盖成功与失败路径。明确授权、事务和并发边界，以及任务、连接等资源的持有者与生命周期。说明谁处理取消和停止、谁核对未知结果、谁决定重试、谁记录最终失败。按[职责划分](../architecture.md#crate-与模块组织)核对接口与调用方所承担的规则。

设计详略与改动复杂度相称。简单修改可简述，已有有效设计直接复用；只重开缺失或被证据反驳的决定。考虑已确认的后续能力如何接入，具体设施仍随实际消费者实现。设计说明不要求固定模板或状态文件，也不新增审批环节；现有操作授权要求仍然适用。

已确认的业务事实保持权威，直到用户明确更改。区分已确认事实、观察、推断、提议和待定问题。旧确认标签或审查状态不能使已被替代的架构重新生效。

### 实施切片

整体梳理覆盖受影响的架构、调用链及消费者。分析范围不受当前切片的目录限制。只读分析或设计确认本身不授权实施。实施结果必须在用户明确授权的项目目标、批次或单片范围内。项目目标或批次授权有效时，由主代理自主选片；否则先由用户选定结果。

- 业务目标不直接决定 PR 范围。可整体设计完整架构，每次只实施已选定的结果。每个 PR 承担能独立说明、审查和验证的职责，最终集成负责完整业务结果。编码前确定组件与集成边界，说明直接依赖、各 PR 的验收结果和安全中间状态。隔离工作区中的实现和组合验证用于核验、修正已有边界，不代替首次划界。完整业务片仍限于已选结果，不扩大到后续路线图。用户授权项目目标或一批结果时，主代理在该范围内自主选片并逐片交付。仅授权单片时，在该片完成集成与验收后结束。认可阶段或架构本身不构成实施授权。
- 编码前明确本片唯一的可观察结果、必要改动、验收方式和排除的后续工作。按审查者必须同时理解的规则、消费者和不变量，选择最小完整结果。逐项判断：移除这项能力后，当前结果是否仍能完整、安全地成立？若能，将该能力作为独立结果另行交付；若不能，指出受损的具体事实或保证。项目目标或批次授权有效时，由主代理自主选定并说明本片。尚无覆盖这些结果的授权时，先推荐第一片供用户选择。已有业务确认直接复用。
- “开始”“继续”承接当前明确的工作和仍有效的授权。已有项目目标或批次授权时，自主进入其中的下一片。仅有单片授权时，不自动扩展到剩余路线图。范围不清时先澄清，再编码。片内必要的准备、实现、测试和缺陷修复自主完成。只为缺失的业务决定或范围变化询问用户，不反复确认普通可逆技术选择。
- 按业务行为和责任拆分。不要按端点、技术层、文件、目录、crate、行数或提交数机械划界。共享业务名称、调用关系或数据生产与消费关系，不足以证明必须同交。确需同交时，沿调用链指出拆分会破坏的具体不变量。例如必须共同成立的事实、事务原子性、原操作恢复身份或现有消费者保证。说明为何无法形成安全、可运行的中间版本。只有这些约束使更小边界不成立时，才选择最小必要的成套交付。拆文件不代替职责拆分，不把多个独立结果合成一个大 PR。
- 同一类缺陷可在一个 PR 中完整修复。先核对共同原因、受损不变量和相关调用链。统一修复已证实的实例，补齐各分支的差分验证。不要按函数或调用点机械拆片。只有表面相似、原因或验收结果独立的问题，仍分别选片。
- 独立的组件或集成 PR 从最新 `origin/dev` 创建工作分支，并以 `dev` 为目标。真实依赖链可使用[两层原生 stack](review-gate.md#两层原生-stack)：下层面向 `dev`，上层从下层准确候选创建并面向下层分支。各层分别承担完整职责、必要验证与审查，最终目标仍为 `dev`。同一 PR 的审查修复留在原分支，合并后不复用该分支。完整实现工作区保留到不再承担拆分、集成或验证。开始前核对工作区和远端，保留其他分支、worktree 与未提交工作。分支工作不替代提交、推送、开 PR 或合并所需的授权。合并和提升遵守[分支流程](#分支测试与提升)。
- 设施、设置、数据库结构和供应商接入必须绑定具体消费者，只实现该消费者所需部分。本仓库的当前或真实消费者包括已有调用方。同一业务片内已实现并完成组合验证、尚待集成的调用方也属于真实消费者。以此支撑组件先行时，真实调用方和组合证据是组件合入的必要条件。随后按依赖顺序集成。PR 说明绑定消费者的源码修订、验证范围和剩余集成步骤。设想、接口草图或测试替身本身不构成业务消费者，不据此预建后续能力。[应用内核](../architecture.md#应用内核)与[状态历史模块](../architecture.md#状态历史模块)把各用例共同的流程只实现一次。替换重复实现时，以被替换副本为消费者，随该消费者实际迁入删除旧副本。
- 每个组件或集成 PR 随功能代码交付直接覆盖其行为的必要测试和文档。测试覆盖该结果所需的拒绝、失败、恢复及保护。组件测试验证本组件，集成测试验证真实调用与组合行为；不把必要测试留到另一个 PR。每次合并后的中间版本必须可运行，并保留现有消费者的保证。最终集成负责接通入口、替换旧实现、同步配置与文档，并验证完整业务结果。组件已合并或独立测试通过，不代替最终集成验收。
- 这些边界同样适用于 TypeScript、Rust、应用内核和数据库组件。必须共同提交的事实、授权与受保护操作、事务与恢复责任保持成套交付。现有调用方仍依赖的[权限、锁函数和保护](../database.md#登录身份与部署)，保留到实际迁入且替代保证生效。不能保持安全且可运行的中间状态时，相关改动共同交付。迁入执行器的用例经内核取得原操作识别、恢复与错误分类；数据库继续承担[结构保护](../architecture.md#数据库与-rust-的职责)。拆分不改变这些职责，也不扩大实际数据库操作授权。
- 发现独立主题或新能力时，先核对是否超出当前片及有效授权。独立结果另行选片，继续完成当前片。当前结果确实需要调整实施边界时，先说明新增责任与原因。目标授权已覆盖且业务决定齐备时自主完成。超出有效授权时取得用户确认后再实施。等待期间继续不受影响的已授权工作。
- 完成当前片及已授权审查修复后，报告交付结果、验证证据与限制。项目目标或批次授权仍覆盖后续工作时，自主选定下一片并继续。片间报告不构成新的审批节点。授权范围已经完成时，再提出后续建议。路线图本身不授予实施权。当前片的缺陷修复仍属当前工作，不受任意迭代轮数限制。

拆分或替换已审查的 PR 时，将仍涉及接收候选的发现连同原报告链接移交。接收 PR 说明对应改动、已有处置证据和待解决问题。与新候选无关的发现须有差异或调用链依据，保留原报告及其去向。关闭原 PR、删除分支或新审查未再提及，都不代表原发现已经解决。覆盖及处置继续按[审查关卡与证据复用](#审查关卡与证据复用)核对，不重复审查输入未变的材料。

## 开发协作与交接

### 开发循环

每个业务片按下列时机检查实际产物。组件和集成 PR 分别完成发布前及 PR 更新后的检查，业务结果以最终集成验收为准。上文拥有范围和设计边界，[源码检查](verification.md#源码检查)拥有检查方法；具体规则仍归架构、语言和业务文档。已有设计和输入未变的验证直接复用。

| 时机           | 执行内容                                                                       | 完成依据                                                                               |
| -------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| 选片前         | 核对当前实现、适用规则和真实消费者，编码前按审查负担确定当前 PR 的最小完整结果 | 能指出规则所有者、实际调用链、必要改动、验收与排除范围；拆分时说明直接依赖及安全中间态 |
| 核心边界成形时 | 检查职责、接口、值类型、状态和事务边界，核对已有实现及适用库                   | 事实有明确所有者，类型和调用表达所需保证，新增概念有当前消费者                         |
| 补齐实现时     | 沿成功、拒绝、失败和恢复路径实现完整结果，随改动补齐适用验证与文档             | 结果可运行，失败后果和资源寿命可核对                                                   |
| 发布前         | 读取最终差异及受影响消费者，检查结构、规则落实、行为证据和残留引用             | 适用检查通过，必要证据齐备，剩余限制明确                                               |
| PR 更新后      | 处理实际审查发现，等待当前候选的最终准入结果                                   | 按下文流程完成已授权的合并与清理；当前业务片完成集成与验收后，再按授权选择下一片       |

实现者在扩展调用方前完成核心边界检查，不把所有结构问题留到代码写完后处理。修改共享类型、错误或资源边界时，重新追踪受影响的处理链。发现同类遗漏时检查本片相关消费者，修复后补做受影响验证。独立结果按实施切片规则处理。

完整验收的准备入口分别由[数据库交付验证](../database.md#交付验证)、[Halo 本地检查](../../halo/README.md#构建与本地检查)和[浏览器隔离验收](../../halo/README.md#浏览器隔离验收)维护。数据库沿用隔离集群、虚构数据与实际运行身份。Halo 沿用所属类型检查和真实后端、Nginx 夹具。准备时核对本片临时路径、测试账户与办理人资格，避免将准备错误带入完整验收。

这些检查由执行者在已授权范围内完成，不新增逐阶段审批或固定记录模板。委派结果的接纳按[模型政策](models.md#职责与委派)执行。检查结论及证据按[验证边界](verification.md#证据与自动化)记录。

### 连续交付与授权

持续授权可覆盖指定仓库的项目目标、有限批次或单个切片。先明确目标范围、完成条件、允许的操作和排除事项。用户明确要求自主完成项目时，由主代理依据已确认设计和最新实现选择依赖顺序。仍按[实施切片](#实施切片)逐片交付，切片是交付单位，不是逐次授权单位。实际授权及其条件保留在任务或 PR 记录中；本文不代表任何目标已经获准。

约定交付操作时，一并明确实施、验证、签名提交、普通推送和开 PR。PR 更新、同片审查修复、审查回复与线程处置也纳入同一约定。主代理在授权范围内确定工作分支、PR 编号和候选提交。这些标识尚未产生，不构成再次授权的理由。范围与条件仍有效时直接复用授权。首次推送、上下文压缩、新的发现项或进入下一片本身不结束授权。用户设定的累计次数、期限和禁止项仍有效。

用户后续收窄范围、暂停或取消任务时，按最新明确指令更新有效授权。只允许完成当前 PR 时，继续其必要修复、审查和已授权的合并。完成后停止，原目标不能据此启动下一片。主代理将变更同步给受影响的执行者。现有交接记录保留剩余授权及停止条件。笼统的“继续”沿用最近明确的范围，不自动恢复已暂停的目标。用户明确恢复目标后，才在恢复的范围与条件内接续。

持续授权可一并包含满足条件后的 `dev` 合并，无须等每个 PR 建立后再询问。合并仍要求必需检查通过、有效审查覆盖和发现处置完成。合并后清理该 PR 已无剩余用途的分支与专属工作区，再从最新基线继续交付。仍承担完整实现、集成或验证的工作区保留。`main` 提升、实际部署及真实供应商操作分别明确授权。修改保护规则或宿主权限配置同样如此。这些操作不由自主开发目标自动推定。

每片按[开发循环](#开发循环)完成实现、检查及已授权的发布。开 PR 后等待必需 CI 和审查结果。优先按[审查关卡与证据复用](#审查关卡与证据复用)确认合并条件，再报告结论。组件先合并不结束本业务片的集成、修复和完整验收责任。

每片完成后核对仍有效的授权与项目目标的剩余范围。继续其中获准且可独立推进的工作，直到完成条件满足或达到停止条件。合并和清理遵守[分支流程](#分支测试与提升)。新增业务决定、超出目标范围的能力或授权外操作只暂停依赖部分，其余获准工作继续。片内发现独立主题时重新选片；目标级授权覆盖该主题时，无须仅因它另成一片而再次申请。扩大目标范围仍由用户决定。

业务授权不改变宿主权限或 GitHub 分支保护。受限操作按固定目标申请必要权限。遭到拒绝时报告动作、来源和原因，仅暂停依赖部分。外部写入结果不明时先回读同一目标，已有授权不等于可以盲目重试。

### 审查关卡与证据复用

审查、Cladiron 关卡、分支保护与合并队列共同承担准入。日常开发按本节使用最终状态。关卡的可信身份、候选与基线绑定、新鲜度、失效和配置由[审查关卡契约](review-gate.md)维护。修改关卡、排查异常或审计流程时，再读取底层契约与实现。普通 PR 不重复检查这些内部条件。

发现处理者在处理审查意见时完成实质判断。在原线程记录修复及验证依据，或非阻塞建议的延期理由、拒绝依据，再解决线程。已知阻塞必须处理，不能仅靠解决线程、删除评论或撤销审查消除。输入未变的处置直接复用，不在合并前追加独立审计、定制报告或台账。交接复用原线程与 PR，接手者只处理剩余问题和已知矛盾。

`dev` 与 `main` 使用以下日常流程，平台配置由[关卡契约](review-gate.md#保护配置与准入异常)统一维护：

1. 确认当前 PR、目标和头提交属于授权范围，PR 开放且非草稿。
2. 等待当前候选的必需检查通过，包括指定 Cladiron App 的 `Cladiron review gate`，并由 GitHub 确认批准与合并条件。以这一最终准入结果为依据，不再读取批准正文、Codex 汇总、审查元数据、重开时间线、规则配置或历史处置来重建关卡判断。
3. 绑定准确头提交，按平台规则请求合并。`dev` 进入 squash 队列，`main` 使用 merge commit。回读最终合并结果；入队或请求成功不等于已经合并。合并后再清理本任务独有且不再使用的分支与工作区。

`dev` 目标 tip 前进时，由队列验证新的组合，不仅为同步基线而更新已审查的 PR。`main` 的当前基线由准入检查核对，基线变化时按检查提示更新候选。主动修改当前候选前，先取消其自动合并或排队请求。推送后等待新候选的最终准入结果。候选未变的审查与验证按实际输入复用。

本 PR 的执行者负责观察 GitHub CI、Codex 审查与队列条目。等待与结果接纳按[职责与委派](models.md#职责与委派)执行。状态尚未完成时等待；失败、意外出队、未知结果或已知矛盾时，只调查相关原因。出队先读移除原因与失败检查，必要时读规则执行记录，不能直接反复入队。修复后让流程重新给出准入结果。已知未解决缺陷即使遇到绿色状态也要停止合并。关卡缺失、不可用或覆盖不足时，暂停受影响路径并修复[仓库流程](review-gate.md#保护配置与准入异常)，不改由开发代理手工判定后放行。

仓库通过 Codex GitHub App 自动启动代码审查与安全审查。原 PR 负责人沿原句柄观察有正常进展的轮次。没有运行记录时先查触发与运行状态，缺少记录本身不授权重试。原自动审查异常长期停在 running，且有界调查确认可用表面没有有效进展时，负责人依据实际等待历史说明恢复原因。在完整审查交付或同类恢复的有效授权内，主动通过提供方支持的手动机制发起一次有界恢复，不逐次索取同范围授权。内部存活、结束或未公开的并存证明不作为首次恢复的前置条件；保留已发布的限制、次数额度与实际拒绝。

写前回读准确仓库、PR、head、提供方、审查种类、原轮次、结果及请求记录。内部运行 ID 不可见时，用可用的触发、时间与摘要绑定原轮。已有有效结果就消费，已有新轮就接续；未知手动写只回读原目标，不重发。写后在同一目标回读请求及新轮绑定。保留原轮与发现、恢复原因、新请求回执和轮次绑定，由原负责人维持每个结果面的唯一观察者。保留已完成 CI 与审查结果；一个请求联动多种审查时不另发重复请求。后续再次停滞须重新判断，不设全局分钟数或周期性重触发。缺少机制、授权或遭拒绝时报告具体依赖；恢复不授权取消原轮、修改配置、账号或权限。

恢复规则采用 [agents 审查政策（7396807）](https://github.com/silence-force/agents/blob/739680761c13dcb3e3d2bb216360dfe453a89d07/delivery/policy/review.md#stalled-review-recovery)的有界恢复判据，由本文拥有项目规则；验收输入见[审查恢复场景](model-scenarios.md#审查恢复)。个人安装更新不自动改变项目规则。

项目接受可信公开完成状态、已解决线程和必需检查作为自动准入依据。它不表示机器理解每项修复，也不证明供应商完整报告已公开。发现处理责任与已知异常处理仍然有效。

关卡契约或实现的变更，按目标分支的既有可信契约直接审查。候选不能扩大自身的信任范围。升级后的 `nucleus-review-gate:v4` 明确上述责任划分；控制器不接受旧格式批准，按当前证据正常刷新。自动流程仍采用[当次核验与异步失效](review-gate.md#dev-队列检查)，不承诺审查活动与合并原子完成。

## 分支、测试与提升

`dev` 是仓库默认分支，承担日常集成和测试候选。当前应用先在 `dev` 完成全部选定功能，再部署到测试环境使用。完整功能验收通过后，才向 `main` 提升。开发期间逐片验证，最终再做整体业务验收。现有分支名不构成应用完整或部署可用的证据。

功能 PR 仍只交付一个可独立验收的组件或集成结果。合入 `dev` 前完成适用检查和实际审查，使用 squash 保留每个 PR 的结果。`dev` 的分支规则仅允许 squash 合并。[队列检查](#dev-队列检查)启用后，合入 `dev` 必须经过队列。文档、Rust 和 Halo CI 支持 PR 与队列候选，合并前必须通过对应候选上的必需检查。独立的[依赖缓存准备](rust.md#workspace-validation)从受保护的 `dev` 提供跨 PR 缓存，不替代检查。确认合并后按[实施切片](#实施切片)清理已无剩余用途的分支和专属工作区，保留长期分支、仍需使用的完整实现工作区及无关工作。

合并回读后，交付代理核对本片委派任务、本地验证进程和远端运行。仍有验收目的、服务其他候选或承担共享维护的任务继续运行。只停止本片已无剩余用途的运行，包括已被替代或重复的工作。停止前绑定准确任务、进程或运行 ID，核对所属 PR、候选与用途，并复用适用授权。不按相同名称或合并提交批量取消，也不取消共享审查关卡来清理单个 PR。

区分仍在执行的任务、已完成运行和历史检查记录。旧检查显示等待，不单独证明工作仍在运行；先回读对应执行和最新候选状态。停止本地等待不证明远端操作结束。存在未知外部写入时，先完成原目标回读；取消后确认实际终态，再释放其使用的分支、工作区与材料。无法确认或无权停止时，保留依赖资源并报告准确目标与限制。单片收尾不结束仍有效的目标级任务，后续切片按原授权继续。

仓库的 squash 消息采用 `PR_TITLE` / `COMMIT_MESSAGES`。标题取 PR 标题并保留 PR 编号后缀，正文取原始提交消息。模型与会话 trailers 保留在原始签名提交中，无须复制到 PR 正文。合并后回读最终提交，核对标题与 trailers。

两条长期分支都要求 PR、签名提交、必需 CI 和审查线程解决，并禁止强推和删除。GitHub Rulesets 拥有远端强制配置。[日常合并](#审查关卡与证据复用)使用流程最终状态，配置审计按[关卡契约](review-gate.md)进行。准入通过不替代当前业务片的功能验收。

当前两条分支的保护规则集均无 bypass，不另设 `Restrict updates` 合并人白名单。仓库写权限决定可执行合并的身份，保护规则继续约束合并条件。遇到 `BLOCKED` 时读取具体未满足条件及实际规则，区分检查、审查和引用更新权限；不要仅凭汇总状态修改保护配置。

最终测试绑定确定的 `dev` 提交。测试期间冻结新功能合入，只接收修复。修复后更新候选，并补做受影响验证；输入未变的有效结果继续复用。测试环境的实际部署与使用验收另行授权。当前分支配置不代表测试环境已经建立。

提升 PR 从已验收的 `dev` 向 `main` 提交。正文汇总所含功能 PR、准确候选、测试结果和剩余限制。合并前取得最终候选相对 `main` 基线的审查覆盖。此前逐片审查作为证据保留，不能替代组合后的验收。提升 PR 只整合已交付的切片，不在其中继续开发独立功能。

提升使用 merge commit，保留各片提交和共同历史。`main` 的分支规则仅允许 merge 合并。提升后继续从 `dev` 开发；已提升的提交仍是两条分支的共同祖先，无需仅为历史对齐将 `main` 合回 `dev`。

网站独立构建和托管，逐片消费后端入口，发布边界见[网站交付](../http/site.md)。小程序在网站基础能力之后交付本人服务。工牌流程先由网站完整办理。前端页面范围见[网站与小程序页面](../client/pages.md)，传输和恢复见[客户端协议](../client/protocol.md)。

S1 用隔离场景覆盖现有账户和无账户分流。正式业务账户来源在 S2 交付，测试预置不能代替初始化与注册验收。S2 在空业务库建立系统角色和首个管理员，之后开放注册；初始化不签发在线会话。

每片只引入实际消费者需要的设施和表。后续消费者必须同时接入已交付的暂停、注销、实名更正、工号撤销和历史读取后果。S2 的默认头像使用部署发布资源。S3 本人读取同时交付其签名链接和匿名图片读取，S7 再交付用户上传文件能力。

Schedule、旧系统导入、数据迁移、共存和切换不在计划内。工号业务允许的单项历史补录由[工号](../workforce/numbers.md)拥有，不扩展为批量导入旧系统。

## 里程碑与生产准备

每片先通过所属隔离验收。里程碑再验收已组合的业务链，不能用各 PR 的通过状态推定组合成功。开发完成后的最终测试仍按[分支流程](#分支测试与提升)固定候选并冻结新功能。

建议在全部功能完成前增加阶段性测试环境验收，具体时机和环境见[待确认事项](#待确认事项)。授权前继续隔离开发，不调用真实供应商。阶段性验收不表示提前向 main 提升，也不改变最终完整功能验收的要求。

| 决定                         | 推荐与理由                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | 影响的切片                         |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 公开读取的缓存规则与预算组   | 公开 JSON 保持 `no-store`，只由站点服务端内存缓存，建议新鲜期 60 秒、nucleus 不可用时最多用 24 小时旧数据；公开图片 `public, max-age=3600`，不用 immutable，使撤回内容的图片在有界时间内退出缓存；公开图片宽限 10 分钟，长于 60 秒新鲜期并留出余量。JSON 预算按现有分组量级：来源每秒 10、容量 20，进程每秒 50、容量 100。图片预算按单页最多图片数确定，因为浏览器原生图片请求遇到 429 或 503 不会重试：首页解析后至多 144 张、文章至多 101 张（含封面）、管理图片列表一页至多 100 张，故来源每分钟 600、容量 200，进程每秒 200、容量 400，另设 32 个传输许可，并由页面延迟加载首屏以外的图片。浏览器不直接读公开 JSON，HTTP 缓存头对它没有收益 | 栏目与文章、内容图片、公开页面渲染 |
| 小程序公开简介是否读同一接口 | 读取同一套公开接口，只展示首页编排的子集，正文用原生组件按节点渲染。避免两套内容事实；结构化正文便于原生渲染；须在小程序合法域名中登记 API origin                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | 另行选片                           |

## 验收与证据

每片按[验证边界](verification.md#检查范围)选择检查，具体命令与依赖边界由 [Rust 工作区规则](rust.md#workspace-validation)拥有。业务验收通过真实进程和公开协议；数据库使用隔离 PostgreSQL、真实迁移和运行身份，材料全部虚构。

共同故障场景由[架构验收矩阵](../architecture.md#隔离验收)拥有。各片补齐自己的准确输入、预期后果、竞争对象和失败恢复，覆盖原证明、异输入、响应丢失、提交未知、普通重启及技术清理。迁入执行器的命令由内核流程测试统一覆盖重放、异输入、响应丢失、提交未知、恢复与排空，所属片只验证本命令的拒绝、纯判断与数据库往返。文件逐同步点注入故障；供应商替身记录实际次数及请求字节。

交付状态见[能力状态](../README.md#能力状态)。现有测试只覆盖对应的已交付能力，不证明完整业务阶段已通过运行验收，也不证明目标架构已经实现。

迁移的拆分遵守[实施切片](#实施切片)中的消费者和中间版本保护要求。持久数据库已应用的迁移保持不变，隔离测试不冻结迁移。文档检查只验证格式、结构和引用，不提供业务或运行就绪证明。
