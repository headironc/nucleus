# 业务交付顺序

状态：当前目标交付计划。[架构](../architecture.md)拥有共同机制，各业务专题拥有规则。本文维护实施切片、开发循环、交付授权、分支流程、业务里程碑、剩余交付范围及验收入口。模型选择、委派和接续由[模型政策](models.md)维护。阶段编号不决定迁移编号，也不代表实现已经完成。

## 设计与实施边界

新增能力或调整职责前，先结合现有整体架构设计结构。追踪现有消费者的输入、构造、调用和错误处理，区分当前实现与目标设计。从已确认的业务问题、参与者、用例、事实与不变量出发。明确事实与规则的所有者、模块职责、依赖方向及主要调用流程，再决定表和 API 字段。说明复用哪些已有能力，以及新增边界的依据。

设计同时覆盖成功与失败路径。明确授权、事务和并发边界，以及任务、连接等资源的持有者与生命周期。说明谁处理取消和停止、谁核对未知结果、谁决定重试、谁记录最终失败。按[职责划分](../architecture.md#crate-与模块组织)核对接口与调用方所承担的规则。

设计详略与改动复杂度相称。简单修改可简述，已有有效设计直接复用；只重开缺失或被证据反驳的决定。考虑已确认的后续能力如何接入，具体设施仍随实际消费者实现。设计说明不要求固定模板或状态文件，也不新增审批环节；现有操作授权要求仍然适用。

已确认的业务事实保持权威，直到用户明确更改。区分已确认事实、观察、推断、提议和待定问题。旧确认标签或审查状态不能使已被替代的架构重新生效。

### 实施切片

整体梳理覆盖受影响的架构、调用链及消费者。分析范围不受当前切片的目录限制。只读分析或设计确认本身不授权实施。实施结果必须在用户明确授权的项目目标、批次或单片范围内。项目目标或批次授权有效时，由主代理自主选片；否则先由用户选定结果。

- 业务目标不直接决定 PR 范围。可整体设计完整架构，每次只实施已选定的结果。每个 PR 承担能独立说明、审查和验证的职责，最终集成负责完整业务结果。编码前确定组件与集成边界，说明直接依赖、各 PR 的验收结果和安全中间状态。隔离工作区中的实现和组合验证用于核验、修正已有边界，不代替首次划界。完整业务片仍限于已选结果，不扩大到后续路线图。用户授权项目目标或一批结果时，主代理在该范围内自主选片并逐片交付。仅授权单片时，在该片完成集成与验收后结束。认可阶段或架构本身不构成实施授权。
- 编码前明确本片唯一的可观察结果、必要改动、验收方式和排除的后续工作。按审查者必须同时理解的规则、消费者和不变量，选择最小完整结果。逐项判断：移除这项能力后，当前结果是否仍能完整、安全地成立？若能，将该能力作为独立结果另行交付；若不能，指出受损的具体事实或保证。项目目标或批次授权有效时，由主代理自主选定并说明本片。尚无覆盖这些结果的授权时，先推荐第一片供用户选择。已有业务确认直接复用。
- “开始”“继续”承接当前明确的工作和仍有效的授权。已有项目目标或批次授权时，自主进入其中的下一片。仅有单片授权时，不自动扩展到剩余路线图。范围不清时先澄清，再编码。片内必要的准备、实现、测试和缺陷修复自主完成。只为缺失的业务决定或范围变化询问用户，不反复确认普通可逆技术选择。
- 按业务行为和责任拆分。不要按端点、技术层、文件、目录、crate、行数或提交数机械划界。共享业务名称、调用关系或数据生产与消费关系，不足以证明必须同交。确需同交时，沿调用链指出拆分会破坏的具体不变量。例如必须共同成立的事实、事务原子性、原操作恢复身份或现有消费者保证。说明为何无法形成安全、可运行的中间版本。只有这些约束使更小边界不成立时，才选择最小必要的成套交付。拆文件不代替职责拆分，不把多个独立结果合成一个大 PR。
- 同一类缺陷可在一个 PR 中完整修复。先核对共同原因、受损不变量和相关调用链。统一修复已证实的实例，补齐各分支的差分验证。不要按函数或调用点机械拆片。只有表面相似、原因或验收结果独立的问题，仍分别选片。
- 独立的组件或集成 PR 从最新 `origin/dev` 创建工作分支，并以 `dev` 为目标。真实依赖链可使用[两层原生 stack](review-gate.md#两层原生-stack)：下层面向 `dev`，上层从下层准确候选创建并面向下层分支。各层分别承担完整职责、必要验证与审查，最终目标仍为 `dev`。同一 PR 的审查修复留在原分支，合并后不复用该分支。完整实现工作区保留到不再承担拆分、集成或验证。开始前核对工作区和远端，保留其他分支、worktree 与未提交工作。分支工作不替代提交、推送、开 PR 或合并所需的授权。合并和提升遵守[分支流程](#分支测试与提升)。
- 设施、设置、数据库结构和供应商接入必须绑定具体消费者，只实现该消费者所需部分。本仓库的当前或真实消费者包括已有调用方。同一业务片内已实现、尚待集成的调用方也属于真实消费者。以此支撑组件先行时，绑定调用方的源码修订、实际调用契约和组件验证，保留安全、可运行的中间状态。最终页面与后端的端到端验收在形成可运行的集成候选后执行，不作为每个组件开发或开 PR 的统一前置条件。组件必要的权限、事务、并发、失败和恢复检查仍随本组件交付。PR 说明验证范围、剩余集成步骤及其负责人。设想、接口草图或测试替身本身不构成业务消费者，不据此预建后续能力。[应用内核](../architecture.md#应用内核)与[状态历史模块](../architecture.md#状态历史模块)把各用例共同的流程只实现一次。替换重复实现时，以被替换副本为消费者，随该消费者实际迁入删除旧副本。
- 每个组件或集成 PR 随功能代码交付直接覆盖其行为的必要测试和文档。测试覆盖该结果所需的拒绝、失败、恢复及保护。组件测试验证本组件，集成测试验证真实调用与组合行为；不把必要测试留到另一个 PR。每次合并后的中间版本必须可运行，并保留现有消费者的保证。最终集成负责接通入口、替换旧实现、同步配置与文档，并验证完整业务结果。组件已合并或独立测试通过，不代替最终集成验收。
- 这些边界同样适用于 TypeScript、Rust、应用内核和数据库组件。必须共同提交的事实、授权与受保护操作、事务与恢复责任保持成套交付。现有调用方仍依赖的[权限、锁函数和保护](../database.md#登录身份与部署)，保留到实际迁入且替代保证生效。不能保持安全且可运行的中间状态时，相关改动共同交付。新普通业务使用短事务、状态条件与审计；仍依赖旧内核的消费者保留原合同，直至整套迁出。数据库继续承担[结构保护](../architecture.md#数据库与-rust-的职责)。拆分不改变这些职责，也不扩大实际数据库操作授权。
- 发现独立主题或新能力时，先核对是否超出当前片及有效授权。独立结果另行选片，继续完成当前片。当前结果确实需要调整实施边界时，先说明新增责任与原因。目标授权已覆盖且业务决定齐备时自主完成。超出有效授权时取得用户确认后再实施。等待期间继续不受影响的已授权工作。
- 完成当前片及已授权审查修复后，报告交付结果、验证证据与限制。项目目标或批次授权仍覆盖后续工作时，自主选定下一片并继续。片间报告不构成新的审批节点。授权范围已经完成时，再提出后续建议。路线图本身不授予实施权。当前片的缺陷修复仍属当前工作，不受任意迭代轮数限制。

拆分或替换已审查的 PR 时，将仍涉及接收候选的发现连同原报告链接移交。接收 PR 说明对应改动、已有处置证据和待解决问题。与新候选无关的发现须有差异或调用链依据，保留原报告及其去向。关闭原 PR、删除分支或新审查未再提及，都不代表原发现已经解决。覆盖及处置继续按[审查关卡与证据复用](#审查关卡与证据复用)核对，不重复审查输入未变的材料。

## 开发协作与交接

### 开发循环

每个业务片按下列时机检查实际产物。组件和集成 PR 分别完成发布前及 PR 更新后的检查，业务结果以最终集成验收为准。上文拥有范围和设计边界，[源码检查](verification.md#源码检查)拥有检查方法；具体规则仍归架构、语言和业务文档。已有设计和输入未变的验证直接复用。

| 时机           | 执行内容                                                                       | 完成依据                                                                               |
| -------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| 选片前         | 核对当前实现、适用规则和真实消费者，编码前按审查负担确定当前 PR 的最小完整结果 | 能指出规则所有者、实际调用链、必要改动、验收与排除范围；拆分时说明直接依赖及安全中间态 |
| 核心边界成形时 | 检查职责、接口、值类型、状态和事务边界，核对已有实现及适用库                   | 事实有明确所有者，类型和调用表达所需保证，新增概念有当前消费者                         |
| 补齐实现时     | 沿成功、拒绝、失败和恢复路径实现完整结果，随改动补齐适用验证与文档             | 结果可运行，失败后果和资源寿命可核对                                                   |
| 发布前         | 读取最终差异及受影响消费者，检查结构、规则落实、行为证据和残留引用             | 适用检查通过，必要证据齐备，剩余限制明确                                               |
| PR 更新后      | 处理实际审查发现，核对当前候选的本地检查及托管审查结果                         | 按下文流程完成已授权的合并与清理；当前业务片完成集成与验收后，再按授权选择下一片       |

实现者在扩展调用方前完成核心边界检查，不把所有结构问题留到代码写完后处理。修改共享类型、错误或资源边界时，重新追踪受影响的处理链。发现同类遗漏时检查本片相关消费者，修复后补做受影响验证。独立结果按实施切片规则处理。

完整验收的准备入口分别由[数据库交付验证](../database.md#交付验证)、[Halo 本地检查](../../halo/README.md#构建与本地检查)和[浏览器隔离验收](../../halo/README.md#浏览器隔离验收)维护。数据库沿用隔离集群、虚构数据与实际运行身份。Halo 沿用所属类型检查和真实后端、Nginx 夹具。准备时核对本片临时路径、测试账户与办理人资格，避免将准备错误带入完整验收。

这些检查由执行者在已授权范围内完成，不新增逐阶段审批或固定记录模板。委派结果的接纳按[模型政策](models.md#职责与委派)执行。检查结论及证据按[验证边界](verification.md#证据与自动化)记录。

### 双机开发与集成

本机网站、小程序与 `dev` 后端按[双机职责](models.md#双机职责)各自完成开发循环。双方先对齐本片的业务契约和接口，再在各自绑定工作区实现、验证、修复并完成已授权交付。跨端依赖通过契约、准确提交、PR 与原始证据协作，不把未提交源码打包后经 tar/scp 往返传递作为常规验收路径。

可独立接纳的结果分别提交 PR，仍遵守[实施切片](#实施切片)的真实消费者和安全中间态要求。集成负责人通过正常 Git 流程取得准确修订，记录组件 head、目标基线与实际集成候选。依赖尚未合入时，明确所消费的提交及整合结果；不要用浮动分支名或对方的工作目录代替候选身份。发布或合并尚未获授权时，保留各自候选与缺失阶段，不用搬运 WIP 绕过交付边界。

各端先完成实现、协议核对、受影响测试、构建及必要界面检查，形成各自 PR 候选。随后按正常流程审查、修复和集成。尚未形成可运行的集成候选时，明确后续端到端验收项、负责人和前提，不阻塞已满足自身交付条件的独立结果。当前组件自身的权限、事务、失败和恢复检查不延后。

这里的组合验收是验证本片页面与真实后端能共同完成业务，并保留适用的权限、失败和恢复保证。前后端在明确候选或测试环境汇合后，再执行这项端到端验收，作为整片完成依据。它沿用已有业务验收，不新增统一运行器、全量重跑或跨机搬源码要求。总协调安排具体负责人和消费候选；执行方式与覆盖按[双机验证](verification.md#双机验证与能力缺口)核实。两端各自通过检查或组件已合并，只证明各自覆盖；最终业务结果由匹配集成候选的证据接纳。

### 连续交付与授权

持续授权可覆盖指定仓库的项目目标、有限批次或单个切片。先明确目标范围、完成条件、允许的操作和排除事项。用户明确要求自主完成项目时，由主代理依据已确认设计和最新实现选择依赖顺序。仍按[实施切片](#实施切片)逐片交付，切片是交付单位，不是逐次授权单位。实际授权及其条件保留在任务或 PR 记录中；本文不代表任何目标已经获准。

约定交付操作时，一并明确实施、验证、签名提交、普通推送和开 PR。PR 更新、同片审查修复、审查回复与线程处置也纳入同一约定。主代理在授权范围内确定工作分支、PR 编号和候选提交。这些标识尚未产生，不构成再次授权的理由。范围与条件仍有效时直接复用授权。首次推送、上下文压缩、新的发现项或进入下一片本身不结束授权。用户设定的累计次数、期限和禁止项仍有效。

用户后续收窄范围、暂停或取消任务时，按最新明确指令更新有效授权。只允许完成当前 PR 时，继续其必要修复、审查和已授权的合并。完成后停止，原目标不能据此启动下一片。主代理将变更同步给受影响的执行者。现有交接记录保留剩余授权及停止条件。笼统的“继续”沿用最近明确的范围，不自动恢复已暂停的目标。用户明确恢复目标后，才在恢复的范围与条件内接续。

持续授权可一并包含满足条件后的 `dev` 合并，无须等每个 PR 建立后再询问。合并仍要求适用本地检查通过、有效托管审查覆盖和发现处置完成。合并后清理该 PR 已无剩余用途的分支与专属工作区，再从最新基线继续交付。仍承担完整实现、集成或验证的工作区保留。`main` 提升、实际部署及真实供应商操作分别明确授权。修改保护规则或宿主权限配置同样如此。这些操作不由自主开发目标自动推定。

每片按[开发循环](#开发循环)完成实现、检查及已授权的发布。开 PR 后核对适用本地检查并等待当前候选的托管审查结果。按[审查关卡与证据复用](#审查关卡与证据复用)确认合并条件，再报告结论。组件先合并不结束本业务片的集成、修复和完整验收责任。

每片完成后核对仍有效的授权与项目目标的剩余范围。继续其中获准且可独立推进的工作，直到完成条件满足或达到停止条件。合并和清理遵守[分支流程](#分支测试与提升)。新增业务决定、超出目标范围的能力或授权外操作只暂停依赖部分，其余获准工作继续。片内发现独立主题时重新选片；目标级授权覆盖该主题时，无须仅因它另成一片而再次申请。扩大目标范围仍由用户决定。

业务授权不改变宿主权限或 GitHub 分支保护。受限操作按固定目标申请必要权限。遭到拒绝时报告动作、来源和原因，仅暂停依赖部分。外部写入结果不明时先回读同一目标，已有授权不等于可以盲目重试。

### 审查关卡与证据复用

旧 CI、Cladiron 关卡和自动准入工作流已退役。当前平台采用[普通分支保护](#普通分支保护)，强制当前候选的四项原生 CI 检查通过。交付负责人另行验收适用本地检查和业务结果。普通开发 PR 按下文请求 Cubic 与 Codex，提供方选择和额度兜底遵守采用的共享规则。仓库自有 App 核验适用审查路线后批准仍为交付目标。晋级的 AI 审查例外由[项目指令](../../AGENTS.md#commits-and-review)拥有，不将本节审查或其 App 批准条件扩大到 `dev`→`main` 提升。审查通过本身仍不授权合并。旧部署协议与原操作恢复由[历史关卡契约](review-gate.md)解释，不恢复旧流程。

每个 PR 的唯一执行者绑定 PR、完整 head 提交和目标分支基线，完成[适用本地检查](verification.md#检查范围)及适用审查。发现处理者核对已出现的具体缺陷，在原线程记录修复及验证，或非阻塞建议的延期理由、拒绝依据，再解决线程。保留原严重度及处置原因；解决线程不能代替缺陷修复。候选或相关基线变化后补齐受影响覆盖，输入未变的证据继续复用。保留旧轮发现及处置，不以新轮无发现抹去旧缺陷。

合并前确认 PR 开放、非草稿，目标和准确头提交属于有效授权。检查实际平台合并状态，遇到拒绝或已知未解决缺陷时停止并处理具体原因，不使用管理员绕过。绑定准确头提交，普通功能 PR 使用 squash，提升 PR 按[分支流程](#分支测试与提升)保留历史。合并结果未知时先回读同一 PR，不重复发送。确认合并后清理本任务独有且不再使用的分支与工作区，保留恢复材料和其他工作。

#### 普通开发 PR 的手动审查

提供方选择及额度兜底采用 [agents 审查规则（36d239e）](https://github.com/headironc/agents/blob/36d239ead2ea214e720e3ae555226beb4d81ba36/delivery/policy/review.md#review-provider-selection)。本仓库普通开发 PR 正常显式请求两方；证实 Cubic 额度不足时，按该规则由 Codex 完成适用代码与安全审查，不把 Cubic 未执行记录为通过。额度判断、账号与用量池绑定及恢复边界由共享源拥有。

负责人不等待自动触发或自动轮次超时。写前先回读同一 PR、head 和基线的有效请求与结果，复用已有覆盖，不重复请求。按 [Cubic 官方调用](https://docs.cubic.dev/ai-review/introduction)，发表评论 `@cubic-dev-ai review this PR`；按 [Codex 官方调用](https://learn.chatgpt.com/docs/third-party/github)，发表评论 `@codex review`。所选路线的首次请求属于正常交付流程，不属于异常恢复。

Cubic 的[普通 PR 审查包含安全范围](https://docs.cubic.dev/ai-review/key-features)，不虚构独立的 security 触发命令。Codex 则分别核对 Code Review 与 Security Review 的完成结果。先确认代码请求是否已实际联动安全审查；已有有效安全请求或结果时沿原句柄接续，仅在未覆盖时补发 `@codex security review`。联动设置及两种命令的契约见上述 Codex 官方文档。[Cubic 手动请求](https://docs.cubic.dev/ai-review/ai-review-settings)仍受文件忽略规则和实际限制约束；手动请求回执不证明全部必要材料已审。

各方证据绑定请求 ID、对应运行和完成结果，并保留提供方身份、PR、完整 head、目标基线、实际范围与未覆盖材料。核对真实报告、完成语义及全部结果面上的发现。接受无发现结论时，确认提供方的完成报告明确覆盖所绑定的候选及范围。单独的 `SUCCESS`、summary、反应图标或零线程不证明审查执行。明确跳过、仅合并而未审、额度耗尽、未运行、失败或未知均不算该方通过。Cubic 额度兜底只改变适用路线，不伪造其成功结果。可选或为 `null` 的报告字段不推定为“无问题”，应从对应完整报告或独立完成回执核实；结果仍未知时保持批准依赖未完成。

原负责人沿现有句柄观察所选路线的完成结果与发现。审查异常时保留原轮次及未知写入，按[审查恢复场景](model-scenarios.md#审查恢复)与已采用的[有界恢复规则](https://github.com/silence-force/agents/blob/739680761c13dcb3e3d2bb216360dfe453a89d07/delivery/policy/review.md#stalled-review-recovery)处理。适用路线仍缺覆盖时只阻塞依赖该审查的批准，继续独立获准工作，不更换账号或修改配置。晋级已有的 AI 请求和报告保留真实状态，不因例外而删除证据，也不为取得审查绿灯重新触发。

#### App 核验与批准目标

普通开发 PR 的批准目标由仓库自有 Cladiron App 执行：所选路线的代码与安全审查全部通过、发现处置完成、无未解决 inline review thread，并且当前候选的适用 CI 全部成功后，才发布 `APPROVE`。采用 Cubic 额度兜底时保留共享规则要求的证据，核实 Codex 的两类完成结果，不再等待 Cubic 通过。读取 inline 状态时完整分页查询 GitHub `reviewThreads`，逐项确认 `isResolved`。曾有评论且已处置、resolve 的线程符合要求；`isOutdated` 不代替解决。REST comments 列表为空、计数为零或只读取第一页都不证明全部线程已解决。没有 inline thread 的报告或其他结果面上的阻塞发现仍须处置。

CI 的候选绑定遵守[触发与选检](verification.md#ci-触发与选检)，按[普通分支保护](#普通分支保护)核验各适用 workflow 最新有效 run/attempt。四项稳定 required checks 与受影响的专用 CI 都成功才满足批准条件。批准前回读候选、相关基线、审查、线程与 CI，发生变化时补齐受影响证据。

App 的源码与本地模拟见[机器合同](review-approval.md)，凭据、部署与真实行为分别验收，状态见[能力状态](../README.md#能力状态)。App 完成真实行为验收并启用前，普通开发 PR 按本节现行准入和有效 Human 合并授权执行；该阶段不另授合并权限。源码合并不证明 App 已批准，也不自动启用程序或使其成为平台强制条件。缺少真实批准时，批准阶段仍未完成。需要 App 批准的动作继续核对真实结果，不以人工身份替代或伪造 App 批准，不绕过平台保护，也不恢复旧控制器。批准完成后仍按有效授权、平台保护和本节合并回读规则执行。

## 分支、测试与提升

`dev` 是仓库默认分支，承担日常集成和测试候选。当前应用先在 `dev` 完成全部选定功能，再部署到测试环境使用。完整功能验收通过后，才向 `main` 提升。开发期间逐片验证，最终再做整体业务验收。现有分支名不构成应用完整或部署可用的证据。

功能 PR 仍只交付一个可独立验收的组件或集成结果。合入 `dev` 前完成适用检查和实际审查，使用 squash 保留每个 PR 的结果。[普通分支保护](#普通分支保护)约束合并方式；旧[队列入口](#dev-队列检查)继续停用。本地检查、原生 CI 及实际审查仍绑定当前候选。确认合并后按[实施切片](#实施切片)清理已无剩余用途的分支和专属工作区，保留长期分支、仍需使用的完整实现工作区及无关工作。

合并回读后，交付代理核对本片委派任务、本地验证进程和远端运行。仍有验收目的、服务其他候选或承担共享维护的任务继续运行。只停止本片已无剩余用途的运行，包括已被替代或重复的工作。停止前绑定准确任务、进程或运行 ID，核对所属 PR、候选与用途，并复用适用授权。不按相同名称或合并提交批量取消，也不取消共享审查关卡来清理单个 PR。

区分仍在执行的任务、已完成运行和历史检查记录。旧检查显示等待，不单独证明工作仍在运行；先回读对应执行和最新候选状态。停止本地等待不证明远端操作结束。存在未知外部写入时，先完成原目标回读；取消后确认实际终态，再释放其使用的分支、工作区与材料。无法确认或无权停止时，保留依赖资源并报告准确目标与限制。单片收尾不结束仍有效的目标级任务，后续切片按原授权继续。

仓库的 squash 消息采用 `PR_TITLE` / `COMMIT_MESSAGES`。标题取 PR 标题并保留 PR 编号后缀，正文取原始提交消息。模型与会话 trailers 保留在原始签名提交中，无须复制到 PR 正文。合并后回读最终提交，核对标题与 trailers。

### 普通分支保护

两条长期分支采用具名普通规则：[dev 配置](../../.github/rulesets/dev.json)只匹配 `refs/heads/dev`，[main 配置](../../.github/rulesets/main.json)只匹配 `refs/heads/main`。两者均为 active，无 bypass。规则要求 PR、签名提交和解决全部审查线程，禁止强推与删除。`dev` 仅允许 squash，`main` 仅允许 merge commit。人工批准数为 0，不要求 CODEOWNERS 或最后一次推送的人工批准。

两条分支均要求 `Nucleus Docs`、`Nucleus Maintenance tools`、`Nucleus Rust checks` 和 `Nucleus Packages` 通过。检查来源限定为 GitHub Actions（integration ID `15368`）。启用 strict，要求候选包含目标分支的最新代码；创建分支也不豁免。四个检查都无路径过滤，始终上报；Rust 与 package 的内部选检仍按[实际选检范围](verification.md#ci-触发与选检)执行。带路径过滤的专用检查和动态矩阵行不列为全局 required checks。

合并前核对当前候选各适用 workflow 最新有效 run/attempt 的四项检查均已完成且为 `success`。被重跑替代的旧失败保留历史，不永久阻塞。最新运行失败、取消、超时、缺失、等待或旧候选成功均阻止合并。不能通过取消当前必要运行、复用旧绿灯、禁用规则或管理员绕过取得合并资格。平台允许的 `neutral` 或 `skipped` 也不代替这四个稳定检查的成功；工作流内部按合同跳过步骤，由稳定检查验证选检结果后上报成功。受影响的专用 CI 仍须通过，代码与安全审查、发现处置及业务验收继续按[日常合并流程](#审查关卡与证据复用)执行。

版本化 JSON 是平台配置输入，不是实际启用的证明。配置负责人在变更前保存完整前态。完成准确候选的正式审查，再用隔离夹具验证阻断及允许路径。启用后回读同一规则和有效分支规则，核对匹配范围、参数与无 bypass。写入结果未知时先查原目标；部分成功时保留准确状态并停止依赖合并。新规则造成已授权正常流程故障时，按保存前态恢复受影响规则并回读，不加 bypass。验收后清理本片临时夹具，保留验收和恢复原件。

旧组织与个人准入实现保留用于原操作解释和离线恢复测试，当前不作为写入入口。冻结来源、凭据、Environment 和操作历史各有原所有者；普通保护的配置变更不授权修改这些材料。

### 关闭 PR 后锁定讨论

[Lock closed PR](../../.github/workflows/lock-pr.yml) 响应 `pull_request_target.closed`，覆盖合并与直接关闭。GitHub 从默认分支 `dev` 读取工作流，PR 的目标分支不改变源码来源。先完成正式审查与发现处置，再合并；关闭后的锁定不替代审查，也不修改固定提升候选。

作业只授予 `pull-requests: write`，通过 API 操作事件中的同一 PR，不检出或执行候选代码。先读取最新状态；仍开放或已锁定时结束。关闭且未锁定时只发送一次锁定请求，再回读原 PR。请求失败也先回读，不重复写入；无法确认锁定就失败。每个 PR 独立串行，运行上限为 3 分钟，不取消在途请求。

本地回归运行 `bun test tools/lock-pr-workflow.test.ts`。它验证跳过、成功、未知写入后的回读与失败传播。首次启用以正常 PR 关闭事件验收，核对准确运行、日志和该 PR 的 `locked=true`。源码合入与本地通过不代表真实事件已经执行。工作流不扫描历史关闭 PR，也不自动解锁重开的 PR。

### 测试与提升

最终测试绑定确定的 `dev` 提交。测试期间冻结新功能合入，只接收修复。修复后更新候选，并补做受影响验证；输入未变的有效结果继续复用。测试环境的实际部署与使用验收另行授权。当前分支配置不代表测试环境已经建立。

每次提升从当次最新 `main` 建立专用临时分支，使用普通 merge 纳入已验收的准确 `dev` 提交。提升 PR 以该临时分支为 head、`main` 为 base；不直接以缺少前次提升合并提交的 `dev` 为 head。绑定已验 `dev` SHA、实际 `main` 基线、提升 head 和 Git tree。提升 head 必须包含当前 `main`，且 tree 必须与已验 `dev` tree 完全相同。除下述[首次历史过渡](#首次历史-ci-过渡)外，出现冲突或 tree 不等时停止，由正常 `dev` 修复流程处理并重新选定、验收候选；不在提升分支补产品改动。

原个人发布准备与准入工具已退役，不作为当前提升入口。正文汇总所含功能 PR、准确候选、测试结果和剩余限制。当前四项 required CI、受影响专用 OCI 和业务验收必须覆盖实际提升组合；AI 审查按[项目例外](../../AGENTS.md#commits-and-review)执行。此前逐片证据不能替代组合后的验收。`main` 再前移时，重新整合最新基线，核对 tree，并补齐当前 CI 与受影响验证；不绕过 strict。提升 PR 只整合已交付的切片，不在其中继续开发独立功能。

提升使用 merge commit，保留各片提交和共同历史，由 `main` 普通保护约束合并方式。保护允许合并不代替准确候选的业务验收与提升授权。提升后继续从 `dev` 开发；下一次从实际 `main` 新建提升分支，以保留前次提升的祖先关系，无需将 `main` 合回 `dev`。确认提升合并后清理该专用分支与工作区，保留已验候选及必要恢复证据。

#### 首次历史 CI 过渡

## 顺序与验收边界

当前方向是内部网站工牌闭环。下表是待选择的实施顺序，不是整批实施授权。先完成简化设计，再按一个可独立验收的结果选片；每片包含必要读取、失败处理与页面，不以只建表或只建框架作为交付。

| 顺序 | 可观察结果               | 验收重点                                                       |
| ---- | ------------------------ | -------------------------------------------------------------- |
| 1    | 正式设计统一到小系统方案 | 目标与当前实现分开；旧强恢复、封印和来源追溯不再约束新增工牌   |
| 2    | 本人提交并查看固定申请   | 固定模板、照片、快照、列表和审计一起交付；同人同类型允许多份   |
| 3    | 有权者审批及处理误申请   | 权限与范围、条件更新、理由、取消、资料差异和审计               |
| 4    | 批准后生成与下载 PDF     | 固定输入、文件完整后保存记录、失败人工重试、越权下载拒绝       |
| 5    | 登记已发放               | ready 才能发放；操作人与时间保存；重复点击不覆盖               |
| 6    | 可从完整备份恢复         | 数据库、文件、配置与密钥实际可用；失败告警；真实数据上线前完成 |

网站已交付注册、退出、本人换号、本人政治面貌、员工服务状态和工号摘要等页面，具体状态以能力台账为准。申请片可用真实后端建立的虚构测试账户验收；面向同事上线前，另选片补齐实际采用且尚缺的准入、工号办理及管理页面。具体页面范围见[页面设计](../client/pages.md)。

已有功能的简化不作为工牌开工的全部前置条件。工牌复用当前有效身份和资格读取，普通新增写入采用简化规则。使用旧读取器不要求新申请加入封印、完成记录或恢复执行器。

首版包含网站管理与发布内容、网站和小程序共用已发布内容展示，按[网站公开内容](#网站公开内容)另选完整切片，工牌优先顺序不变。Schedule 仍暂缓。已有首页、登录及账户入口继续使用。外部旧系统导入不在本轮范围；现有数据的结构转换只随已选简化片安排，不自动授权生产数据迁移。
