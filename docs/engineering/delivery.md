# 业务交付顺序

状态：当前目标交付计划。[架构](../architecture.md)拥有共同机制，各业务专题拥有规则。下表列出业务阶段及依赖；编号不决定迁移编号，也不代表实现已经完成。

## 设计与实施边界

新增能力或调整职责前，先结合现有整体架构设计结构。追踪现有消费者的输入、构造、调用和错误处理，区分当前实现与目标设计。从已确认的业务问题、参与者、用例、事实与不变量出发。明确事实与规则的所有者、模块职责、依赖方向及主要调用流程，再决定表和 API 字段。说明复用哪些已有能力，以及新增边界的依据。

设计同时覆盖成功与失败路径。明确授权、事务和并发边界，以及任务、连接等资源的持有者与生命周期。说明谁处理取消和停止、谁核对未知结果、谁决定重试、谁记录最终失败。按[职责划分](../architecture.md#crate-与模块组织)核对接口与调用方所承担的规则。

设计详略与改动复杂度相称。简单修改可简述，已有有效设计直接复用；只重开缺失或被证据反驳的决定。考虑已确认的后续能力如何接入，具体设施仍随实际消费者实现。设计说明不要求固定模板或状态文件，也不新增审批环节；现有操作授权要求仍然适用。

已确认的业务事实保持权威，直到用户明确更改。区分已确认事实、观察、推断、提议和待定问题。旧确认标签或审查状态不能使已被替代的架构重新生效。

### 实施切片

整体梳理覆盖受影响的架构、调用链及消费者。分析范围不受当前切片的目录限制。只读分析或设计确认本身不授权实施，实施范围以用户明确选定的结果为准。

- 可整体设计完整架构，默认只实施当前明确选定的小切片。用户明确授权多项整理时，可逐项准备、实施和验证，仍按独立结果分别交付。交付阶段是业务里程碑，不是单个 PR 的实施范围。认可 S1 或架构，不授权一次交付整个 C1→R1 服务。
- 编码前明确本片唯一的可观察结果、必要改动、验收方式和排除的后续工作。多个结果可独立验收且尚未明确选定时，先推荐第一片供用户选择。已有明确选择和业务确认时直接复用。
- “开始”“继续”承接当前提出且范围明确的工作，不自动扩展到剩余路线图。范围不清时先澄清，再编码。片内必要的准备、实现、测试和缺陷修复自主完成。只为缺失的业务决定或范围变化询问用户，不反复确认普通可逆技术选择。
- 按业务行为和责任拆分，不按文件、目录、crate、行数或提交数判断范围。每片必须可单独审查与验收，不得逐片写完后合成一个大 PR。
- 每片使用独立工作分支，一个分支对应一个面向 `main` 的 PR。同片的审查修复继续留在原分支；交付后不复用该分支承接下一片。开始下一片时核对最新 `origin/main` 并创建新分支，保留其他分支、worktree 与未提交工作。分支工作不替代提交、推送、开 PR 或合并所需的授权。
- 设施、设置、数据库结构和供应商接入随首个真实消费者交付。只实现该消费者当前所需部分，不预建通用执行框架、完整基础设施或后续能力。
- 每片必须完整、可运行、可验证，包含所需数据库保护、失败处理、恢复、测试和文档。一个结果所需的改动可以跨技术层。不得省略这些责任，也不得拆开必须共同提交的事实来缩小表面范围。
- 发现独立主题或新能力时，先核对是否超出授权或扩大验收。超出范围的内容列为后续建议，继续完成当前片。当前结果确实需要扩围时，先说明新增责任与原因，取得用户确认后再实施。等待期间继续不受影响的已授权工作。
- 完成当前片及已授权审查修复后，报告交付结果、验证证据与限制。下一片已明确授权时按选定范围继续，否则提出建议并等待用户选择。路线图仍有工作不授权自动进入下一片。当前片的缺陷修复仍属当前工作，不受任意迭代轮数限制。

## 顺序与验收边界

| 阶段              | 必须可用的结果                                        | 关键依赖与验收                                                                   |
| ----------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| S1 认证闭环       | C1 发码至 R1 会话或注册凭据，包含原结果查询           | 有界工作、普通池和独立恢复、一次发送、错误计数、保留与清理、HTTP；仅用供应商替身 |
| S2 正式账户       | R2 注册与空库初始管理员建立，真实账户可登录           | Identity 与 Access 共同提交；默认头像发布资源；唯一号码占用                      |
| S3 当前资格与管理 | 当前身份、退出、账户暂停恢复、机构角色和指派          | 当前认证、等级与权限；角色修改与用权交错；会话撤销                               |
| S4 账户办理       | 注销、实名更正、换号、微信身份及小程序手机号认证      | 各用例分别交付；晚到结果拒绝、单次 code 交换、原结果恢复                         |
| S5 档案与参与     | Center 档案；Workforce 直接准入、邀请、暂停恢复与退出 | 完整准入前提、当前角色、唯一未结束授权、邀请累计容量                             |
| S6 编号与目录     | 编号完整生命周期和目录配置                            | 同池竞争、双人恢复、真实科室及全部分类规则                                       |
| S7 文件能力       | 头像、照片、模板和字体                                | 所属 SQL 发布意图、持久发布、删除、签名读取和换钥恢复                            |
| S8 工牌成品       | 固定申请、审批、Render 与 Badge，含增办和换证         | 固定来源、后台发现、原尝试重启、永久保护、取消与晚到接纳                         |
| S9 实际发放       | 制作页面、Delivery、本人和管理历史、完整客户端恢复    | 原 Grant 发放序号、人工确认、提交未知和系统停止                                  |

网站独立构建和托管，逐片消费后端入口，发布边界见[网站交付](../http/site.md)。小程序在网站基础能力之后交付本人服务。工牌流程先由网站完整办理。前端页面范围见[网站与小程序页面](../client/pages.md)，传输和恢复见[客户端协议](../client/protocol.md)。

S1 用隔离场景覆盖现有账户和无账户分流。正式业务账户来源在 S2 交付，测试预置不能代替初始化与注册验收。S2 在空业务库建立系统角色和首个管理员，之后开放注册；初始化不签发在线会话。

每片只引入实际消费者需要的设施和表。后续消费者必须同时接入已交付的暂停、注销、实名更正、编号撤销和历史读取后果。S7 才交付用户文件能力，S2 的默认头像使用部署发布资源。

Schedule、旧系统导入、数据迁移、共存和切换不在计划内。编号业务允许的单项历史补录由[人员编号](../workforce/numbers.md)拥有，不扩展为批量导入旧系统。

## 验收与证据

每片按[验证边界](verification.md#检查范围)选择检查，具体命令与依赖边界由 [Rust 工作区规则](rust.md#workspace-validation)拥有。业务验收通过真实进程和公开协议；数据库使用隔离 PostgreSQL、真实迁移和运行身份，材料全部虚构。

共同故障场景由[架构验收矩阵](../architecture.md#隔离验收)拥有。各片补齐自己的准确输入、预期后果、竞争对象和失败恢复，覆盖原证明、异输入、响应丢失、提交未知、普通重启及技术清理。文件逐同步点注入故障；供应商替身记录实际次数及请求字节。

既有代码和测试材料见[文档导航](../README.md#实际交付状态)。当前没有上述完整业务阶段的运行验收结论。既有测试只覆盖当前代码中的对应能力，不证明目标架构已经实现。

迁移随消费者交付。持久数据库已应用的迁移保持不变，隔离测试不冻结迁移。文档检查只验证格式、结构和引用，不提供业务或运行就绪证明。
