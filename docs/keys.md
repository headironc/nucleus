# 密钥材料

本页的已实现密码与密钥合同继续有效。普通业务事实封印停止扩展并随消费者退出；新工牌不新增文件、Layout 或 Confirmation 密文用途。下面涉及未实施工牌封装的旧目标不再适用，现有敏感字段、短信证明和会话安全仍保留。备份须保留恢复所需旧密钥，见[备份与恢复](operations/backup.md)。

本文规定应用密钥的根材料来源、派生用途、装载规则、指纹编码与信封字节契约。全部应用密钥由一个带版本的根派生：凭据只有一个文件 `keys.json`，数据库只有一张根版本元数据表。当前消费者包括 C1 token 与 Message 验证码证明、手机号与身份证号查找、R1/R2 及管理办理的原输入证明、个人信息与凭据封装、政治面貌与邀请原码封装、状态及事实封印、完成输入和默认头像链接签名。启动核验覆盖当前能力的保留事实；换钥与退役维护尚未实施，目标见[密钥维护](operations/keys.md)。后续能力用途见各能力文档；完整阅读路径见[文档导航](README.md)。

## 1. 材料来源

在线与部署入口各自从服务单元凭据目录读取固定文件 `keys.json`，再调用共用的输入转换和根版本校验。环境键、来源与读取归入口，派生用途及受控构造归消费者。

- 不读 `.env`、不搜索路径、不接受命令行传入。
- 缺失时不生成回退密钥，直接失败。
- 运行期一次装载后固定，更换经受控维护并重启生效。

部署基线为 Ubuntu 26.04。材料经 systemd 的 `LoadCredentialEncrypted` 提供，服务激活时解密到 `CREDENTIALS_DIRECTORY`。TPM 属可选强化，未核实设备具备。机制依据为 [systemd Credentials](https://systemd.io/CREDENTIALS/)，2026-09-11 核对。

供应商与应用秘密走各自的凭据文件。发码使用 `challenge.json` 和 `message.json`，格式见[供应商凭据](platform/credentials.md)；微信应用凭据见[微信身份](identity/wechat.md)。应用密钥只读取 `keys.json`；其他文件不会被读取，也不能补足缺失的根文件。

本地装载校验只证明文件结构。校验不证明主机已正确配置凭据，也不证明材料未泄露。校验同样不证明某份材料对应真实业务用途。

## 2. 根版本与派生用途

文件中的每个条目是一个根版本，`active` 指定唯一的活动根。用途是代码常量，不对应文件或表；每个用途对每个根版本派生一把 32 字节的键：

```text
K(use, id) = HKDF-SHA256(salt = "nucleus/key/v1", ikm = root[id], info = use)
```

HKDF 按 RFC 5869 先提取再扩展，输出长度 32 字节，`use` 是下表名称的 UTF-8 字节。用途名称与盐值是已冻结的字节协议。根材料只在派生期间存在，装载后进程只持有派生键与根指纹。

| use          | 算法            | 范围                                                                                   | 保留版本的运行期用途                                                                          |
| ------------ | --------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `encryption` | AES-256-GCM-SIV | 手机号、实名姓名与身份证号、政治面貌取值、邀请原码、完成输入，以及待注册与原会话 token | 按信封内 key ID 解封原记录                                                                    |
| `lookup`     | HMAC-SHA-256    | 手机号、当前身份证号与邀请码的查找摘要，C1 token 的原结果证明与占用                    | 手机号与身份证号只用活动根；邀请码按记录版本重算并检查全部保留版本；C1 token 检查全部保留版本 |
| `proof`      | HMAC-SHA-256    | 绑定原消息的验证码证明，原请求与注册受理、换号及管理办理的原输入证明                   | 按记录的 key ID 核对原证明                                                                    |
| `seal`       | HMAC-SHA-256    | 状态、永久事实与完成封印，当前范围见[事实封印](architecture.md#事实封印)               | 按记录的 key ID 核验原封印                                                                    |
| `link`       | HMAC-SHA-256    | 头像链接签发与验证                                                                     | 验证保留版本签发且尚未到期的链接                                                              |

同一用途的多个消费者共用一把派生键，隔离由各字段的域、业务身份与字段用途保证：每种 HMAC 输入以所属协议的域字符串开头，每种信封的 AAD 绑定域、业务身份与字段用途。任何字段的域与字段用途一经交付不得改写，也不得与另一字段相同。具体编码见各事实所有者。

手机号和身份证号查找各自计算[确定性摘要](identity/lookup.md)，不保存逐行 key ID。个人信息加密已接入 Challenge、Account、Registration、Attempt、Suspension、Resumption 与 Cancellation 手机号，以及 Revision 姓名与身份证号。每个字段绑定原记录 ID 与字段用途；key ID 随信封保存，不增加重复列。Session 只保存 token 的 SHA-256 摘要；原 token 仅在限期 Handoff 中封装。

根版本按 key ID 一起切换：活动根变化时，所有用途同时改用新根的派生键，旧根的派生键只用于上表的保留用途。只有比较、解密或占用依赖全部结束后才允许退役根版本，规则见[密钥维护](operations/keys.md)。微信身份和工牌扩展用途时，沿用这五个用途或新增一个冻结的用途名称，并同步更新持久引用与启动核验。

## 3. 结构与拒绝规则

文件是 JSON，字段为 `version`、`active`、`keys`。文件不设字节大小上限，条目上限 256。

`active` 直接保存 key ID 整数。`keys` 是条目数组，每个条目为仅含 `id`、`material` 的对象；`material` 为根材料文本。文件和条目都不声明用途。顶层和条目拒绝数组形式、缺失字段、未知字段和重复字段。空的 `keys` 无法满足活动键引用，因此拒绝。

以下每一条都使装载失败，没有任何一条会被改写成默认值：

| 拒绝条件                                           | 说明                                                         |
| -------------------------------------------------- | ------------------------------------------------------------ |
| 超过条目上限                                       | 解析之后判断                                                 |
| `version` 不是 1                                   | 只接受整数 1                                                 |
| key ID 为负数或大于有符号 64 位整数上限            | 凭据文件与数据库都只接受 `0..=i64::MAX`                      |
| 未知字段、重复 JSON 字段                           | 包括条目中的 `purpose` 字段                                  |
| JSON 文档之后存在非空白字节                        | 追加第二份文档不覆盖第一份，整份拒绝；尾随空白与换行仍然接受 |
| 材料不是规范无填充 Base64url，或解码后不是 32 字节 | 带填充、用标准字母表的 `+` `/`、尾位非零都拒绝               |
| 同一 key ID 声明多次                               |                                                              |
| 同一份材料出现在多个 key 下                        | 错误指明这两个 key ID                                        |
| 未声明活动键                                       | 必须提供 `active` 整数                                       |
| 活动键指向未声明的 ID                              |                                                              |

装载错误包含固定文件名 `keys.json`，区分活动键字段 `active` 与条目字段 `keys[index].id`、`keys[index].material`，索引从零开始。材料校验失败同时保留已验证的 key ID，错误来源链保留值类型的校验原因。默认诊断不包含材料、原始输入或文件目录。

## 4. 指纹编码

每个根版本在装载时计算一个 32 字节指纹，把材料绑定到它自己的 ID。用途字段固定为 `root`，不取自文件：

```text
fingerprint = SHA-256(
    E("nucleus/identity/key/v1", i64be(id), "root", material)
)
```

`E` 是 §5.1 的长度前缀串联。同一份材料换一个 ID，指纹就不同；用途字段不是 `root` 的指纹一律不匹配。域 `nucleus/identity/key/v1` 是已冻结的字节协议。

nucleus 与部署入口各自读取固定文件，共用 `domain::keys::input::Input` 解析文件结构。输入类型拥有必填字段、对象限制和版本检查，不读取环境或文件。原始材料文本使用 `Zeroizing<String>` 持有。`TryFrom<Input>` 显式调用 `Id::new` 和 `Material::new`，返回已校验的活动 ID 与条目。目标值类型不实现 `Deserialize`。入口再调用 `domain::keys::Keys::new`，校验根版本集合、计算指纹并派生全部用途，返回各能力不能混用的用途集合与非秘密元数据。转换错误拥有字段、索引与已校验 ID，入口补充固定文件名。装载后集合不可修改，文件缓冲与根材料在释放时清零。装载不连接数据库，不验证持久引用，也不代表应用就绪。

各能力继续拥有字段绑定。Identity 保有 Challenge、Message、请求证明、凭据、查找与头像集合，邀请保有原码与查找集合。Identity 的个人数据、Center 取值及共同完成输入复用 `kernel::keys` 的信封集合实现，`keys::seal` 管理共享封印集合。集合只能由根派生构造；加密集合在内部选择活动键加密，按信封版本取原键解密；查找集合只用活动键；证明与签名集合按记录的 key ID 取原键。初始化、停机指派与系统管理员实名更正向 `domain::startup::Administration` 提供完整根派生集合，复用在线启动核验与应用执行器。四个系统角色、首个 Holder、指派与初始化完成在同一事务封印。

### 持久元数据

根版本元数据只有一张表 `security.keys`，归 `security`。每行以非负数字 `id` 为主键，保存 32 字节 `fingerprint` 和非空布尔值 `active`；部分唯一索引限制至多一个活动版本。全部业务事实的 `key_id` 与 `seal_key_id` 都外键引用这张表，被引用的版本不能删除。表只保存元数据；各业务能力保存自己的事实。部署身份拥有结构，运行身份只读。

`domain::keys::database` 接收调用方事务，以单条查询核对同一快照。初始化与启动核验要求数据库与装载的根版本完全一致：缺版本、额外版本、指纹不符或活动版本不同均失败，不补齐或覆盖；第二个活动版本由唯一索引在写入时拒绝。首次初始化在同一事务中写入全部根版本，事务与原结局核对归[部署工具](engineering/deployment.md#密钥初始化与核验)。当前交付支持新库和可重建的隔离库；部分登记与旧用途指纹均拒绝，不自动升级。

启动扫描所有保留 Authentication、Session、Handoff、Registration、Attempt、Receipt 和 Account 手机号，包括已过期但尚未清理的行。保留证明引用的根版本与信封版本仍须可读。Handoff 合法缺席不免除 Session 本身的来源、时间和摘要结构核验；存在原 token 时另核对摘要配对。所有保留 Revision 另行解密，拒绝非规范历史明文。当前 Account 的身份证号摘要与当前实名版本重新配对，Receipt 使用注册时的首份 Revision。Center 另扫描全部政治面貌取值，包括人员注销后保留的行。启动还解封全部保留邀请原码，按记录的版本重算并核对查找摘要。核验不静默改写数据。元数据完全一致不代表换钥已实现。

所有永久 Suspension 和 Resumption 的原手机号也参加启动解封。两者使用同一 `encryption` 集合，按信封内 key ID 选择材料。它们可共用事实 ID，AAD 字段分别为 `suspension.mobile` 与 `resumption.mobile`，不能互换密文。完整编码归[暂停恢复事实](identity/suspension.md#事实约束与权限)。恢复、再次暂停和认证清理均不结束这些历史引用；完整退役范围见[密钥维护引用](operations/key-scope.md)。

Center、角色与机构 Holder 的状态及永久记录参加启动封印核验。扫描包含删除及注销墓碑。Center、角色、机构指派、初始化和 Workforce 配置完成也参加核验。除配置完成保留 24 小时外，这些完成永久保留。所有仍保留的完成输入都必须能解封，包括已经到期但未清理的配置完成。技术重加密保持规范明文及原绑定，不改变明文封印；重新封印仍须先核验旧封印。完整保留范围见[完成记录](architecture.md#完成记录)与[密钥引用](operations/key-scope.md)。

## 5. 密码原语与信封

通用密码能力拥有算法与信封布局，不认识用途，也不判断哪个字段能用哪把钥匙。用途和钥匙选择归拥有记录的能力。

### 5.1 长度前缀编码

```text
LP(x) = u32be(byte_length(x)) || x
E(x1, x2, ...) = LP(x1) || LP(x2) || ...
```

前缀使字段边界无歧义。两个不同的字段列表不会编码成同一串字节。因此把字节从一个字段挪到下一个字段，摘要一定改变。

编码结果放入可清零缓冲，按精确长度一次分配。字段可能是手机号、身份证号和验证码的明文；缓冲增长会把明文留在已释放的堆上。清零义务在共享入口，不在调用方。调用者传入的值由各自类型完成解析与规范化。本入口不修剪、不转换大小写、不做 Unicode 规范化。

### 5.2 信封

```text
信封 = version:u8(1) | key_id:i64be | nonce:12 | ciphertext | tag:16
AAD  = E(域, version||key_id||nonce, 业务身份, 字段用途)
```

信封头本身进入 AAD，所以版本、key ID 和 nonce 是被认证的，而不只是被携带。域、业务身份和字段用途由拥有记录的能力给出；Identity 使用 `nucleus/identity/envelope/v1`。读取端拒绝负数 key ID 和未知版本，不尝试按其他布局解码。

每次封装取新的随机 nonce。随机源取不到材料时不产出信封，不会复用 nonce。

单 UUID 的业务身份使用其原始 16 字节；多个 UUID 组成的身份按 §5.4 编码。任何已持久化字段的 AAD 字节契约一经交付便不变。

### 5.3 随机源

安全随机材料经共享的随机源入口获取，生产实现使用 `getrandom::fill` 读取操作系统随机源。不提供种子、时间戳或伪随机回退；失败后缓冲内容不保证可用，调用方丢弃。失败是返回值，不是 panic。

### 5.4 封装边界目标设计

保留 §5.1 与 §5.2 的 V1 字节契约，作为应用内部持久值的格式。现行用例由服务自身写入并读取密文，没有跨系统密文互通需求。V1 头部固定，AAD 字段顺序明确。本单元不为这些值引入新的序列化或封装依赖。通用格式仍需项目选择业务身份与字段用途；比较依据见[设计证据](engineering/evidence.md#26-密码封装库与格式)。未来若有新的格式需求，另定义版本及独立向量，保持 V1 的解码含义。

共享设施使用已有 crate 完成整数写入、摘要、HMAC、AEAD、随机获取和敏感缓冲清零。这些通用算法不另行实现。长度前缀、信封头及 AAD 的字段顺序仍由本项目规定。通用序列化格式只有逐字节符合 V1 才能代替编码入口；结构往返成功不足以证明等价。

已交付的 `platform::cryptography` 使用 ring 计算长度前缀 SHA-256、HMAC-SHA-256 和 HKDF-SHA-256。HMAC 核对使用 `ring::hmac::verify`，不使用普通数组相等比较。`hkdf::derive` 接收盐值、32 字节材料与 info，输出放入可清零的 32 字节缓冲。Platform 接口不认识密钥用途；`domain::keys` 固定根指纹、盐值与用途名称，各事实所有者固定证明域和业务绑定。编码拒绝超过 u32 的字段长度，检查总长度并按精确容量构造可清零缓冲。

`platform::cryptography::envelope` 使用 `aes-gcm-siv` 0.12.1，启用 `aes` 和 `zeroize`，关闭默认特性。`Key::new` 同时绑定受控 key ID 与材料，之后不可修改。`seal` 只接收实现 `envelope::Input` 的业务输入，不再单独接收 key ID。`open` 拒绝信封 key ID 与本键不符，再验证 AAD 与标签。

`Binding::domain()` 提供域，`identity()` 提供业务身份，`field()` 提供字段用途。Platform 固定执行 `E(域, 信封头, 业务身份, 字段用途)`，业务方不能遗漏头部或改变四字段顺序。输入同时持有明文与绑定，算法读取时才取得字节视图。nonce 由内部类型通过 `getrandom::fill` 生成，每次取得新的 12 字节，失败直接返回。

`Envelope::new` 只检查结构，成功后保留原始字节与已校验头部，不反复解析 key ID。结构失败返回 `ParseError`；版本选取、算法、随机与编码失败保留为运行错误。封装按最终长度一次分配，在可清零缓冲内原地加密，成功后才移交密文字节。解密缓冲在成功或失败后的释放时清零。该实现不提供通用密钥仓库，也不引入 `aws-lc-rs`。

`Encoded::new` 只接收实现 `cryptography::Input<N>` 的协议输入类型，不接受裸字节列表。trait 返回固定数量的字段引用，字段含义和排列顺序由协议所有者实现。Platform 拥有字段长度、总长度和分配检查，私有持有可清零的编码缓冲。SHA-256 与 HMAC-SHA-256 的消息输入都只接收 `&Encoded`，不自行重新编码。`sha256::Digest::new` 返回私有持有 32 字节的 `Digest`，通过 `AsRef<[u8; 32]>` 提供字节视图；根指纹保留该类型。

`hmac::Key::sign` 返回私有持有 32 字节的专用 `Tag`，通过 `AsRef<[u8; 32]>` 提供字节视图。Tag 只由签名计算产生，不表示认证通过。`verify` 接收待核对的 `&[u8; 32]`，交给 ring 验证它与本键、本次编码输入是否匹配。Challenge 和 Message 的 `Proof` 已通过 SQL 解码恢复持久证明字节；解码只检查存储表示，所属用例仍须验证原输入。持久证明不重建为 Tag，领域所有者继续拥有证明域和消息输入含义。

事实所有者固定每种字段的域、业务身份、字段用途和许可的密钥用途。所有者提供受控的绑定构造，所属用途的密钥集合完成版本选择。业务封装入口只接受所属绑定与对应密钥集合，不接受任意材料与域字符串。共享设施仍不认识各能力的用途全集。

新字段需要绑定多个 UUID 时，所属能力定义一种具名业务身份和固定字段顺序。每个 UUID 取其规范文本去掉连字符后所表示的 16 个字节，按字段顺序直接连接；连接结果整体作为 §5.2 中的一个业务身份传给 `E`，只写一次 u32 大端长度前缀。内部 UUID 不另加前缀、分隔符或文本编码。域与字段用途固定该业务身份的种类和 UUID 数量；调用方不能传任意字节或可变长 ID 列表。加密、读取和技术重加密均从同一业务事实重建绑定，不从密文推断身份。

[Center 取值](center/affiliation.md#存储密码与维护)保留已实现的多字段绑定及 V1 信封合同。新工牌不保存 Layout 密文或审批 Confirmation，不为它们定义派生用途、AAD 或重封装流程。

完成输入采用[完成记录](architecture.md#完成记录)定义的混合身份，按 §5.1 逐字段编码家族、原操作 ID、主体标签和主体字段。固定编码与独立向量由 `kernel::completion` 维护。

在线机构角色与 Workforce 角色分别使用 `institution_role` 与 `workforce_role` 家族，独立绑定 Operation-Id。两者永久保留封装的规范输入和会话主体，完成封印覆盖规范明文而非密文。同一办理人员的重放核验完成完整性和规范输入，其他人员的请求拒绝。原结果读取单条已封印原变更，核对字段一致性，并结算对应的待定锚定；历史页另核验完整前驱序列。

打开密文时，先校验最短长度、版本和非负 key ID。所有者按记录用途取得该版本的材料，再以受控绑定进行 AEAD 验证。头部继续参与 AAD。未知版本、缺失密钥、用途不符和认证失败各有技术错误，不尝试其他版本或用途。成功解密后，所有者再校验明文的领域值；失败不得解释为凭据不匹配或记录缺席。

SHA 与 HMAC 接口可按 §5.1 的顺序增量写入长度和字段字节，避免复制敏感明文。AEAD 接口需要连续 AAD 字节时，仍按精确长度构造可清零缓冲。增量输入与缓冲输入必须得到相同的固定向量结果。减少分配不得改变前缀宽度、字段顺序或密钥指纹。密文缓冲的归属与失败清理须在实现时核对。

### 5.5 角色状态与变更封印

角色使用[共同事实封印](architecture.md#事实封印)格式 `E("nucleus/seal/v1", 种类名, 编码版本, 字段……)`，当前种类为 `access.role` 与 `access.change`，编码版本均为十进制文本 `1`。UUID 取原始 16 字节，文本取 UTF-8；等级、序号、版本和权限数量取十进制文本，时间取 Unix 微秒数的十进制文本。权限按代码严格递增排序，每个代码单独占一个长度前缀字段。

`access.role` 依次绑定角色 ID、范围、名称、等级、状态文本 `active` 或 `deleted`、最新变更 ID、变更时间、对象内序号、状态版本和权限数量，再追加权限代码。角色 State 永久保留；删除终态的当前权限为空集合，封印仍覆盖终态及全部计数。

`access.change` 依次绑定变更 ID、角色 ID、前驱变更 ID、对象内序号、范围、来源 `entry`、动作、名称、等级、办理人实名版本 ID、变更时间和 Operation-Id，再绑定权限集合。缺席的前驱或来源编码为空字段；创建和修改先写权限数量，再追加各代码。删除的权限集合缺席，编码为单个空字段，与空集合的数量文本 `0` 不同。字段排列由 `role/state.rs` 与 `role/change.rs` 的 `fields` 实现固定。

## 6. 失败分档

三档不允许互相冒充：

| 档                 | 例子                                                | 处置                                                   |
| ------------------ | --------------------------------------------------- | ------------------------------------------------------ |
| 装载与结构         | §3 的全部拒绝条件                                   | 启动失败，非零退出                                     |
| 运行期密码技术错误 | 未知信封版本、非法封装、认证标签失败、缺对应 key ID | 技术错误，不报成凭据不匹配、记录不存在或客户端输入错误 |
| 业务证明失败       | 可信摘要比较不符、规范值不符                        | 相应的证明或输入错误                                   |

**诊断脱敏。** 材料类型不派生 `Debug`、`Display`、`Serialize` 或 `Clone`。文件读取、解析失败标识固定文件名，不展示底层解析错误。Serde 报告类型不符时可能引用读到的材料。原因仍留在来源链上供核对。

根文件装载器沿用供应商凭据的读取错误边界。集合校验失败保留具体错误变体及相关数字 key ID。原始 JSON 错误只保留在来源链，不直接记录。缺原版本密钥与编码失败属于技术错误；用正确版本计算后不匹配才是业务证明失败。

## 7. 验证与限制

当前内联测试覆盖 HKDF 派生、根指纹、固定编码、C1/R1/R2 证明和头像签名向量，活动与保留根版本核对、严格字段、重复 ID 与材料、条目上限、材料规范编码和安全诊断。期望值由 Python 的整数大端编码、`struct`、`hashlib`、`hmac` 与 `AESGCMSIV` 独立计算：派生键、根指纹以及经根派生的手机号与身份证号查找、事实封印、信封和 C1 token 证明直接从根材料计算；各字段所有者的证明与信封向量以固定的用途键计算，测试夹具根派生出的原输入证明另以 Python HKDF 重新计算。nucleus 与部署子进程测试使用临时目录与虚构材料，验证固定文件 `keys.json`、导出的目录变量和含大量空白的合法文件；环境中的材料值、`.env` 及旧的按用途文件都不构成备用来源。数据库元数据的初始化、权限和只读核验已有[隔离部署测试](engineering/deployment.md#验证边界)；部署与启动均验证旧用途指纹、缺版本、额外版本与活动版本不同被拒绝且原登记不被修复，第二个活动版本由数据库拒绝。C1/R1/R2 已验证原证明、凭据交接及保留事实的启动扫描，证据见[短信认证](identity/authentication.md)和[正式注册](identity/registration.md#清理与验收)。真实部署与换钥事务仍未验收。

交付时验证：

- 长度前缀编码、SHA-256、HMAC-SHA-256、HKDF-SHA-256、信封的固定向量。期望值全部由本代码之外计算。SHA-256 用公开发布值，其余用 Python 的 `hmac` 与 `AESGCMSIV`。
- 字段边界不可挪动。信封换域、换记录、换字段用途、换密钥都打不开。截断、改版本位、改 key ID、改 nonce、改密文各自归到正确的技术错误。key ID 的 0 与 `i64::MAX` 可用；负数和未知版本被拒绝。
- 随机源失败时不产出信封；连续封装的 nonce 不重复。
- §3 的每一条拒绝条件；指纹与派生的独立向量，同一材料换 ID 后指纹改变，活动根切换后全部用途随之切换。
- 诊断不含材料，文件解析失败标识固定文件名，集合校验失败保留具体错误类型。

以独立 V1 向量比较两条编码路径、信封和指纹。多 ID 用例须检查完整 AAD 字节、ID 顺序、跨任一身份替换及原单 UUID 向量不变。验证跨字段、跨记录与跨用途替换均被拒绝，并检查最终依赖特性与目标 CPU。

明确不证明的：

- `aes-gcm-siv` 维护者声明该 crate 未经安全审计；依赖组件受过审不等于它或本项目受过审。
- 常数时间性质有处理器与编译配置条件，目标 CPU 与最终编译配置仍必须进入安全审查。
- 内存清理撤不回已复制到日志、崩溃转储或交换区的秘密；`Zeroizing` 不是全进程保密证明。本文覆盖的是本项目自己持有的副本。`aes-gcm-siv` 0.12.1 有可选 `zeroize` 特性；源码显示该特性清零派生过程的临时缓冲，密钥扩展后的轮密钥是否随 Drop 清零未经核实。JSON 解析器在读出材料字符串前的内部缓冲同样不在控制范围内。
- 当前根材料、派生键、HMAC 原材料与项目编码缓冲在释放时清零；ring 内部的 HKDF 伪随机键与 HMAC 派生状态没有本项目可依赖的释放清零保证。
- 本地校验不证明 systemd 凭据已配置、材料属于真实业务用途，或供应商凭据有效。

密钥维护与退役流程见[密钥维护](operations/keys.md)；具体字段的封装、摘要和原结果恢复由各事实所有者交付。
