# 密钥材料

本文规定应用密钥材料的来源、封闭用途、装载规则、指纹编码与信封字节契约。已交付 C1 token 证明、手机号查找摘要与 Challenge 手机号密文。Message 验证码证明及四份用途密钥装载也已交付。Platform 已交付长度前缀 SHA-256、HMAC-SHA-256 和 V1 AEAD 信封。四个用途的持久元数据、首次初始化和只读核验已交付。C1 持久接纳的启动核验已检查原键、密文和摘要；换钥维护尚未实施。后续能力用途见各能力文档；完整阅读路径见[文档导航](README.md)。

## 1. 材料来源

在线与部署入口各自从服务单元凭据目录读取固定文件，再调用所属用途的输入转换和集合校验。环境键、来源与读取归入口，密钥用途及受控构造归消费者。现有装载接口与目标入口位置按[实际交付状态](README.md#实际交付状态)区分。

- 不读 `.env`、不搜索路径、不接受命令行传入。
- 缺失时不生成回退密钥，直接失败。
- 运行期一次装载后固定，更换经受控维护并重启生效。

部署基线为 Ubuntu 26.04。材料经 systemd 的 `LoadCredentialEncrypted` 提供，服务激活时解密到 `CREDENTIALS_DIRECTORY`。TPM 属可选强化，未核实设备具备。机制依据为 [systemd Credentials](https://systemd.io/CREDENTIALS/)，2026-09-11 核对。

供应商与应用秘密走各自的凭据文件。发码使用 `challenge.json` 和 `message.json`，格式见[供应商凭据](platform/credentials.md)；微信应用凭据见[微信身份](identity/wechat.md)。应用密钥按用途拆分文件，各用途独立装载和轮换。

本地装载校验只证明文件结构。校验不证明主机已正确配置凭据，也不证明材料未泄露。校验同样不证明某份材料对应真实业务用途。

## 2. 封闭用途

每份文件只保存一个用途的活动版本和保留版本。用途由装载入口固定，文件不声明 `purpose`。`active` 指定唯一的活动 key ID。必需文件缺失时装载失败，不回退到其他用途文件。

| 已交付文件             | 用途         | 应用装载入口                      | 保留版本的运行期用途             |
| ---------------------- | ------------ | --------------------------------- | -------------------------------- |
| `challenge-keys.json`  | `challenge`  | `nucleus::keys::challenge::load`  | 原 token 核对及新 token 占用查找 |
| `mobile-keys.json`     | `mobile`     | `nucleus::keys::mobile::load`     | 不参与请求查找；统一使用活动键   |
| `encryption-keys.json` | `encryption` | `nucleus::keys::encryption::load` | 按信封内 key ID 解密旧记录       |
| `message-keys.json`    | `message`    | `nucleus::keys::message::load`    | 按 Check 的 key ID 核对原码证明  |

手机号查找只计算[确定性摘要](identity/lookup.md)，不保存逐行 key ID。个人信息加密当前只接入 [Challenge 手机号](identity/authentication.md#challenge-手机号保护)，key ID 随密文信封保存，不增加重复列。

各用途的算法与范围如下。尚未交付的用途随消费者接入，不预建文件或装载器：

| 用途               | 算法与范围                                                |
| ------------------ | --------------------------------------------------------- |
| `encryption`       | AES-256-GCM-SIV；手机号密文，以及实名版本的姓名与身份证号 |
| `credential_seal`  | AES-256-GCM-SIV；待注册 token、有限恢复期内的原会话 token |
| `mobile`           | HMAC-SHA-256；手机号查找                                  |
| `id_number_lookup` | HMAC-SHA-256；当前身份证号占用                            |
| `message`          | HMAC-SHA-256；绑定原消息的验证码                          |
| `wechat_proof`     | HMAC-SHA-256；微信一次性 code 占用                        |
| `input_proof`      | HMAC-SHA-256；原请求与注册受理的输入摘要                  |
| `avatar_signature` | HMAC-SHA-256；头像链接签发与验证                          |

微信身份、邀请码、工牌和人员档案扩展用途时，同步更新装载器、持久引用与启动核验。每个已交付用途恰好一个活动键；停止生成新值的旧键仍可保留。只有比较、解密或占用依赖结束后才允许退役材料。

## 3. 结构与拒绝规则

文件是 JSON，字段为 `version`、`active`、`keys`。文件不设字节大小上限，条目上限 256。

`active` 直接保存 key ID 整数。`keys` 是条目数组，每个条目为仅含 `id`、`material` 的对象；`material` 为材料文本。顶层和条目拒绝数组形式、缺失字段、未知字段和重复字段。空的 `keys` 无法满足活动键引用，因此拒绝。

以下每一条都使装载失败，没有任何一条会被改写成默认值：

| 拒绝条件                                           | 说明                                                         |
| -------------------------------------------------- | ------------------------------------------------------------ |
| 超过条目上限                                       | 解析之后判断                                                 |
| `version` 不是 1                                   | 只接受整数 1                                                 |
| key ID 为负数或大于有符号 64 位整数上限            | 凭据文件与数据库都只接受 `0..=i64::MAX`                      |
| 未知字段、重复 JSON 字段                           | 包括条目中的 `purpose` 字段                                  |
| JSON 文档之后存在非空白字节                        | 追加第二份文档不覆盖第一份，整份拒绝；尾随空白与换行仍然接受 |
| 材料不是规范无填充 Base64url，或解码后不是 32 字节 | 带填充、用标准字母表的 `+` `/`、尾位非零都拒绝               |
| 同一 key ID 声明多次                               |                                                              |
| 同一份材料出现在多个 key 下                        | 错误指明这两个 key ID                                        |
| 未声明活动键                                       | 必须提供 `active` 整数                                       |
| 活动键指向未声明的 ID                              |                                                              |

同一文件内的不同 key ID 不能共用一份材料，装载器会拒绝重复材料。不同用途必须使用独立材料；当前各装载入口分别校验自己的文件，不宣称核验了跨文件材料重复。

根装载错误包含固定文件名，区分活动键字段 `active` 与条目字段 `keys[index].id`、`keys[index].material`，索引从零开始。材料校验失败同时保留已验证的 key ID，错误来源链保留值类型的校验原因。默认诊断不包含材料、原始输入或文件目录。

## 4. 指纹编码

每个条目在装载时计算一个 32 字节指纹，把材料绑定到它自己的 ID 和用途。Challenge 的用途标识固定为 `challenge`，不取自文件：

```text
fingerprint = SHA-256(
    E("nucleus/identity/key/v1", i64be(id), purpose, material)
)
```

`E` 是 §5.1 的长度前缀串联，`purpose` 是 §2 表中的名称字符串。同一份材料换一个 ID 或换一个用途，指纹就不同。

数据库侧保存同一指纹，由停机部署步骤写入，见[数据库](database.md)。启动时须比对材料、活动状态与持久引用。

nucleus 与部署入口各自读取固定文件，共用 `domain::identity::keys::input::Input` 解析文件结构。输入类型拥有必填字段、对象限制和版本检查，不读取环境或文件。原始材料文本使用 `Zeroizing<String>` 持有。`TryFrom<Input>` 显式调用 `Id::new` 和 `Material::new`，返回已校验的活动 ID 与条目。目标值类型不实现 `Deserialize`。各入口再调用用途的 `Keys::new`，校验集合并生成指纹，返回不能混用的密钥集合。转换错误拥有字段、索引与已校验 ID，入口补充固定文件名。装载后集合不可修改，文件缓冲在释放时清零。装载不连接数据库，不验证持久引用，也不代表应用就绪。

`domain::identity::keys::challenge::Keys` 提供活动键、指定版本和全部版本，供原 token 证明使用。`domain::identity::keys::mobile::Keys` 只用活动键计算手机号摘要。`domain::identity::keys::encryption::Keys` 在内部选择活动键加密，按信封版本取原键解密。后两者提供活动 key ID 和各版本指纹，供元数据核验使用。加密集合的单键类型、材料字段和查找方法均为私有；记录所有者只调用集合的受控操作。

`domain::identity::keys::message::Keys` 用活动键计算原码证明，按 Check 的 key ID 核对保留证明。证明绑定 Message UUID 和八位原码，编码由[短信认证](identity/authentication.md#消息与校验事实)拥有。原码只在原发送工作中短暂保留。

### 持久元数据

密钥元数据按用途分表，归 `security`。当前四个用途分别使用 `security.challenges`、`security.mobiles`、`security.encryptions` 和 `security.messages`。它们只保存密钥元数据；`identity.challenges` 保存 C1 接纳事实。用途、字段编码和退役引用归实际消费能力。

每张表以非负数字 `id` 为主键，保存 32 字节 `fingerprint` 和非空布尔值 `active`。各表的部分唯一索引限制至多一个活动键。初始化与启动核验要求每个用途恰好一个活动键，并与装载集合完全一致。Challenge 的 `key_id` 直接外键引用 `security.challenges.id`；Check 的 `key_id` 引用 `security.messages.id`。其他用途的同号版本不能满足引用。部署身份拥有结构，运行身份只读。

`domain::identity::keys::metadata::Metadata::new` 从四个受控集合构造清单。`domain::identity::keys::database` 接收调用方事务，以单条查询核对四表的同一快照。缺用途、部分初始化、缺版本、额外版本或活动键不一致均失败，不补齐或覆盖。首次初始化在同一事务中写入四个用途，事务与原结局核对归[部署工具](engineering/deployment.md#密钥初始化与核验)。

其他用途及退役引用随消费者交付。当前四个集合的完全比较不代表全能力引用核验。拆表不改变材料文件、指纹编码或信封字节契约。

## 5. 密码原语与信封

通用密码能力拥有算法与信封布局，不认识用途，也不判断哪个字段能用哪把钥匙。用途和钥匙选择归拥有记录的能力。

### 5.1 长度前缀编码

```text
LP(x) = u32be(byte_length(x)) || x
E(x1, x2, ...) = LP(x1) || LP(x2) || ...
```

前缀使字段边界无歧义。两个不同的字段列表不会编码成同一串字节。因此把字节从一个字段挪到下一个字段，摘要一定改变。

编码结果放入可清零缓冲，按精确长度一次分配。字段可能是手机号、身份证号和验证码的明文；缓冲增长会把明文留在已释放的堆上。清零义务在共享入口，不在调用方。调用者传入的值由各自类型完成解析与规范化。本入口不修剪、不转换大小写、不做 Unicode 规范化。

### 5.2 信封

```text
信封 = version:u8(1) | key_id:i64be | nonce:12 | ciphertext | tag:16
AAD  = E(域, version||key_id||nonce, 业务身份, 字段用途)
```

信封头本身进入 AAD，所以版本、key ID 和 nonce 是被认证的，而不只是被携带。域、业务身份和字段用途由拥有记录的能力给出；Identity 使用 `nucleus/identity/envelope/v1`。读取端拒绝负数 key ID 和未知版本，不尝试按其他布局解码。

每次封装取新的随机 nonce。随机源取不到材料时不产出信封，不会复用 nonce。

单 UUID 的业务身份使用其原始 16 字节；多个 UUID 组成的身份按 §5.4 编码。任何已持久化字段的 AAD 字节契约一经交付便不变。

### 5.3 随机源

安全随机材料经共享的随机源入口获取，生产实现使用 `getrandom::fill` 读取操作系统随机源。不提供种子、时间戳或伪随机回退；失败后缓冲内容不保证可用，调用方丢弃。失败是返回值，不是 panic。

### 5.4 封装边界目标设计

保留 §5.1 与 §5.2 的 V1 字节契约，作为应用内部持久值的格式。现行用例由服务自身写入并读取密文，没有跨系统密文互通需求。V1 头部固定，AAD 字段顺序明确。本单元不为这些值引入新的序列化或封装依赖。通用格式仍需项目选择业务身份与字段用途；比较依据见[设计证据](engineering/evidence.md#26-密码封装库与格式)。未来若有新的格式需求，另定义版本及独立向量，保持 V1 的解码含义。

共享设施使用已有 crate 完成整数写入、摘要、HMAC、AEAD、随机获取和敏感缓冲清零。这些通用算法不另行实现。长度前缀、信封头及 AAD 的字段顺序仍由本项目规定。通用序列化格式只有逐字节符合 V1 才能代替编码入口；结构往返成功不足以证明等价。

已交付的 `platform::cryptography` 使用 ring 计算长度前缀 SHA-256 和 HMAC-SHA-256。HMAC 核对使用 `ring::hmac::verify`，不使用普通数组相等比较。Platform 接口不认识密钥用途；Identity 固定指纹、证明域和业务绑定。编码拒绝超过 u32 的字段长度，检查总长度并按精确容量构造可清零缓冲。

`platform::cryptography::envelope` 使用 `aes-gcm-siv` 0.12.1，启用 `aes` 和 `zeroize`，关闭默认特性。`Key::new` 同时绑定受控 key ID 与材料，之后不可修改。`seal` 只接收实现 `envelope::Input` 的业务输入，不再单独接收 key ID。`open` 拒绝信封 key ID 与本键不符，再验证 AAD 与标签。

`Binding::domain()` 提供域，`identity()` 提供业务身份，`field()` 提供字段用途。Platform 固定执行 `E(域, 信封头, 业务身份, 字段用途)`，业务方不能遗漏头部或改变四字段顺序。输入同时持有明文与绑定，算法读取时才取得字节视图。nonce 由内部类型通过 `getrandom::fill` 生成，每次取得新的 12 字节，失败直接返回。

`Envelope::new` 只检查结构，成功后保留原始字节与已校验头部，不反复解析 key ID。结构失败返回 `ParseError`；版本选取、算法、随机与编码失败保留为运行错误。封装按最终长度一次分配，在可清零缓冲内原地加密，成功后才移交密文字节。解密缓冲在成功或失败后的释放时清零。该实现不提供通用密钥仓库，也不引入 `aws-lc-rs`。

`Encoded::new` 只接收实现 `cryptography::Input<N>` 的协议输入类型，不接受裸字节列表。trait 返回固定数量的字段引用，字段含义和排列顺序由协议所有者实现。Platform 拥有字段长度、总长度和分配检查，私有持有可清零的编码缓冲。SHA-256 与 HMAC-SHA-256 的消息输入都只接收 `&Encoded`，不自行重新编码。`sha256::Digest::new` 返回私有持有 32 字节的 `Digest`，通过 `AsRef<[u8; 32]>` 提供字节视图；Challenge 的指纹字段及访问接口保留该类型。

`hmac::Key::sign` 返回私有持有 32 字节的专用 `Tag`，通过 `AsRef<[u8; 32]>` 提供字节视图。Tag 只由签名计算产生，不表示认证通过。`verify` 接收待核对的 `&[u8; 32]`，交给 ring 验证它与本键、本次编码输入是否匹配。Challenge 和 Message 的 `Proof` 已通过 SQL 解码恢复持久证明字节；解码只检查存储表示，所属用例仍须验证原输入。持久证明不重建为 Tag，领域所有者继续拥有证明域和消息输入含义。

事实所有者固定每种字段的域、业务身份、字段用途和许可的密钥用途。所有者提供受控的绑定构造，所属用途的密钥集合完成版本选择。业务封装入口只接受所属绑定与对应密钥集合，不接受任意材料与域字符串。共享设施仍不认识各能力的用途全集。

新字段需要绑定多个 UUID 时，所属能力定义一种具名业务身份和固定字段顺序。每个 UUID 取其规范文本去掉连字符后所表示的 16 个字节，按字段顺序直接连接；连接结果整体作为 §5.2 中的一个业务身份传给 `E`，只写一次 u32 大端长度前缀。内部 UUID 不另加前缀、分隔符或文本编码。域与字段用途固定该业务身份的种类和 UUID 数量；调用方不能传任意字节或可变长 ID 列表。加密、读取和技术重加密均从同一业务事实重建绑定，不从密文推断身份。

[Center 取值](center/affiliation.md#存储密码与维护)与 [Workforce Layout](workforce/media.md#文字排版) 各自规定域、字段用途和 ID 顺序。采用上述编码时沿用 V1 信封及四字段 AAD 结构。某个字段一旦交付，其域、用途、ID 数量或顺序不得在 V1 下改写；需要修改时须定义新版本和旧值的明确读取规则。

打开密文时，先校验最短长度、版本和非负 key ID。所有者按记录用途取得该版本的材料，再以受控绑定进行 AEAD 验证。头部继续参与 AAD。未知版本、缺失密钥、用途不符和认证失败各有技术错误，不尝试其他版本或用途。成功解密后，所有者再校验明文的领域值；失败不得解释为凭据不匹配或记录缺席。

SHA 与 HMAC 接口可按 §5.1 的顺序增量写入长度和字段字节，避免复制敏感明文。AEAD 接口需要连续 AAD 字节时，仍按精确长度构造可清零缓冲。增量输入与缓冲输入必须得到相同的固定向量结果。减少分配不得改变前缀宽度、字段顺序或密钥指纹。密文缓冲的归属与失败清理须在实现时核对。

## 6. 失败分档

三档不允许互相冒充：

| 档                 | 例子                                                | 处置                                                   |
| ------------------ | --------------------------------------------------- | ------------------------------------------------------ |
| 装载与结构         | §3 的全部拒绝条件                                   | 启动失败，非零退出                                     |
| 运行期密码技术错误 | 未知信封版本、非法封装、认证标签失败、缺对应 key ID | 技术错误，不报成凭据不匹配、记录不存在或客户端输入错误 |
| 业务证明失败       | 可信摘要比较不符、规范值不符                        | 相应的证明或输入错误                                   |

**诊断脱敏。** 材料类型不派生 `Debug`、`Display`、`Serialize` 或 `Clone`。文件读取、解析失败标识固定文件名，不展示底层解析错误。Serde 报告类型不符时可能引用读到的材料。原因仍留在来源链上供核对。

已交付装载器沿用 Challenge、Message 的凭据读取错误边界。集合校验失败保留具体错误变体及相关数字 key ID。原始 JSON 错误只保留在来源链，不直接记录。缺原版本密钥与编码失败属于技术错误；用正确版本计算后不匹配才是业务证明失败。

## 7. 验证与限制

当前内联测试覆盖固定编码、指纹和 C1 证明向量，活动与保留版本核对、严格字段、重复 ID 与材料、条目上限、材料规范编码和安全诊断。nucleus 子进程测试使用临时目录与虚构材料，验证固定文件、导出的目录变量和含大量空白的合法文件；环境中的材料值及 `.env` 不构成备用来源。期望值由 Python 的 `struct`、`hashlib` 与 `hmac` 独立计算。数据库元数据的初始化、权限和只读核验已有[隔离部署测试](engineering/deployment.md#验证边界)。C1 接纳库已验证 token 持久占用及启动时的原密钥核对，证据见[首次接纳边界](identity/authentication.md#首次接纳边界)。完整应用启动与换钥事务仍未实现或验收。

交付时验证：

- 长度前缀编码、SHA-256、HMAC-SHA-256、信封的固定向量。期望值全部由本代码之外计算。SHA-256 用公开发布值，其余用 Python 的 `hmac` 与 `AESGCMSIV`。
- 字段边界不可挪动。信封换域、换记录、换字段用途、换密钥都打不开。截断、改版本位、改 key ID、改 nonce、改密文各自归到正确的技术错误。key ID 的 0 与 `i64::MAX` 可用；负数和未知版本被拒绝。
- 随机源失败时不产出信封；连续封装的 nonce 不重复。
- §3 的每一条拒绝条件；指纹的独立向量，以及同一材料换 ID 后指纹改变。
- 诊断不含材料，文件解析失败标识固定文件名，集合校验失败保留具体错误类型。

以独立 V1 向量比较两条编码路径、信封和指纹。多 ID 用例须检查完整 AAD 字节、ID 顺序、跨任一身份替换及原单 UUID 向量不变。验证跨字段、跨记录与跨用途替换均被拒绝，并检查最终依赖特性与目标 CPU。

明确不证明的：

- `aes-gcm-siv` 维护者声明该 crate 未经安全审计；依赖组件受过审不等于它或本项目受过审。
- 常数时间性质有处理器与编译配置条件，目标 CPU 与最终编译配置仍必须进入安全审查。
- 内存清理撤不回已复制到日志、崩溃转储或交换区的秘密；`Zeroizing` 不是全进程保密证明。本文覆盖的是本项目自己持有的副本。`aes-gcm-siv` 0.12.1 有可选 `zeroize` 特性；源码显示该特性清零派生过程的临时缓冲，密钥扩展后的轮密钥是否随 Drop 清零未经核实。JSON 解析器在读出材料字符串前的内部缓冲同样不在控制范围内。
- 当前 HMAC 原材料与项目编码缓冲在释放时清零；ring 内部派生状态没有本项目可依赖的释放清零保证。
- 本地校验不证明 systemd 凭据已配置、材料属于真实业务用途，或供应商凭据有效。

密钥维护与退役流程见[密钥维护](operations/keys.md)；具体字段的封装、摘要和原结果恢复由各事实所有者交付。
