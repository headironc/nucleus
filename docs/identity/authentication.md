# 短信认证与原结果交接

状态：C1 接纳、人机校验、短信发送与原结果恢复已交付库接口及 `POST /codes`。C1 到期清理已接入，原操作仅在记录保留期内防重。R1 尚未交付。本文拥有认证专属事实、时间、额度、供应商阶段及原结果。共同执行与提交恢复由[架构](../architecture.md#原操作与恢复)拥有。

## 首次接纳边界

C1 接收已验证 Operation-Id、Mobile、Token 和可信 IP，用途固定为 authentication。IPv4-mapped IPv6 转为 IPv4。Challenge 保存原 token HMAC、受保护手机号、首次来源、固定验证身份、calls=1 和 10 秒截止。calls 只表示机会占用，不证明已外呼。

记录的用途字段采用 `domain::identity::challenge::Purpose` 枚举。`FromSql` 与 `ToSql` 编解码持久用途值，未知值在解码时拒绝。持久用途与供应商 action 的对应关系见 [Turnstile 用途表](../platform/turnstile.md#入口与上下文)。

保存 Challenge 不表示通过校验或获得发送许可。后续阶段分别保存通过结论、发送许可与发送占用；各阶段的继续条件见[目标事务契约](#c1-与-r1-的目标事务契约)。

库级应用入口为 `nucleus::process::Application::start`。调用方提供连接、四个用途的密钥集合、容量、发送限额和停止预算。另需提供本机运行锁与已构造的人机校验、短信客户端。生产入口固定锁路径，并先检查旧应用进程退出边界，具体装配见 [HTTP 入口](../http/api.md#已交付入口)。`domain::identity::authentication::Service::start` 接收已核验的 `domain::database::Barrier`、密钥、C1 设置和两个客户端，核验业务事实后返回服务。权限、屏障、可信时间与生命周期的分工见[数据库](../database.md#c1-接纳与可信时间)。两个启动方法都不读取环境、凭据或业务文件。

`verify` 接收受控 `Input`，将接纳、外呼和结论回写登记为同一有界工作。取消等待不取消已接纳的工作。同操作等待原任务实际结束，再分别验证原 token 和手机号。`Receipt` 返回原 Challenge ID、开始、截止和阶段。`Status` 的变体持有所属时点：`Calling` 没有时点，`Passed` 持有 `solved_at` 与 `finished_at`，其余阶段只持有 `finished_at`。行转换共同核对阶段和两个时间列，拒绝无效组合。Receipt 是原事实回执，不是发送许可或 HTTP progress。

运行身份可查询、首次插入，以及更新调用次数、阶段和结论时点。触发器允许从调用中保存结论，从可重试阶段占用第二次调用，或将可重试阶段关闭为无法确定。原操作、证明、号码、来源及截止不可改，结论不能重开。记录承担原操作识别和 token 防重，只有[保留与清理](#c1-保留与清理)满足保留条件后才能删除。新办理的可信时间独立持久提交，业务事务回滚不擦除已观察时间。连接及停止责任见[数据库](../database.md#c1-接纳与可信时间)。

隔离测试使用实际迁移和运行身份。场景覆盖并发同请求、异输入、token 跨版本占用、等待取消、停止排空及旧截止。停止测试核对等待取消、预算耗尽和排空后的锁保留，以及应用对象释放后的锁交接。TLS 代理注入提交响应丢失、旧后端延迟提交、确定回滚和时间采样停滞。历史核验测试覆盖多批累计超过 10 秒仍可启动，以及单批停滞时关闭服务并结束原连接。权限测试覆盖其他 schema 的直接、PUBLIC 和 SET ROLE 权限，以及缺失的阶段更新权限。子进程测试先确认旧进程退出，再启动新进程核对原事实。人机校验测试还覆盖下节所列阶段。这些测试不覆盖应用 HTTP 入口或完整认证闭环。

重复 C1 在原工作结束后才能取得自己的受管理执行，再核对原证明与阶段；恢复写入不在可取消的 HTTP 等待中执行。目标 progress 只反映已经确认本地阶段后仍在执行的工作。每次查询独立核对原证明与输入；阶段结束、登记缺席或提交结局待核对时，不用未完成行冒充进度。非阻塞查询不等待数据库连接；R1 在尝试 COMMIT 前移除进度登记。

## 已实现的人机校验

内部接纳结果使用私有 `verification::Acceptance` 枚举。`Existing` 携带已有回执，`Acquired` 携带当前工作取得的首次调用占用。两者都不代表校验通过。首次占用确认提交后，原工作调用 Siteverify。首次提交异常时，原工作跨锁确认占用后才能保留执行资格。后来的请求不能从已有 `calling` 行继承这份资格。客户端提交原材料后，服务将孤立的 `calling` 关闭为 `inconclusive`，不重复外呼。

可重试错误先保存 `retryable`，再提交第二次 `calling` 占用。两次调用沿用原验证 ID、token 和截止。错误分类由 [Turnstile](../platform/turnstile.md#验收与证据边界) 拥有。已保存的 `retryable` 只有次数和原截止仍允许时才能继续。

原工作按下文[本地回写协议](#c1-阶段与外部调用)保留响应，最多尝试两次本地保存。通过、拒绝和异常结论不可重开。原通过结果仍可回读，token 后来到期不改写已保存结论；后续发送许可须另查原证明效力。技术异常首次返回安全的结构化错误，保存后的异常阶段供后续原请求核对。底层可信时间失败关闭接纳，并保留尚未可靠收尾的调用阶段。

调用前预算耗尽时，先保存 `inconclusive`，再向本次调用者返回 `client::Error::Expired`。可重试阶段因原截止耗尽而关闭时采用相同处理。结论保存失败则保留回写错误，不用预算错误遮盖提交未知。后续原请求回读已保存的阶段，不再外呼。

`cargo test -p domain --locked` 用本地 HTTP 替身验证实际请求次数和固定验证身份。覆盖有限重试、次数与截止耗尽、异常响应、原结果重启回读和孤立调用收尾。隔离 PostgreSQL 验证首次提交恢复：响应丢失或延迟提交时，原工作确认占用后只外呼一次。确定回滚时不外呼。结论提交响应丢失、延迟提交或回滚时，仍复用原响应。两次回写都失败时，保留两个原因。还覆盖外呼期间时间回拨、等待取消、停止排空、非法状态迁移和时点组合。这些人机校验测试不覆盖短信发送；发送证据见下节。测试没有调用真实供应商，也不证明 HTTP 或完整认证闭环已交付。

首次调用占用的恢复测试通过独立连接和运行身份直接查库。延迟提交时，先观察恢复连接等待原事务锁。锁观察使用独立计算的预期键。测试精确匹配原 Operation-Id 的排他锁。确认原记录尚不可见且没有外呼后，再放行提交。收到供应商请求时，查库核对 `calling`、一次占用及十秒有效期。测试核对请求身份对应已提交的 Challenge。回读前再次查库，确认已保存 `passed`，原标识与期限保持不变。确定回滚时，测试确认没有留下记录。替身监视覆盖恢复、原请求回读及排空，确认没有额外外呼。

首次提交恢复的过期测试在隔离库中前移创建时点和截止，保留十秒有效期。代理拦截真实 COMMIT。锁观察使用独立计算的预期键。测试精确匹配原 Operation-Id 的排他锁。确认恢复连接等待后，再放行提交。回放前直接查库确认 `inconclusive` 已保存，随后核对重启回读。测试还断言恢复采用持久截止。替身监视覆盖恢复、原请求回读、重启及两次排空，确认零调用。这个场景使用已过期的持久事实；实际调用预算耗尽由供应商等待测试覆盖。

结论恢复测试先观察恢复连接等待原操作锁，再放行延迟提交。测试用独立计算的预期键，精确匹配原 Operation-Id 的排他锁。放行前确认通过结论尚未提交。三种提交故障均在重放前直接查库。测试核对 `passed`、原供应商的 `solved_at` 和回执结论时点。持久调用占用保持为一次。替身监视覆盖恢复、原请求回读及排空，确认没有再次外呼。

人机校验的库级重启测试先保存 `calling` 或 `retryable`，再停止并重建服务。孤立的 `calling` 收尾为 `inconclusive`，不再外呼。有效的 `retryable` 只允许一次后续调用。收到请求时，独立连接确认第二次占用已提交。请求核对原 token 和验证 ID，持久记录核对原身份与截止。重放前直接查库确认结论已保存。替身监视覆盖首次排空、服务重建、恢复、重放及最终排空。

人机校验的两次回写失败测试核对两次权限拒绝及诊断脱敏。独立连接先保存外呼时的原记录，再确认失败后整行未变。恢复测试权限后，原请求将遗留阶段收尾为 `inconclusive`。再次回读前直接查库，核对原身份、一次调用占用、期限及持久结论时点。替身监视覆盖回写失败、故障解除、收尾、回读及排空，确认没有再次外呼。

## 已实现的短信发送

`Service::send` 接收与 `verify` 相同的原输入。它在同一受管工作中完成人机校验、许可、发送占用和结论保存，返回只读 `authentication::dispatch::Receipt`。回执由认证用例核对原证明与输入后构造，包含消息 ID、创建时点、截止和状态。短信值与供应商协议模块不反向导出认证用例结果。同原操作请求等待已有工作结束后，各自核对原证明和输入。`verify` 仍只返回 Challenge 回执。

许可阶段先查原 Message，再判断通过证明和额度。新的许可按手机号、首次来源和部署额度取得事务锁，同时保存 Message 与同 ID Check。每个 Challenge 至多一份 Message；延迟外键要求配对共同提交。Check 当前保存摘要、原键和固定截止，R1 的失败计数与消费引用尚未接入。

只有保留原码的原工作可以取得 claim。claim 绑定 Message 与原工作，运行身份不能转让或单独删除。发送前确认占用提交，再检查剩余时间；请求只构造、签名和执行一次。发送区最多容纳两个工作，名额持有至本地结论处理结束。新实例先等待一秒；之后以锁覆盖实际调用，并在调用结束后等待一秒。这比实际开始间隔的下限更保守，不承诺两个请求同时外呼。

新进程回读许可时不重建验证码。有许可无占用则关闭为 failed，有占用但失去可信结果则关闭为 unknown。原工作仍持有供应商结果时最多尝试两次本地保存。终态不会重开，失败或未知不返还额度。时间样本先持久提交，后续时间采样拒绝倒退。

请求构造失败时，原工作先保存 failed。外呼失败或供应商结果无法确定时，先保存 unknown。保存成功后返回原错误。保存失败则返回 `MessageConclusion`，保留原错误与回写错误。回写错误保留提交未知和恢复失败的原因，包括连接收尾失败。错误诊断不包含原请求、验证码、手机号或供应商原文。

`Facts` 与 `Time` 携带固定的 `Stage` 和规则说明。诊断区分解码、事实核验、许可、恢复、占用、结论及签名阶段。配对、原工作归属、原码证明和事件先后分别报告。规则说明由代码固定，不携带异常值或数据库原文。这两类错误仍关闭接纳。提交恢复或结论错误包装保留这一关闭要求。

隔离测试覆盖四类供应商结局、同请求等待、异输入拒绝和重启回读。许可、占用、结论各注入提交响应丢失、延迟提交和回滚。还覆盖原码证明、配对约束、占用归属和不可重开终态。额度测试覆盖并发部署限制、滚动窗口与首次来源。故障测试覆盖等待取消、停止排空、时间回拨和两次本地回写失败，采样测试核对借池等待不重复累计。测试使用隔离 PostgreSQL 与回环 TLS 替身，不验证真实短信送达。HTTP 适配证据见[匿名身份入口](../http/identity.md#验收)；R1 和换钥仍未交付。

发送许可恢复测试从 `Service::send` 发起。延迟提交时，测试释放发送间隔锁，精确观察原 Operation-Id 锁上的等待。确认 Message、Check 和 claim 均不可见且没有外呼后，再放行提交。外呼前独立读取许可与码证明，随后核对实际 OutId、验证码和原工作归属。响应丢失或延迟提交均只发送一次。原消息标识、期限与码证明保持不变。确定回滚时返回未提交，三表均无残留且零外呼。替身监视覆盖恢复、原结果回读及排空。

发送占用恢复测试从 `Service::send` 发起。测试在原许可提交后注入占用 COMMIT 故障。延迟提交时，精确观察原 Operation-Id 锁上的等待。确认占用尚不可见且没有外呼后，再放行提交。占用回滚后，原工作凭保留的原码重新提交占用。收到 PNVS 请求时，独立 SQL 核对原工作占用已提交。请求的 OutId 和验证码分别对照原 Message 与 Check。三种故障均核对原许可和码证明保持不变。回读前确认发送结论已保存。替身监视覆盖恢复、原请求回读及排空，确认只外呼一次。

短信结论恢复测试在供应商响应前记录已提交的 Message 和发送占用。测试还核对外呼 OutId。延迟提交时，先观察恢复连接等待原操作锁。测试用独立计算的预期键，精确匹配原 Operation-Id 的排他锁。确认 `sending` 尚未改变后，再放行提交。三种提交故障均在重放前查库，确认原 Message 已保存 `sent`。测试还核对原工作归属、占用时点、消息期限及回执结论时点。替身监视覆盖恢复、查库、原请求回读及排空，确认没有再次外呼。

短信的库级重启测试覆盖有许可无占用和已有占用两种孤立阶段。停止并重建服务后，分别收尾为 `failed` 和 `unknown`。重放前通过独立 SQL 确认结论已保存。原 Message、码证明和占用保持不变，回执沿用原标识与期限。PNVS 替身监视覆盖首次排空、服务重建、恢复、重放及最终排空，确认零发送。

短信回写失败测试保留供应商错误、两次回写原因及诊断脱敏检查。独立连接核对故障前后的原 Challenge、Message、码证明和发送占用。时钟失效时服务关闭接纳，原记录组保持不变。移除回写故障后，原请求只将消息收尾为 `unknown`。再次回读前直接查库，确认结论已保存且原事实未变。PNVS 替身监视覆盖故障处理、收尾、回读及排空，确认没有再次发送。

发送期限测试从 `Service::send` 发起，覆盖占用前和占用提交等待后的剩余时间不足。隔离材料前移 Challenge 与许可时点，保留原事件顺序、五分钟有效期和配对截止。提交等待场景用延迟约束触发器阻塞真实 `COMMIT`。独立连接确认等待及占用尚不可见，再观察数据库时间跨过发送阈值后放行。回读前查库确认 `failed` 已保存，原许可、码证明与 Challenge 保持不变。占用前拒绝不产生 claim，提交等待后的拒绝保留原 claim。PNVS 替身持续监视至重放和排空结束，确认零发送。材料前移不代表实际等待五分钟；提交等待使用真实经过的时间。

新许可竞争测试从 `Service::send` 发起。测试用发送间隔锁将旧工作暂停在占用前，旧工作继续持有原码。待新许可提交或确定回滚后再放行。同手机号的新许可提交后，旧工作保存 `failed`，不取得 claim 或外呼。新许可的发送被拒绝后，旧结论仍可回读。新许可回滚或属于其他手机号时，旧工作仍发送一次。回滚场景拦截新许可的真实 `COMMIT`，独立查库确认没有遗留消息、码证明或占用。每次外呼核对原消息 ID、手机号、码证明及已提交占用。重放前查库确认结论与原事实，随后持续监视至排空结束。隔离材料仅前移第一份历史。事件顺序与固定期限保持不变，第二份许可仍遵守真实额度规则。测试没有实际等待一分钟。

发送容量测试从 `Service::send` 发起。两份不同号码的工作均已收到供应商成功响应。TLS 代理保留第一份结论的未确认提交。独立连接锁住第二份消息，阻塞结论更新。测试先观察原操作恢复锁及指定后端的阻塞，再取消第一份请求的等待者。第三份许可仍保存 `failed`，没有 claim 或外呼。释放第一份原提交后，测试通过 `Service::verify` 等待原工作结束。这个入口只核对人机校验，不补写短信结论。独立查库确认 `sent` 后，第四份请求可发送，此时第二份结论仍受阻。全部放行后，测试核对原事实、持久结论和重放结果。供应商监视持续到排空结束。测试复用真实运行身份与隔离故障设施，以调用次数和持久事实验证名额寿命。

同进程发送间隔测试从 `Service::send` 发起。第一条响应悬置时，独立查库确认另一号码的许可已提交。释放响应前，测试要求准备耗时不足一秒。耗时达到一秒则失败，避免准备阶段耗尽被测间隔。随后分别释放成功、拒绝或丢失响应，检查下一条请求的接收间隔至少一秒。PNVS 替身逐连接处理 TLS、请求头和响应等待，在请求头完整时记录单调时点。前一条响应和事件队列消费速度均不阻塞后续接收。测试核对外呼前的持久占用、原消息身份及重放前的结论，并持续监视至排空结束。替身测试另覆盖悬置响应与握手期间的并发接收、连接失败和停止收尾。显式停止会关闭监听，结束并等待全部连接任务，保留连接任务失败。这些时点只证明回环替身的接收间隔，不代表真实供应商的接收或送达时间。

## Challenge 手机号保护

`domain::identity::challenge::mobile::Sealed` 已交付手机号封装与读取。加密只接收 `domain::identity::keys::encryption::Keys`、Challenge ID 和已校验的 `Mobile`。它使用活动 `encryption` 键；读取按信封原 key ID 取键，不回退到活动键。密文使用[密钥材料](../keys.md#52-信封)规定的 V1 布局，key ID 随信封保存，不另设重复列。

AAD 为 `E("nucleus/identity/envelope/v1", header, challenge_id, "challenge.mobile")`。`header` 是信封的 21 字节头，`challenge_id` 是 UUID 的原始 16 字节。本模块固定域、字段用途和业务身份，Platform 固定头部位置与四字段编码顺序。业务调用方不能传任意域或字段列表。读取端从当前记录重建 Challenge ID，不能从密文推断归属。

`Sealed::new` 只校验信封结构，`open` 才完成认证并构建 `Mobile`。认证后的明文仍须通过同一个严格手机号解析器，不修剪或转换。缺少原键、绑定或标签不符、非法 UTF-8 和非法手机号均为技术错误，不解释成证明不匹配。明文手机号与解密临时缓冲在释放时清零，错误不包含原号码或密文。

手机号的[查找摘要](lookup.md)不含 Challenge ID，保证相同号码跨记录可比较。Challenge 的 `mobile` 列使用 `identity.mobile` 复合类型。子字段 `value` 使用 `identity.sealed` domain，要求非空且至少 37 字节。`hash` 使用 `identity.digest` domain，要求非空且恰好 32 字节。PostgreSQL 可能跳过已带 domain 类型的 NULL 检查，见 [CREATE DOMAIN](https://www.postgresql.org/docs/18/sql-createdomain.html#SQL-CREATEDOMAIN-NOTES)。列约束因此再次拒绝空子字段。本片按原操作和 token 查找，没有新增手机号索引。

`challenge::mobile::Mobile` 共同编码和读取密文与摘要。子字段 SQL 编解码接受 `bytea` 及以它为基类型的 domain，不限定模式名和名称。解码仍检查密文结构和摘要长度；随后按原业务身份鉴别解密，再核对摘要。原请求先验证 token，才鉴别解密并比较手机号；启动也校验全部保留行。行解码不产生认证成功。封装测试使用独立密码向量和虚构材料。持久测试覆盖嵌套空值、长度错误、密文篡改及摘要不符。

## 输入与事实归属

C1 输入为原 Operation-Id、规范手机号和原 token。Challenge 先按记录上的原键验证 token，再核对用途和规范手机号。重试来源变化保留首次统计来源，不形成新的发送归属。不同操作复用同一 token，由稳定对象协调下全部保留键版本的查询拒绝。

R1 输入包含原 Operation-Id、32 字节规范 Base64url secret、Message ID、手机号和八位数字码。实际 AppID 来自入口已核验设置，不由客户端指定。原 secret 的 SHA-256 与规范输入 HMAC 分别保存，核验顺序和准确编码见[原输入证明](proofs.md)。

identity.authentications 同时拥有原操作、原 secret 证明、输入摘要及 key ID、用途、应用来源和不可重开的认证结论。原请求与认证结论不再拆成一对一表。Check 拥有码的效力、错误次数和消费引用；Session、Handoff 与注册凭据有独立生命周期。

## 消息与校验事实

每个 Challenge 最多产生一份 Message，Message 用 challenge_id 引用原 Challenge。Message ID 同时作为 Check ID 和供应商 OutId。ordinal 表示许可提交顺序，不从时钟或 UUID 推断。Message 从 sending 进入 sent、failed 或 unknown 后不可重开；sent 只表示供应商受理。

验证码生成规则为八位 ASCII 数字，保留前导零。对随机 u32 拒绝采样，丢弃不小于 4,200,000,000 的值，再对 100,000,000 取余并补零。随机源失败不形成部分许可。原发送工作持有可清零的 Code，数据库只保存 Check HMAC，不保存验证码密文。

目标 Check 与 Message 共 ID，保存 hash、key_id、failures、可缺席的 authentication_id 和固定 expires_at。摘要使用 message 用途与固定域 nucleus/identity/message-code/v1，编码 Message UUID 的 16 字节及八位原码。按原 key ID 常数时间核验。

有效 Check 属于准确手机号和用途，是该号码最新许可，未消费、未到期且 failures 小于 5。存在 ordinal 更大的已提交 Message/Check 时旧码失效；新许可回滚不替换旧码。Message 发送状态不改变这些条件。启动与原结果回读核对保留消息的事件时间，新许可使用持久可信时间。发现回拨或先后矛盾后，按[可信时间规则](../architecture.md#时间与个人顺序)关闭时间敏感接纳。

## C1 与 R1 的目标事务契约

整体调用链和事务分段见[架构流程](../architecture.md#c1-与-r1)。各事务按[共同锁序](../architecture.md#锁与决定性读取)取得原操作及实际竞争对象。C1 使用 token、手机号、首次来源、部署额度和消息；R1 另涉及账户及注册凭据。锁后才判断原结果、时间与当前资格。

| 事实               | 关键约束                                                                              |
| ------------------ | ------------------------------------------------------------------------------------- |
| Challenge          | 动作家族内原操作唯一；原 token 按 key ID 与完整摘要唯一，跨保留版本由稳定对象协调检查 |
| Message 与 Check   | 一份 Challenge 至多一个 Message；许可提交时 Message 与同 ID Check 完整配对            |
| claims             | ID 为 Message ID，唯一外键；固定原工作身份，不提供可转让状态                          |
| Authentication     | 原操作唯一，原证明与输入不可改；结论与本次 Check 后果及适用凭据共同提交               |
| Session 与 Handoff | 来源、账户、原 token 摘要和固定期限配对；回读不新建或续期                             |

发送占用至少保留到 Message 合法删除。运行身份不能单独删除或更新 claim。Message 进入 sent 或 unknown 必须已有 claim；failed 可以来自发送前关闭或占用后的明确拒绝。原手机号、来源、许可时点及截止不可改。

### C1 阶段与外部调用

| 阶段         | 本地事实与判断                                                            | 继续边界                                                                  |
| ------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 接纳校验     | 保存 Challenge、原证明、固定验证 ID、首次调用代次和截止                   | 确认提交后，原工作使用原 token 外呼                                       |
| 再次校验占用 | 前次调用已结束，错误可重试，原次数和截止仍允许；先保存下一代次，最多两次  | 沿用原验证 ID 和 token，重启不重置次数                                    |
| 校验结论     | 核对供应商成功、hostname、action、cData、时间和本次代次                   | 保存 passed、rejected、可重试等待或 inconclusive；结果丢失不能形成 passed |
| 发送许可     | 原通过证明仍可用，全部额度允许；共同保存 Message、Check 和截止            | 许可计数成立，新码成为最新；原 Message 已存在时只读取                     |
| 发送占用     | 原工作取得有界发送许可和实际开始间隔；码仍有效且至少剩余 60 秒            | 先确认唯一 claim 提交，再在事务外复查剩余时间并调用一次                   |
| 发送结论     | 核对 claim 与原工作；受理、明确拒绝、不确定分别形成 sent、failed、unknown | 可信结果仍在原工作时只重试本地回写，不能再次外呼                          |

原 token 不持久化。新进程在客户端提供原材料后按已保存阶段判断，不能因为 widget 重置或供应商 token 到期宣布原办理失败。完整恢复窗口内，已保存的通过、许可和结果各按原事实解释。

原工作保留已核对的 Siteverify 响应。在线借池、事务开启或回写失败后，最多使用独立恢复连接追加一次本地回写。恢复先跨原操作锁读取原阶段；阶段已提交时复用其原时点，否则用保留响应重新判断并保存。该恢复不重新调用 Siteverify，也不重置外呼次数或截止。通过证明仍须满足回写时的时间条件。

原发送许可存在但没有 claim，原工作结束后归为未发送的 failed。已有 claim 但失去可信供应商结果时归为 unknown，即使实际调用可能尚未开始。两种情况均不允许新进程补发，也不退还持久额度。

PNVS 请求由原工作一次构建并验证，按[发送协议](../platform/pnvs.md)原样执行。OutId 不证明供应商去重。签名、等待和调用不延长 Check 截止。

发送占用取得的可信数据库时间与采样语句发起时的单调时点配对。签名时间和剩余有效秒数只累计此后的耗时，包括有预算上限的采样往返与提交；借池、事务锁和采样锁之前的等待不再叠加到较晚的数据库样本上。

原工作持有可信发送结果时，先通过在线池保存。借池、开启事务或本地回写失败后，使用独立恢复连接核对并保存同一结果。恢复连接仍受原操作锁约束；整个过程最多两次本地尝试，不重复外呼。两次均失败时保留两个安全错误来源，再按持久证据处理未知结果。

发送终态和孤立发送收尾均先取得持久可信时间，再绑定 finished_at 写入。供应商调用期间发生回拨时关闭时间敏感接纳，保留尚未可靠收尾的 sending 与发送占用；不能用更早的原始数据库时间强行形成终态。后续恢复仍遵守原执行结束边界。

### 时间与持久额度

下表规定 C1 与 R1 目标路径的工程初值。各项随首个真实消费者所在的切片交付，不要求在首片中全部实现。不能据此推断实际吞吐或供应商送达。额度和期限从服务端设置取得；已经保存的截止与许可时点不因设置调整而重算。

| 范围           | 初值与事务依据                                                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Turnstile 校验 | 首次占用时固定 10 秒总调用预算，最多两次调用；同一原 token 与固定验证身份在允许的重试中复用，不重置开始时点。                                                                        |
| 通过证明       | 供应商完成时点 `C` 与回写事务数据库时点 `T` 满足 `C <= T + 2 秒` 且 `T < min(C,T) + 300 秒`，才保存 `solved_at=C` 与 `finished_at=T`；准备许可时再次要求当前数据库时间早于同一截止。 |
| 验证码         | 许可提交时固定默认 5 分钟截止；有效码最多接受 5 次错误猜测。发送等待、回读和重启不延期。                                                                                             |
| 同手机号许可   | 最短间隔 60 秒；滚动 1 小时最多 5 份，滚动 24 小时最多 10 份。                                                                                                                       |
| 可信来源许可   | 滚动 60 秒最多 3 份；滚动 1 小时涉及最多 10 个不同手机号。首次 Challenge 固定统计来源，重试来源变化不重归属。                                                                        |
| 部署许可       | 滚动 24 小时最多 100 份；实际短信开始间隔至少 1 秒，最多 2 个发送工作在途。                                                                                                          |

所有持久发送额度都以 Message 的原许可时点、规范手机号和 Challenge 固定来源统计，不另设可重置的已用计数。滚动窗口为 `(T - window, T]`，`T` 是取得对象协调后的数据库时间。额度读取失败不能当成零；许可和全部额度占用同事务提交，发送失败、未知或进程退出均不返还。旧码只在新 Message 与 Check 成功提交后失效。供应商返回的发送状态不决定 Check 的本地效力。

额度耗尽时，根据已提交许可计算下一次可接纳时点。计数窗口须等到足够多的记录退出；来源的不同手机号占用须等到该号码的最后一份许可退出，当前请求号码只占一个槽位。多个约束同时不足时取最晚时点，剩余秒数向上取整，由 HTTP 映射为 Retry-After。该时点不保证没有新竞争，也不延长原证明期限。

### R1 单事务与对象协调

命中 Authentication 时先核对 secret，再比较用途、来源与规范输入。命中原结果后不重新验码。新办理取得 Check 行锁后才采样数据库时间。等待跨过截止时按过期处理，不计错、不消费。共同结果复用锁后的时点，并核对消息归属、最新许可及手机号当前占用。

| 锁后结果                           | 共同提交                                                     | 原结果回读                             |
| ---------------------------------- | ------------------------------------------------------------ | -------------------------------------- |
| 消息不适用、过期、已消费或达到上限 | 不计错，不创建认证记录；明确回滚                             | verification_required，没有保存原结论  |
| 有效码但输入错误                   | Check 错误次数增加一次，保存原证明、输入和拒绝               | 同原操作不重复计错                     |
| 正确码且账户正常                   | 消费 Check、保存认证成功、独立 Session 和 Handoff            | 仅交付仍有效的同一会话                 |
| 正确码且账户暂停                   | 消费 Check、保存拒绝，不建立凭据                             | 后来解除暂停不改变原拒绝               |
| 正确码且无账户                     | 消费 Check、保存待注册结论、新凭据并替换同手机号旧未完成凭据 | 原凭据被替换、消费或到期后要求重新认证 |

Session token 为随机 32 字节，数据库保存摘要。网站短信会话默认 24 小时。注册 token 同为随机 32 字节，默认 10 分钟。Handoff 用 credential_seal 独立封装原会话 token，默认 10 分钟且不超过 Session 期限。

原结果交付先验证原证明与输入，再取得可信数据库时间，核对当前账户、Session 撤销、来源与凭据、Handoff 期限。回拨关闭时间敏感接纳，不因时钟变早而重新交付已到期凭据。原凭据或交接失效不重新签发。密码、引用或密钥故障保留技术错误，不能伪装成过期或错误验证码。

在线池借用、事务开启或提交失败后，R1 使用独立恢复连接核对原结果。原结果不存在时保留原技术错误；存在时仍先验证证明和输入，再交付当前有效的原凭据。

新事务中的原证明不匹配、输入不匹配或消息不适用，在明确确认 ROLLBACK 后直接返回所属拒绝。已知未提交的业务拒绝不再依赖恢复连接；回滚未确认时仍进入结局核对。

重叠的同原操作请求先等待已有执行结束，再核对持久结果。没有保存 Authentication 时，由重复请求取得自己的执行并重新判断本次输入。不存在持久结果本身不是依赖故障；失效 Check 等明确但未持久化的拒绝仍返回 verification_required。

### 按需核对与清理

本用例按[未知提交协议](../architecture.md#未知提交)核对原阶段，其他无冲突操作继续。C1 的供应商结论与数据库结局分别解释；确定本地事务回滚也不允许重复已占用的发送。

| 候选                 | 本用例的保留条件                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------- |
| Challenge 与调用阶段 | 原恢复责任已结束，调用代次可解释，Message 与真实引用均已释放                              |
| Check 与 Message     | Check 到期及 Message 终态两者中较晚时点之后至少 24 小时；已退出统计窗口且无恢复或凭据引用 |
| Authentication       | 原结论终态后至少 24 小时；Check 消费、凭据和 Handoff 等引用均已释放                       |
| 发送占用             | 先解释 sending 的终态；随 Message 合法清理，不单独释放                                    |
| 最后原操作结果       | 所属恢复、防重、统计和引用责任全部结束后，与从属记录共同删除                              |

先清 Check，再清 Message，最后清无依赖的 Challenge。原结果仍承担恢复或防重时继续保留。清理按对象核对，不按批次整体推断成功；共同清理规则见[架构](../architecture.md#清理)。

数据库删除保护覆盖以上期限、引用与配对条件。认证只允许到期清理会话、交接和注册凭据，或由账户、会话删除带走所属从属记录。新 R1 替换未到期注册凭据时，在提交处核对同手机号的新凭据已形成。运行身份不能通过任意 DELETE 提前释放发送占用、额度或原操作。原执行结束和协调仍由应用证明。

### C1 保留与清理

已接入 C1 短期记录回收，范围包括遗留阶段核对、到期删除、入口响应和停止。没有永久退役表。R1、会话、换钥和通用任务框架不在此实现范围。现有人机校验有限重试及已通过阶段的继续条件保持不变。

`authentication::database` 拥有 Challenge、Message、Check 与 claim 的固定查询、解码和事实校验，不提交事务。请求流程另行核验原 token 和手机号后构造回执；后台清理不构造该回执。`verification` 拥有人机校验事务，`dispatch::transaction` 拥有发送事务与恢复。`retention` 拥有保留规则、分页与删除恢复。Message 的工作标识和结论类型归 `identity::message`，共享事实模块不依赖发送编排。

#### 保留与阶段核对

没有 Message 的 Challenge，至少保留到调用截止与结论较晚时点的 24 小时后。passed 还必须经过原证明的发送有效期。有 Message 时，整组记录必须同时满足既有 Message、Check 保留条件。清理使用持久可信时间，采样失败停止时间敏感办理。

候选的年龄只用于筛选。清理先取得与请求共用的原操作执行名额；已有工作时跳过，后续轮次再检查。取得名额后，依次取得运行共享屏障、原操作锁与所属对象锁，再用新语句读取事实。整个核对、提交恢复与删除过程保留执行名额，重复请求等待结束后独立检查仍保留的原结果。

确认旧执行结束后，遗留 calling 和已过截止的 retryable 才能转为 inconclusive。遗留 sending 按已保存的发送占用解释：没有 claim 时为 failed，有 claim 时为 unknown。只保存本地结论，不调用供应商。结论时点使用本次可信时间，保留期从相应结论重新计算。本轮刚解释的记录继续保留。供应商 unknown 是已保存的发送终态，与尚未查明的数据库提交结局不同。后者在完成原操作核对前保留全部证据；事实矛盾时停止相关接纳。

#### 删除保护与标识复用

记录保留期间，原 Operation-Id 仍绑定原 token、手机号与结果。整组删除后不保留标识墓碑，也不再承诺原结果回读或固定的 404。相同 UUID 再次请求时按新申请处理，重新验证人机证明和额度；有效的新证明可建立新的 Challenge。旧 token 不继承原通过结论，失效证明不能形成发送许可。客户端应在[恢复材料期限](../client/recovery.md#恢复材料)内核对原结果，期满停止自动重试；明确再次申请时使用新标识和新证明。

每笔事务只删除一个原操作的完整记录组，依次删除 Check、claim、Message 与 Challenge。没有 Message 时直接删除符合条件的 Challenge。claim 删除必须满足 Message 的期限，并由提交约束要求 Message 同时删除；不能单独释放发送占用。Check 与 Message 继续由双向延迟外键保护配对。Message 删除的延迟约束要求同笔事务删除原 Challenge。保留原 Challenge 的部分删除在提交时回滚。

数据库用 invoker 触发器与延迟约束保护期限、终态、真实引用及配对删除。Challenge 删除直接核对原行及其引用。新鲜、阶段未结束或仍有 Message 引用时拒绝删除。并发插入同一 Operation-Id 由原唯一约束协调：删除提交后可重新使用，删除回滚则原行继续占用。运行身份不得禁用触发器、截断表或变更结构。不使用可由调用方伪造的会话标记豁免保护。

上述跨表保护只接受 `READ COMMITTED` 写事务，由数据库直接强制。四张 C1 表的 INSERT、UPDATE、DELETE 都在语句执行前通过 invoker 触发器检查。检查读取 `pg_catalog.current_setting('transaction_isolation')`，拒绝其他隔离级别。登录默认值、应用 BEGIN 或自定义会话标记均不能代替这项检查。隔离级别不符属于技术故障，不解释为用户拒绝，也不自动换级别重试。

跨表约束函数显式使用 `VOLATILE`，在锁等待结束后另发查询核对事实。[事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)决定快照的可见范围；延迟执行不会刷新旧 `REPEATABLE READ` 快照。函数内查询的快照规则见 [PostgreSQL 函数易变性](https://www.postgresql.org/docs/18/xfunc-volatility.html)。

运行身份仅新增上述四张 C1 表的受保护 DELETE 与下述序列的 USAGE。启动与部署权限核验同步覆盖权限，拒绝缺失或超出的授权。删除资格由持久事实与数据库时间共同保护；数据库时间早于已保存可信时间时拒绝清理。执行是否结束仍由应用协调证明，数据库权限不代替这个边界。

#### 顺序、运行与恢复

Message 的 ordinal 改由持久数据库序列生成。分配与提交继续持有部署许可锁。序列采用 `CACHE 1`、`NO CYCLE`，运行身份仅有 USAGE，没有重设序列的 UPDATE 权限。序号允许回滚留下间隙；删除全部 Message 后也不从一重新编号。序列的缓存与回滚语义见 [PostgreSQL 序列](https://www.postgresql.org/docs/18/sql-createsequence.html)。本片不改变额度窗口或最新验证码规则。

认证能力的 `Retention` 拥有游标、候选筛选、阶段解释、删除事务和恢复。进程入口持有一个后台任务，负责定时调用、监督和停止。每轮最多取 128 个候选，以原 Operation-Id 为稳定分页键，逐项直接执行。单笔查询或事务最多 10 秒。轮次串行，轮次结束后间隔 60 秒，不积压新轮次。清理与请求共用原操作互斥和固定容量，忙时跳过。停止时不再选取新候选，等待当前清理及其恢复、HTTP 读取和 C1 请求全部结束，随后关闭共享连接。

清理工作在实际结束处记录最终技术失败，携带原操作标识及脱敏原因。进程持有后台句柄，取消停止等待不取消当前清理，也不丢失诊断或任务失败。事实或时间等致命故障关闭接纳，释放执行名额后向监督者返回原始错误，保留提交与恢复原因。已收到停止通知也不能将该错误改写为正常关闭。可重试的单项技术故障保留记录后继续本轮。扫描器观察关闭状态，停止继续选取，不重复记录该原因。请求任务由 C1 `Work` 单独持有和排空。排空完成表示任务与连接已经结束，不把已记录的业务故障改写为成功。

分页游标只在进程内保存，记录最后检查的候选。被占用而跳过的对象也推进游标，让后续候选继续取得检查机会。读到尾部后清空游标，下一轮从起点扫描，重访此前跳过的对象及游标之前的新候选。重启也从起点开始；游标不证明记录已删除，不参与结果恢复判断。不为分页新增持久任务记录。

删除提交未确认时，先淘汰原连接并等待驱动，再用独立恢复连接取得同一原操作锁。原执行保存尝试删除的 Challenge ID、Message ID 和阶段。锁后确认这些原实体及 Check、claim 全部消失，才认定删除完成；完整原组且阶段未变表示未提交。相同 Operation-Id 对应的新实体不属于原组，回读不删除或修改新实体。原组残缺或阶段矛盾属于事实故障。尚未取得原组的读取失败不宣称删除成功；候选已不存在时无需写入。遗留阶段回写按原对象和原阶段恢复，不能通过重跑供应商取得结论。查询失败保留记录，下轮可再选；时间、事实或执行归属故障关闭相关接纳。

#### 验证边界

只用隔离 PostgreSQL、真实运行授权和虚构材料。验证新鲜记录、在途工作、未解释阶段、窗口内额度及真实引用都阻止删除。验证到期整组删除与无 Message 的清理，单独删除 claim 或提前删除必须被拒绝。并发测试覆盖原请求、原结果回读和清理竞争。提交故障区分删除前回滚、提交响应丢失和旧后端迟到提交。

删除恢复测试先保存原 Challenge、Message、Check 与 claim 的标识和全部字段。延迟提交时，锁观察使用独立计算的预期键。测试精确匹配原 Operation-Id 的排他锁。取消等待和关闭接纳后，清理任务仍未结束，原组仍完整可见。放行提交后，测试用独立 SQL 按原实体标识回读四张表。提交响应丢失或迟到提交时，原组全部消失；回滚时，原组的全部字段保持不变。回滚后的检查先于下一轮清理，随后另行验证下一轮可以删除原组。

遗留短信收束另覆盖有无 claim 与三种提交故障的组合。测试使用超过 24 小时的旧许可，独立查库确认终态分别为 `unknown` 和 `failed`。延迟提交时，锁观察使用独立计算的预期键。测试精确匹配原 Operation-Id 的排他锁，再放行原事务。回滚时先确认 `sending` 和空结论时点仍保留，再由下一轮收束。测试核对结论时点属于本轮数据库时间范围，其余原字段保持不变。后续扫描保留新终态及原组，原请求回读返回同一结论时点。短信替身监视覆盖恢复、后续扫描和回读，确认没有外呼。

直接运行身份的 SQL 验证绕过应用入口。覆盖四张 C1 表的写入，确认非 `READ COMMITTED` 事务被拒绝。提交约束拒绝单独删除 claim。删除 Check、claim、Message 却留下 Challenge 时也拒绝提交。整组删除仍可提交。同标识并发重插等待旧行删除，删除提交后允许新行，删除回滚后仍拒绝重复占用。删除恢复另验证相同标识的新实体不被旧尝试误认或删除。

分页验收使用超过 128 个候选。首批对象被占用时，后续批次仍能清理；首批释放后，回环扫描必须再次处理。扫描过程中加入 UUID 小于当前游标的候选，验证下一次回环能够发现。再覆盖进程重启从起点扫描，确认重访不会误删新实体或误判删除结果。

隔离测试覆盖遗留阶段收束、整组及无 Message 清理、直接 SQL 拒绝、并发重插、分页回环、提交故障与排空。清空历史后，同一操作标识配合新的人机证明可再次申请，短信序号继续递增，原发送的滚动额度测试继续适用。入口测试停止原应用实例、准备合法的过期历史，再启动新实例，验证进程触发清理。旧请求重新经过人机校验，替身拒绝旧证明后返回 `403 verification_invalid`，不生成 Message。该重启测试在同一测试进程内重建应用，不是独立进程重启证据。停止测试用数据库屏障阻塞当前清理，验证停止超时和取消后仍持有任务与实例锁；释放屏障后只完成当前候选，后续候选保留，任务与连接结束后进入 `Stopped`。测试只使用隔离 PostgreSQL 和供应商替身，不证明真实部署、实际短信送达或 R1 引用清理。

清理扫描故障与 HTTP 排空超时另有组合测试。测试先阻塞可信时间采样，用 HTTP `100 Continue` 确认正文读取已开始，再释放采样并触发时间倒退检查。覆盖清理先失败和停止信号先到的两种顺序，核对超时诊断保留实际原因和实例锁。逐项清理故障测试在数据库屏障处启动停止，再注入记录时间矛盾并释放原执行。测试验证停止返回原始处理和恢复错误，记录继续保留，任务与连接结束后才进入 `Stopped`。收尾测试还用预置故障和受数据库屏障阻塞的工作，验证取消与超时后的错误保留。子进程使用构造错误验证最终日志保留起因与收尾错误，且只记录一次失败并退出；不将该日志测试视为真实部署故障证据。

## 验收

以下为 C1 与 R1 的累计目标。各项随首个真实消费者验收，阶段不等于一个实施切片；不得延后当前结果所需的保护，也不因矩阵完整而一次实施整条路径。

使用隔离 PostgreSQL 和供应商替身，观察真实调用次数与数据库后果。覆盖各调用占用提交前后退出、可信外部结果仅重试本地回写、token 跨操作及跨键版本竞争、原材料恢复、发送间隔和额度不返还。

覆盖同码两个 R1、新 C1 与旧 R1、五次错误、原拒绝回读、暂停账户正确码消费、注册凭据替换及会话原交接。提交故障验证旧后端迟到提交、原操作核对和无关事务继续；记录调用方故障与 PostgreSQL 线协议故障的证据区别。

共同停止、构造旁路和日志验收见[架构](../architecture.md#隔离验收)。当前不存在完整 C1→R1 的运行验收结论。

补充验证在线池耗尽后的同结果回写与 R1 恢复、Check 锁等待跨越截止、消息终态回写期间时钟回拨。可信时间覆盖业务回滚不擦除样本、采样提交未知不交付时间、普通重启及原凭据读取拒绝回拨。数据库保护覆盖提前删除、标识复用、合法清理和注册凭据替换。监听或任务异常后，验证已接纳外呼收尾、驱动结束和失败退出；全部场景只使用隔离材料。
