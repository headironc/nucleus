# 短信认证与原结果交接

本文拥有 C1 发码与网站短信 R1 的认证专属事实、时间、额度、供应商阶段及原结果，入口为 `POST /api/v1/codes`、`POST /api/v1/sessions`。原操作仅在记录保留期内防重。R2 由[注册用例](registration.md)拥有。共同执行与提交恢复由[架构](../architecture.md#原操作与恢复)拥有。

## 首次接纳边界

匿名 C1 接收已验证 Operation-Id、Mobile、Token 和可信 IP，用途固定为 authentication。[换号发码](mobile.md#四阶段办理)复用同一接纳协议，并由所属入口绑定人员、会话及适用申请。IPv4-mapped IPv6 转为 IPv4。Challenge 保存原 token 证明、受保护手机号、首次来源、固定验证身份、calls=1 和 10 秒截止。calls 只表示机会占用，不证明已外呼。持久用途与供应商 action 的对应关系见 [Turnstile 用途表](../platform/turnstile.md#入口与上下文)，未知用途是持久事实错误。

保存 Challenge 不表示通过校验或获得发送许可。后续阶段分别保存通过结论、发送许可与发送占用；各阶段的继续条件见[目标事务契约](#c1-与-r1-的目标事务契约)。取消等待不取消已接纳的工作。同操作等待原任务实际结束，再分别验证原 token 和手机号。接纳回执只证明原事实，不是发送许可或 HTTP progress。

原操作、证明、号码、来源及截止不可改，结论不能重开。阶段只能从调用中保存结论，从可重试阶段占用第二次调用，或将可重试阶段关闭为无法确定。记录承担原操作识别和 token 防重，只有[保留与清理](#c1-保留与清理)满足保留条件后才能删除。新办理已观察的可信时间独立持久，业务事务回滚不擦除已观察时间。

重复 C1 在原工作结束后才能取得自己的受管理执行，再核对原证明与阶段；恢复写入不在可取消的 HTTP 等待中执行。目标 progress 只反映已经确认本地阶段后仍在执行的工作。每次查询独立核对原证明与输入；阶段结束、登记缺席或提交结局待核对时，不用未完成阶段冒充进度。R1 在尝试提交前移除进度登记。

## 人机校验

首次调用占用确认提交后，原工作调用 Siteverify。首次提交结局未知时，原工作确认占用后才能保留执行资格。后来的请求不能从已有 `calling` 阶段继承这份资格；客户端提交原材料后，服务将孤立的 `calling` 关闭为 `inconclusive`，不重复外呼。

可重试错误先保存 `retryable`，再提交第二次 `calling` 占用。两次调用沿用原验证 ID、token 和截止。错误分类由 [Turnstile](../platform/turnstile.md#验收与证据边界) 拥有。已保存的 `retryable` 只有次数和原截止仍允许时才能继续。

原工作按下文[本地回写协议](#c1-阶段与外部调用)保留响应，最多尝试两次本地保存。通过、拒绝和异常结论不可重开。原通过结果仍可回读，token 后来到期不改写已保存结论；后续发送许可须另查原证明效力。技术异常首次返回安全的结构化错误，保存后的异常阶段供后续原请求核对。可信时间失败关闭接纳，并保留尚未可靠收尾的调用阶段。

完整核对的 `passed`、`rejected` 和 `inconclusive` 已是持久结论，后续只读收尾失败不覆盖这些结论。`calling`、`retryable` 的读取收尾未确认时，不形成外呼资格；新写入的阶段只有提交确认后才可交付。不可靠原因立即关闭接纳，并阻止本次发送继续。调用预算耗尽与供应商响应过期保持不同分类。

调用前预算耗尽时，先保存 `inconclusive`，再向本次调用者返回过期。可重试阶段因原截止耗尽而关闭时采用相同处理。结论保存失败则保留回写错误，不用预算错误遮盖提交未知。后续原请求回读已保存的阶段，不再外呼。

## 短信发送

发码与 `verify` 接收相同的原输入，在同一受管工作中完成人机校验、许可、发送占用和结论保存，回执包含消息 ID、创建时点、截止和状态。同原操作请求等待已有工作结束后，各自核对原证明和输入。

许可阶段先查原 Message，再判断通过证明和额度。新的许可按手机号、首次来源和部署额度协调，同时保存 Message 与所属校验。每个 Challenge 至多一份 Message，许可提交时 Message 与所属校验完整配对。认证用途保存同 ID Check，包含受保护验证码、原键、固定截止、R1 失败计数和消费关联。原号及新号发码保存互斥的 Confirmation，身份与申请绑定见[手机号更换](mobile.md#事实与约束)。三个用途共用 C1 的额度和执行寿命。新许可只有提交确认或完整原操作回读后才形成发送准备资格；已知原事实不因后续收尾失败改为未知。

只有保留原码的原工作可以取得发送占用。占用绑定 Message 与原工作，不能转让或单独删除。发送前确认占用提交，再检查剩余时间；请求只构造、签名和执行一次。发送区最多容纳两个工作，名额持有至本地结论处理结束；相邻实际开始间隔至少 1 秒，不承诺两个请求同时外呼。

新进程回读许可时不重建验证码。有许可无占用则关闭为 failed，有占用但失去可信结果则关闭为 unknown。原工作仍持有供应商结果时最多尝试两次本地保存。终态不会重开，失败或未知不返还额度。

请求构造失败时，原工作先保存 failed。外呼失败或供应商结果无法确定时，先保存 unknown。保存成功后返回原错误；保存失败则同时保留原错误与回写错误。错误诊断不包含原请求、验证码、手机号或供应商原文。PNVS 错误按[发送协议](../platform/pnvs.md#直接响应与故障)保留安全状态、调用耗时和原因；受管工作结束时记录一次最终失败，等待者取消不改变该边界。事实或时间核验失败关闭接纳。

## Challenge 手机号保护

Challenge 的手机号按[密钥材料](../keys.md#52-信封)规定的信封受保护保存，绑定所属 Challenge 与字段用途；读取按原密钥版本取键，不回退到活动键，也不能从密文推断归属。认证后的明文仍须通过同一个严格手机号解析器，不修剪或转换。缺少原键、绑定不符、非法 UTF-8 和非法手机号均为技术错误，不解释成证明不匹配。明文与临时缓冲在释放时清零，错误不包含原号码或密文。

手机号的[查找摘要](lookup.md)不含 Challenge 身份，保证相同号码跨记录可比较。原请求先验证 token，才解密并比较手机号；启动也校验全部保留记录。

## 输入与事实归属

C1 输入为原 Operation-Id、规范手机号和原 token。Challenge 先按记录上的原键验证 token，再核对用途和规范手机号。重试来源变化保留首次统计来源，不形成新的发送归属。不同操作复用同一 token，由稳定对象协调下全部保留键版本的查询拒绝。

R1 输入包含原 Operation-Id、32 字节规范 Base64url secret、Message ID、手机号和六位数字码。实际 AppID 来自入口已核验设置，不由客户端指定。原 secret 证明与规范输入证明分别保存，核验顺序见[原输入证明](proofs.md)。

Authentication 同时拥有原操作、原 secret 证明、输入证明、用途、应用来源和不可重开的认证结论。Check 拥有码的效力、错误次数和消费关联；Session、Handoff 与注册凭据有独立生命周期。

## 消息与校验事实

每个 Challenge 最多产生一份 Message。Message ID 同时作为所属 Check 或 Confirmation 的 ID 及供应商 OutId。许可顺序号表示许可提交顺序，单调递增、可有间隙，清空历史后也不重新编号，不从时钟或 UUID 推断。Message 从 sending 进入 sent、failed 或 unknown 后不可重开；sent 只表示供应商受理。

验证码为均匀随机的六位 ASCII 数字，保留前导零。随机源失败不形成部分许可。原发送工作持有可清零的验证码，持久事实只保存所属校验的受保护摘要，不保存验证码明文或密文，核验按原密钥常数时间比较。

有效 Check 属于准确手机号和认证用途，是该号码同用途的最新许可，未消费、未到期且 failures 小于 5。存在更晚提交的认证许可时旧码失效；新许可回滚不替换旧码。换号 Confirmation 不替换认证 Check，反向也不互换。Message 发送状态不改变这些条件。启动与原结果回读核对保留消息的事件时间，新许可使用持久可信时间。发现回拨或先后矛盾后，按[可信时间规则](../architecture.md#时间与个人顺序)关闭时间敏感接纳。

## C1 与 R1 的目标事务契约

整体调用链和事务分段见[架构流程](../architecture.md#c1-与-r1)。各事务按[共同锁序](../architecture.md#锁与决定性读取)取得原操作及实际竞争对象。C1 使用 token、手机号、首次来源、部署额度和消息；R1 另涉及账户及注册凭据。锁后才判断原结果、时间与当前资格。

C1 接纳、发送许可准备和 R1 办理中的确定拒绝，发生在提交之前。确认回滚后返回原拒绝；回滚失败或超时则淘汰连接，结果同时保留原拒绝与实际收尾错误，HTTP 返回 dependency_unavailable。本阶段未提交，也没有获准继续的外呼。查询及提交等非拒绝故障仍走原操作恢复。

| 事实               | 关键约束                                                                   |
| ------------------ | -------------------------------------------------------------------------- |
| Challenge          | 原操作唯一；原 token 按密钥版本唯一，跨保留版本由稳定对象协调检查          |
| Message 与 Check   | 一份 Challenge 至多一个 Message；许可提交时 Message 与同 ID Check 完整配对 |
| 发送占用           | 每份 Message 至多一个，固定原工作身份，不可转让                            |
| Authentication     | 原操作唯一，原证明与输入不可改；结论与本次 Check 后果及适用凭据共同提交    |
| Session 与 Handoff | 来源、账户、原 token 摘要和固定期限配对；回读不新建或续期                  |

发送占用至少保留到 Message 合法删除，不能单独删除或修改。Message 进入 sent 或 unknown 必须已有发送占用；failed 可以来自发送前关闭或占用后的明确拒绝。原手机号、来源、许可时点及截止不可改。

### C1 阶段与外部调用

| 阶段         | 本地事实与判断                                                             | 继续边界                                                                  |
| ------------ | -------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 接纳校验     | 保存 Challenge、原证明、固定验证 ID、首次调用代次和截止                    | 确认提交后，原工作使用原 token 外呼                                       |
| 再次校验占用 | 前次调用已结束，错误可重试，原次数和截止仍允许；先保存下一代次，最多两次   | 沿用原验证 ID 和 token，重启不重置次数                                    |
| 校验结论     | 核对供应商成功、hostname、action、cData、时间和本次代次                    | 保存 passed、rejected、可重试等待或 inconclusive；结果丢失不能形成 passed |
| 发送许可     | 原通过证明仍可用，全部额度允许；共同保存 Message、Check 和截止             | 许可计数成立，新码成为最新；原 Message 已存在时只读取                     |
| 发送占用     | 原工作取得有界发送许可和实际开始间隔；码仍有效且至少剩余 60 秒             | 先确认唯一发送占用提交，再在事务外复查剩余时间并调用一次                  |
| 发送结论     | 核对发送占用与原工作；受理、明确拒绝、不确定分别形成 sent、failed、unknown | 可信结果仍在原工作时只重试本地回写，不能再次外呼                          |

原 token 不持久化。新进程在客户端提供原材料后按已保存阶段判断，不能因为 widget 重置或供应商 token 到期宣布原办理失败。完整恢复窗口内，已保存的通过、许可和结果各按原事实解释。

原工作保留已核对的 Siteverify 响应。在线写入失败后，最多使用独立恢复连接追加一次本地回写。恢复先在原操作协调内读取原阶段；阶段已提交时复用其原时点，否则用保留响应重新判断并保存。该恢复不重新调用 Siteverify，也不重置外呼次数或截止。通过证明仍须满足回写时的时间条件。

原发送许可存在但没有发送占用，原工作结束后归为未发送的 failed。已有发送占用但失去可信供应商结果时归为 unknown，即使实际调用可能尚未开始。两种情况均不允许新进程补发，也不退还持久额度。

PNVS 请求由原工作一次构建并验证，按[发送协议](../platform/pnvs.md)原样执行。OutId 不证明供应商去重。签名、等待和调用不延长 Check 截止。签名时间和剩余有效秒数从取得可信时间起累计实际耗时，此前的等待不再叠加到较晚的时间样本上。

原工作持有可信发送结果时，先在线保存；失败后使用独立恢复连接核对并保存同一结果。恢复仍受原操作协调约束；整个过程最多两次本地尝试，不重复外呼。两次均失败时保留两个安全错误来源，再按持久证据处理未知结果。原工作持有原码且已确认原发送占用，才可继续发送；发送前仍须通过归属、最新许可及剩余期限检查。

发送终态和孤立发送收尾均先取得持久可信时间，再写入结束时点。供应商调用期间发生回拨时关闭时间敏感接纳，保留尚未可靠收尾的 sending 与发送占用；不能用更早的原始时间强行形成终态。后续恢复仍遵守原执行结束边界。

### 时间与持久额度

下表规定 C1 与 R1 目标路径的工程初值。不能据此推断实际吞吐或供应商送达。额度和期限从服务端设置取得；已经保存的截止与许可时点不因设置调整而重算。

| 范围           | 初值与事务依据                                                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Turnstile 校验 | 首次占用时固定 10 秒总调用预算，最多两次调用；同一原 token 与固定验证身份在允许的重试中复用，不重置开始时点。                                                                        |
| 通过证明       | 供应商完成时点 `C` 与回写事务数据库时点 `T` 满足 `C <= T + 2 秒` 且 `T < min(C,T) + 300 秒`，才保存 `solved_at=C` 与 `finished_at=T`；准备许可时再次要求当前数据库时间早于同一截止。 |
| 验证码         | 许可提交时固定默认 5 分钟截止；有效码最多接受 5 次错误猜测。发送等待、回读和重启不延期。                                                                                             |
| 同手机号许可   | 最短间隔 60 秒；滚动 1 小时最多 5 份，滚动 24 小时最多 10 份。                                                                                                                       |
| 可信来源许可   | 滚动 60 秒最多 3 份；滚动 1 小时涉及最多 10 个不同手机号。首次 Challenge 固定统计来源，重试来源变化不重归属。                                                                        |
| 部署许可       | 滚动 24 小时最多 100 份；实际短信开始间隔至少 1 秒，最多 2 个发送工作在途。                                                                                                          |

所有持久发送额度都以 Message 的原许可时点、规范手机号和 Challenge 固定来源统计，计数不可重置。滚动窗口为 `(T - window, T]`，`T` 是取得对象协调后的数据库时间。额度读取失败不能当成零；许可和全部额度占用同事务提交，发送失败、未知或进程退出均不返还。旧码只在新 Message 与 Check 成功提交后失效。供应商返回的发送状态不决定 Check 的本地效力。

额度耗尽时，根据已提交许可计算下一次可接纳时点。计数窗口须等到足够多的记录退出；来源的不同手机号占用须等到该号码的最后一份许可退出，当前请求号码只占一个槽位。多个约束同时不足时取最晚时点，剩余秒数向上取整，由 HTTP 映射为 Retry-After。该时点不保证没有新竞争，也不延长原证明期限。

### R1 单事务与对象协调

C1 与 R1 共享受监督工作容量，原操作按用例分开；同一个 UUID 可以分别标识两个用例。可信网站 AppID 来自固定设置，网站短信来源固定使用 cookie。等待者取消后原工作继续收尾；并发重提在原工作结束后各自核对证明和输入，不共享已经验证的回执。

命中 Authentication 时先核对 secret，再比较用途、来源与规范输入。命中原结果后不重新验码。新办理依次协调原操作、已有 Account、手机号及 Check，之后才采样可信时间。等待跨过截止时按过期处理，不计错、不消费。共同结果复用锁后的时点，并核对消息归属、最新许可及手机号当前占用。

| 锁后结果                           | 共同提交                                                     | 原结果回读                             |
| ---------------------------------- | ------------------------------------------------------------ | -------------------------------------- |
| 消息不适用、过期、已消费或达到上限 | 不计错，不创建认证记录；明确回滚                             | verification_required，没有保存原结论  |
| 有效码但输入错误                   | Check 错误次数增加一次，保存原证明、输入和拒绝               | 同原操作不重复计错                     |
| 正确码且账户正常                   | 消费 Check、保存认证成功、独立 Session 和 Handoff            | 仅交付仍有效的同一会话                 |
| 正确码且账户暂停                   | 消费 Check、保存拒绝，不建立凭据                             | 后来解除暂停不改变原拒绝               |
| 正确码且无账户                     | 消费 Check、保存待注册结论、新凭据并替换同手机号旧未完成凭据 | 原凭据被替换、消费或到期后要求重新认证 |

锁后发现手机号的账户归属变化时，先核对原账户。原账户仍保留但已换号，则拒绝本次在途认证，不将换号中的旧认证转成待注册凭据。原账户已注销，或原来无账户而注册先提交时，继续按完整对象集合有界重查。从属的会话与凭据只能与本次认证在同一次办理中建立，不能用旧认证或旧会话重建已清理凭据。

Session token 为随机 32 字节，只保存摘要。网站短信会话默认 24 小时。注册 token 同为随机 32 字节，默认 10 分钟。Handoff 用 `encryption` 派生用途保护原会话 token，默认 10 分钟且不超过 Session 期限。

原结果交付先验证原证明与输入，再取得可信时间，核对当前账户、Session 撤销、来源与凭据、Handoff 期限。过期、撤销、暂停、注册凭据被替换或号码后来占用都不重签凭据；回拨关闭时间敏感接纳，不因时钟变早而重新交付已到期凭据。密码、引用或密钥故障保留技术错误，不能伪装成过期或错误验证码。

在线写入失败后，R1 使用独立恢复连接核对原结果。原结果不存在时保留原技术错误；存在时仍先验证证明和输入，再交付当前有效的原凭据。首次读取原结果与失败后的恢复读取，都保留已经完整核对的结论，后续只读收尾失败不覆盖已知结论。有效 Session、Registration 和持久的错码、暂停拒绝保持原结果。恢复确认可靠缺席时保留未提交结论。必要核对尚未完成的故障仍为 outcome_unknown。不可靠的原失败关闭接纳。

新事务中的原证明不匹配、输入不匹配或消息不适用，按[拒绝收尾](#c1-与-r1-的目标事务契约)返回。已提交的错码次数、暂停结论和成功凭据仍按原事实交付，不作为未提交拒绝处理。原失败可靠且拒绝收尾正常时，普通证明拒绝不增加 ERROR 日志。

重叠的同原操作请求先等待已有执行结束，再核对持久结果。没有保存 Authentication 时，由重复请求取得自己的执行并重新判断本次输入。不存在持久结果本身不是依赖故障；失效 Check 等明确但未持久化的拒绝仍返回 verification_required。

### 按需核对与清理

本用例按[未知提交协议](../architecture.md#未知提交)核对原阶段，其他无冲突操作继续。C1 的供应商结论与数据库结局分别解释；确定本地事务回滚也不允许重复已占用的发送。

| 候选                 | 本用例的保留条件                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------- |
| Challenge 与调用阶段 | 原恢复责任已结束，调用代次可解释，Message 与真实引用均已释放                              |
| Check 与 Message     | Check 到期及 Message 终态两者中较晚时点之后至少 24 小时；已退出统计窗口且无恢复或凭据引用 |
| Authentication       | 原结论终态后至少 24 小时；Check 消费、凭据和 Handoff 等引用均已释放                       |
| 发送占用             | 先解释 sending 的终态；随 Message 合法清理，不单独释放                                    |
| 最后原操作结果       | 所属恢复、防重、统计和引用责任全部结束后，与从属记录共同删除                              |

先清 Check，再清 Message，最后清无依赖的 Challenge。原结果仍承担恢复或防重时继续保留。清理按对象核对，不按批次整体推断成功；共同清理规则见[架构](../architecture.md#清理)。

会话须在到期或撤销后保留 24 小时，随后才可清理，见[撤销所有者的保留规则](revocation.md#撤销事实与约束)；交接和注册凭据按各自期限清理。Session 删除不带走属于 Account 的撤销。新 R1 替换未到期注册凭据时，同手机号的新凭据必须同时形成。清理不能提前释放发送占用、额度或原操作。清理进行时另一合法认证替换 Registration，不构成事实损坏；已经消失的所有者仍留下从属记录才属于矛盾。

### C1 保留与清理

C1 短期记录的回收范围包括遗留阶段核对、到期删除、入口响应和停止。没有永久退役记录。

#### 保留与阶段核对

没有 Message 的 Challenge，至少保留到调用截止与结论较晚时点的 24 小时后。passed 还必须经过原证明的发送有效期。有 Message 时，整组记录必须同时满足既有 Message、Check 保留条件。清理使用事务内可信时间，回拨关闭时间敏感接纳。

候选的年龄只用于筛选。清理先取得与请求共用的原操作执行名额；已有工作时跳过，后续轮次再检查。取得名额后在原操作及所属对象协调下重新读取事实，整个核对、提交恢复与删除过程保留执行名额，重复请求等待结束后独立检查仍保留的原结果。

确认旧执行结束后，遗留 calling 和已过截止的 retryable 才能转为 inconclusive。遗留 sending 按已保存的发送占用解释：没有占用时为 failed，有占用时为 unknown。只保存本地结论，不调用供应商。结论时点使用本次可信时间，保留期从相应结论重新计算。本轮刚解释的记录继续保留。供应商 unknown 是已保存的发送终态，与尚未查明的数据库提交结局不同。后者在完成原操作核对前保留全部证据；事实矛盾时停止相关接纳。

#### 删除保护与标识复用

记录保留期间，原 Operation-Id 仍绑定原 token、手机号与结果。整组删除后不保留标识墓碑，也不再承诺原结果回读或固定的 404。相同 UUID 再次请求时按新申请处理，重新验证人机证明和额度；有效的新证明可建立新的 Challenge。旧 token 不继承原通过结论，失效证明不能形成发送许可。客户端应在[恢复材料期限](../client/recovery.md#恢复材料)内核对原结果，期满停止自动重试；明确再次申请时使用新标识和新证明。

每次删除只针对一个原操作的完整记录组，依次删除所属 Check 或 Confirmation、发送占用、Message 与 Challenge；没有 Message 时直接删除符合条件的 Challenge。校验与发送占用只能随 Message 一同删除，Message 只能随原 Challenge 一同删除；不能单独释放发送占用，也不能留下部分记录组。尚有错误尝试引用的 Confirmation 继续保留，依赖顺序见[换号清理](mobile.md#事实与约束)。新鲜、阶段未结束或仍有 Message 引用的 Challenge 不能删除。删除提交后同一 Operation-Id 可重新使用，删除回滚则原记录继续占用。可信时间早于已保存时间时拒绝清理。

#### 顺序、运行与恢复

清理每轮最多取 128 个候选，以原 Operation-Id 为稳定分页键，逐项执行；轮次串行，结束后间隔 60 秒，不积压新轮次。清理与请求共用原操作互斥和固定容量，忙时跳过并推进分页，读到尾部后从起点重访。分页位置只在进程内保存，不证明记录已删除，也不参与结果恢复判断。停止时不再选取新候选，等待当前清理及其恢复、HTTP 读取和 C1 请求全部结束。

清理在实际结束处记录一次最终技术失败，携带原操作标识及脱敏原因。事实或时间等致命故障关闭接纳并上报监督；停止通知不能把该错误改写为正常关闭。可重试的单项技术故障保留记录后继续本轮。

删除结局未知时，按原实体回读：原 Challenge、Message、校验和发送占用全部消失才认定删除完成；完整原组且阶段未变表示未提交；相同 Operation-Id 对应的新实体不属于原组，不被删除或修改；原组残缺或阶段矛盾属于事实故障。遗留阶段回写按原对象和原阶段恢复，不能通过重跑供应商取得结论。完整核对后的已知结论不因只读收尾失败而改变；必要事实或可信时间尚未读全时，结果仍为未知。

## 验收

以下为 C1 与 R1 的累计目标。各项随首个真实消费者验收，阶段不等于一个实施切片；不得延后当前结果所需的保护，也不因矩阵完整而一次实施整条路径。

使用隔离 PostgreSQL 和供应商替身，观察真实调用次数与数据库后果。覆盖各调用占用提交前后退出、可信外部结果仅重试本地回写、token 跨操作及跨键版本竞争、原材料恢复、发送间隔和额度不返还。人机校验覆盖有限重试、次数与截止耗尽、异常响应、孤立调用收尾和重启回读；短信覆盖四类供应商结局、发送前期限不足、新许可取代旧码、发送容量与相邻间隔、两次本地回写失败及重启收尾，且每份许可至多外呼一次。

覆盖同码两个 R1、新 C1 与旧 R1、五次错误、原拒绝回读、暂停账户正确码消费、注册凭据替换及会话原交接。提交故障验证旧后端迟到提交、原操作核对和无关事务继续；记录调用方故障与 PostgreSQL 线协议故障的证据区别。R1 原结果在只读收尾故障后仍保持原 cookie、注册 token 和期限，错码只计一次，暂停仍返回原拒绝。

清理验证新鲜记录、在途工作、未解释阶段、窗口内额度及真实引用都阻止删除；到期整组删除与无 Message 的清理成立，单独删除发送占用或提前删除被拒绝；原请求、原结果回读和清理竞争，删除前回滚、提交响应丢失和迟到提交分别得到正确结论；超过一页的候选分页、跳过后重访和重启从起点扫描不误删新实体；清空历史后同一操作标识配合新的人机证明可再次申请，许可顺序继续递增。

补充验证在线池耗尽后的同结果回写与 R1 恢复、Check 锁等待跨越截止、消息终态回写期间时钟回拨。可信时间覆盖业务回滚不擦除高水位、后台持久化未知时关闭接纳，以及重启与原凭据读取拒绝回拨。监听或任务异常后，验证已接纳外呼收尾、驱动结束和失败退出；全部场景只使用隔离材料。共同停止、构造旁路和日志验收见[架构](../architecture.md#隔离验收)。
