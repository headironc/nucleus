# 会话撤销与退出目标设计

状态：目标设计，尚未实施。本文拥有逐会话撤销事实，以及退出当前会话、退出全部设备和原退出结果读取。账户暂停、换号和微信解绑也使用同一撤销事实，但各自拥有办理资格与其他业务后果。共用写入屏障与提交未知核对见 [架构恢复协议](../architecture.md#原操作与恢复)。

## 用例、范围与结果

退出只能由当前有效会话的本人发起。`DELETE /sessions/current` 选中本次认证的会话；`DELETE /sessions` 选中该账户在退出事务内尚未撤销的全部会话，包含网站和小程序会话，以及已到期但仍保留的行。两个入口使用各自的客户端 Operation-Id，无正文，客户端不能指定目标账户。退出保留账户、实名、当前微信绑定和领域授权。已签发的头像图片链接依自身期限继续有效。

退出范围由事务取得对象协调后的会话集合固定。新登录先提交、全部退出后提交时，新会话属于撤销范围；退出先提交、新登录后提交时，新会话有效。退出不安排后台扫描后来会话。原退出完成只描述当次撤销的集合，不因后来登录、清理或绑定变化重选范围。

| 入口                                 | 当前身份与结果                                                                                                                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DELETE /sessions/current`           | 当前会话有效时执行；成功返回 200 和 `completion: { id, count, revokedAt }`，`id` 为原 Operation-Id。                                                                            |
| `DELETE /sessions`                   | 当前会话有效时执行；成功返回 200 和同形完成，`count` 为本次撤销的会话数。                                                                                                       |
| `GET /revocations?operation_id={id}` | 由同账户的当前有效会话读取原退出；返回 200、`count` 及按会话 ID 排序的完整 `revocations: [{ id, revokedAt }]`，不分页。没有本账户可读的原退出时返回空列表。只读查询不执行退出。 |

网站使用 Session-Id 选中原 cookie 认证并遵守同源条件，小程序使用 Bearer。两条 DELETE 采用本次请求实际认证的会话；原会话被撤销后，以它重发 DELETE 返回 `authentication_invalid`，不能从这个 401 推断原退出是否提交。用户取得同账户的新会话后只能使用 GET 核对原操作；以新会话和旧 Operation-Id 重发 DELETE 不构成新退出，也不返回原完成。新的退出动作须用新 Operation-Id。GET 不要求原会话或原会话行仍存在。GET 请求头中的 Operation-Id 只标识本次查询，查询参数才是原退出标识；响应不回显本次请求标识。

## 撤销事实与约束

`identity.revocations` 每行证明一条会话已经撤销，同时保存撤销来源。退出、微信解绑、账户暂停及换号分别使用 `logout`、`unbind`、`suspension`、`transfer` 模式；四种模式都沿用各自原请求的非空 Operation-Id。账户注销直接删除会话和账户，不写撤销记录。Session 行建立后不改写撤销状态，当前会话资格由 Session、期限、当前账户及是否存在 Revocation 共同判断。

| 字段           | 含义与约束                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------------- |
| `id`           | 被撤销的 Session ID，也是主键；一条会话至多撤销一次。它是匹配值，不设阻止到期 Session 清理的外键。 |
| `account_id`   | 原 Session 所属 Account 的真实外键；Session 行清理后仍界定结果读取和注销删除。                     |
| `mode`         | 封闭的撤销来源。退出只读写 `logout`。                                                              |
| `operation_id` | 发起本次撤销的原客户端操作 ID，非空；同一退出集合共用它。                                          |
| `revoked_at`   | 本次业务事务的数据库时间；同一退出集合共用它。                                                     |

五列全部非空。提交时检查新 Revocation 对应的 Session 在本事务内确实存在且属于 `account_id`；不能仅靠无 Session 外键的列形状推断。相同 `(mode, operation_id)` 的全部行必须属于同一账户并使用同一 `revoked_at`。同一个操作标识在其他账户已有退出集合时，本次不得接纳为新的退出。撤销集合自身承担原退出完成，不另设同义 Request 或 Receipt。原操作、模式和账户定位结果，`id` 保证同一 Session 不被重复撤销；按 `(mode, operation_id, account_id)` 支持原集合读取，按账户支持注销删除。查询和索引的实际组合需在实施时验证执行计划。

Revocation 无普通 UPDATE。运行身份只拥有受控 SELECT、INSERT 和账户注销所需的 DELETE。Session 仅可按其生命周期受控清理；Handoff 在撤销事务中整行删除。撤销事实随 Account 保留，账户注销事务在删除 Account 前删除；Session 失效后默认保留 24 小时，且无短期引用时方可清理。失效时刻取到期时刻或撤销时刻。删掉 Session 不删除 Revocation，也不把旧 Operation-Id 变成新操作。

## 事务与并发

当前退出与全部退出由所选用例区分。业务事务按[共同锁顺序](../architecture.md#锁与决定性读取)协调原操作、Account 和 Session。锁后重查本次认证的会话、来源、Account 当前资格、数据库时间和原退出集合。第一次只读查到的候选不能直接决定撤销范围。事务以 `READ COMMITTED` 新语句读取锁后的决定性事实；新增竞争键使事务回滚后按完整集合有界重试。

原 Operation-Id 命中 `logout` 集合时，核对所属账户和当次认证会话。当前认证会话不在原集合中，拒绝用该 DELETE 读取或扩展原完成；同账户用户以 GET 读取。命中其他账户的集合返回 409 `request_mismatch`，不返回对方内容。无原集合时确定当前或全部会话集合；为每条尚未撤销的 Session 插入同操作、同账户、同时间的 Revocation，并删除这些 Session 的 Handoff。两项在同一业务事务提交。当前认证会话有效，因此新办理至少撤销一条会话。任何插入、交接删除或完整性检查失败都使本次业务事务整体回滚。

业务事务在提交前按本次退出用例核对范围：当前退出恰好产生原认证会话的一条撤销；全部退出提交时，该账户没有尚未撤销的 Session。检查核对同一账户与时间的撤销集合，以及对应 Handoff 已删除。会话建立、解绑、暂停、换号、注销及 Handoff 清理只要改变上述判断，都须遵守相同账户与会话对象协调。已经撤销的 Session 不重复插入 Revocation。退出与绑定的供应商外呼可交错，但绑定最终接纳时须重新核对原本人会话；退出先提交后，旧绑定不能借后来新会话成功。成功退出的响应在撤销本次认证会话后直接形成，不重新认证而误报 401。

## 响应丢失与读取

退出没有事务外供应商调用。提交未知按[阶段恢复依据](../architecture.md#原操作与恢复)核对原撤销集合及适用 Handoff 删除后果。撤销范围由提交时检查保证，不按后来变化的 Session 集合重算。可靠确认未提交后，原请求仍须具有有效的原会话。原撤销事实因注销删除后，查无记录不能解释为回滚。

GET 在一个决定性语句快照内重查当前会话、可信来源、Account 资格与适用微信关联，再读取本账户的 `logout` 集合。其他账户的同 Operation-Id 与不存在的集合都返回空列表，不泄露归属，也不声称旧事务已回滚。已知相关执行仍处未知提交时先等待核对；无法可靠读取时返回技术错误，不伪造空列表。GET 不删除 cookie、Handoff 或 Session，不启动写入工作。

网站首次退出成功响应只清理由本次认证指向的准确 cookie。浏览器也只在本地仍选中相同 Session ID 与修订时清空选择，迟到响应不得清除后来登录的会话或新登录尝试。原完成查询不清理当前 cookie。服务器上的撤销在提交时生效，不依赖其他设备收到响应。

## 验收

用真实数据库事务控制以下交错：当前退出与全部退出的准确范围；同账户新登录先于或晚于全部退出提交；同一 Session 的两笔撤销竞争；退出与绑定结果竞争；任一 Revocation 或 Handoff 删除失败的整体回滚；提交回包丢失、旧驱动晚提交及普通重启后的按需核对；原会话已撤销时 DELETE 的 401 与同账户新会话 GET 的原集合；跨账户和不存在操作的空列表及零写入；迟到网站响应不清除后来选中的会话。数据库约束测试还须证明不存在或属于他账户的 Session 不能被写成 Revocation，同一操作的账户和时间不能分裂。
