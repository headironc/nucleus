# 人员与实名版本目标设计

状态：目标设计，尚未实施。Person 固定一名人员的身份归属，Revision 保存该人员一次完整的姓名与居民身份证号。首次版本由[正式注册](registration.md)建立，后续版本只由[实名更正](correction.md)追加；当前指针由 Person 持有。两个事实与账户、会话和业务历史的关系按所属用例判定。Person 另保存 last_sequence，统一分配该人员需要组合解释的事实顺序；规则见[个人顺序](../architecture.md#时间与个人顺序)。

## 构造与关系

身份证号值通过 `IdNumber::suffix` 提供最后四个字符。HTTP 的脱敏字段形状与读取权限由[当前身份](current.md#本人账户投影)及所属用例规定，不因该值方法存在而授予读取权。

新建人员和首份实名版本使用同一组预先确定的人员 ID 与版本 ID。首份版本、Person 当前指针、Account 及注册回执必须在一笔成功事务中闭合真实同人关系；不以临时空指针、后续补写或相同 UUID 的约定替代约束。后续更正追加新版本并共同推进当前指针与当前身份证号占用值，既有版本不可修改或普通删除。注销保留 Person、实名版本和必要历史，注销后重新注册建立新的 Person。

姓名和身份证号先按[正式注册的稳定值规则](registration.md#业务边界与不变量)规范化；仅新注册检查可信办理日。历史版本解密、原输入匹配和更正使用同一稳定值规则，不用今天的日期重新判断原值。完整明文只存在于受控输入和必要的解密短期缓冲；普通响应按所属读取权限投影，不能因为持有版本 ID 就读取完整资料。

## 封装与读取

实名版本分别封装姓名与身份证号，两份封装各使用新的随机 nonce、`encryption` 用途密钥和包含本版本 ID 及字段名的 AAD；一个字段失败不得产生部分版本。密文记录保留实际 key ID，解密时核对封装结构、保留密钥的用途、版本 ID、字段名及认证标签。缺失旧键或用途不符不得退回活动键。解密后的 UTF-8 明文必须已经是稳定规范形式；若重新构造所得值不同，报告该字段的完整性故障，不修剪或改写历史。技术重新加密保持业务明文、版本 ID 和人员归属，不形成新的实名版本。

按人员 ID 和版本 ID 读取历史版本时，两者必须同时匹配；查询真正无行与数据库或解码失败分开。注册原结果使用注册时的版本，当前本人读取使用决定性快照中的当前版本；后来的更正不能改变旧回执或业务记录所引用的版本。版本行的结构解码不等于解密成功，也不等于当前本人有权读取。当前读取的权限与投影见[当前身份](current.md)，历史读取见[实名更正](correction.md)。

## 验收

验证首版和 Person 指针的同事务闭合、版本必须属于原人员、单字段封装失败回滚、两字段不同 nonce 与 AAD、旧键读取、错版本或错字段密文拒绝、非规范历史明文拒绝，以及原版本和当前版本分别读取。验证注销保留历史、更正不修改旧版本，且查询失败不伪装成查无行。
