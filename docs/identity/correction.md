# 实名更正目标设计

状态：目标设计，尚未实施。本文拥有实名更正的办理资格、永久事实、历史读取及“系统管理员”运维更正。写入屏障和未知提交核对见 [架构恢复协议](../architecture.md#原操作与恢复)；姓名与身份证号的规范值沿用[正式注册](registration.md)。

## 用例与不变量

当前正常账户的办理人，须有包含 `institution.corrections` 的当前机构角色，且机构等级严格高于目标的当前机构等级；不能经管理入口更正自己。办理人不需要 Workforce 授权，目标的 Workforce 状态也不影响资格。目标没有当前账户时没有当前机构等级，具备更正权的管理者可以按人员 ID 更正。目标人员身份不变，也不因此建立账户或转移其他领域事实。

姓名和身份证号都作为完整的新值提交，只变一项也须提交另一项。姓名去除首尾空白并作 NFC 规范化，限 1 至 64 个 Unicode 标量且无控制字符。身份证号须为 18 位居民身份证号码，出生日期真实、MOD 11-2 校验位有效，末位小写 `x` 规范为 `X`；更正使用稳定值规则，不因本次办理日期重新判断出生日期。更正后的两项共同生效或共同拒绝；与当前两项均相同的新办理返回 409 `state_conflict`，新身份证号被其他未注销账户占用时返回 409 `id_number_taken`。不要求人工理由或审批。

更正不改变手机号、政治面貌、账户状态、会话、角色、授权及已保存的业务历史。新姓名供工牌管理页与原申请的固定姓名比较并显示差异；更正不自动转换或结束申请，也不改写已经确认的打印内容。只改身份证号不产生新的工牌内容后果。原注册结果仍以注册时实名版本核对和恢复。

## HTTP 入口与目标确认

| 入口                                | 输入及读取或写入结果                                                                                                                               |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /corrections/candidates`      | 以正文中的规范手机号精确定位有当前账户的目标；返回完整姓名和身份证号及固定目标。                                                                   |
| `GET /corrections/{person_id}`      | 按已知人员 ID 定位目标，包括没有当前账户的人员；返回同一候选结构。                                                                                 |
| `POST /corrections`                 | 正文必填 `target: { personId, revisionId }`、`name`、`idNumber`，另携客户端 Operation-Id；新成功返回 201 及更正 ID、生效时刻，原成功重放返回 200。 |
| `GET /persons/{id}/corrections`     | 管理者读取指定人员的永久更正历史。                                                                                                                 |
| `GET /accounts/current/corrections` | 当前本人读取自己的永久更正历史。                                                                                                                   |

两个候选入口先验证当前会话及 `institution.corrections`，再按当前等级及非本人条件过滤；无职责返回 403，目标不存在或不在范围内返回 404。数据库或解密失败不能伪装为 404。候选的 `target` 只含人员 ID 和读取时的当前实名版本 ID，不含账户 ID 或手机号；完整姓名和身份证号与目标版本来自同一读取快照。候选只供人工核实，提交时必须重查权限、目标人员、当前版本和占用。旧版本确认不能覆盖其间发生的更正。

写入正文拒绝未知字段，当前会话与 Operation-Id 按共同 HTTP 规则验证。新办理的当前权限、目标确认及号码占用在取得适用对象协调后决定。原 Operation-Id 已有完成时，先读取原更正，核对办理人所属人员、目标人员、推导出的原版本及新版本的规范姓名和身份证号；匹配才返回原完成。当前版本、角色或号码占用后来变化，不改写原成功，也不把它当新办理。标识相同而输入不同返回 409 `request_mismatch`。原标识不单独授予已失权办理人读取资格。

## 永久事实与共同事务

每次更正建立新的实名 Revision 及只追加的 Correction，两者共享 UUID ID。Correction 保存目标 `person_id`、办理人当时实名版本 `operator_id`、`corrected_at`、目标人员的成功事实顺序号及唯一非空 `operation_id`。更正与新版本须真实引用同一人员；同一人员的顺序号唯一。原版本由同人前一条 Correction 的新版本推导；首次更正的原版本为该人员唯一首版。不再单独复制原值、原版本 ID、输入摘要或明文。原版本、新版本和办理人版本永久保留，注销不删除。

业务事务按[共同锁顺序](../architecture.md#锁与决定性读取)协调原操作、办理人与目标人员、当前账户及新身份证号占用。锁后先查原完成，再复查认证、权限、目标当前版本和号码占用。新 Revision、Correction、Person 当前版本指向、适用 Account 的当前身份证号查找值在同一提交中成立。只改姓名时不重算身份证号查找值；目标已无当前账户时不创建或更新 Account。唯一约束最终裁决当前身份证号占用；其他数据库或解密错误不映射成业务冲突。

持久约束保证已有人员的新实名版本必须由同 ID 的 Correction 创建，Person 当前版本只能推进到本次新建的更正版本，当前账户的身份证号查找值与当前版本一致。运行身份不能更新或普通删除 Correction、Revision 等永久历史。更正失败不留下孤立版本、变化的当前指针或部分身份资料。

提交未知按[阶段恢复依据](../architecture.md#原操作与恢复)核对原 Correction 及其共同提交的实名版本与指向。未提交时按当前资格和原输入判断能否继续；后续更正不能覆盖原完成。Correction 是永久结果，不能删除原更正来释放 Operation-Id。

## 历史读取

两个列表入口使用 `page` 和 `size`；省略时分别为 1 和 20，`page` 从 1 开始，`size` 为 1 至 100，显式无效值返回 400 `invalid_input`。每页在同一快照中核对当前权限、计算 `count` 并读取本页记录；按同一人员实际更正成功顺序倒序，不按 UUID 推断先后。每条含更正 ID、`before`、`after`、`correctedAt`。无记录返回 200、`count: 0` 和空数组；越界页返回 200、原总数和空数组。跨页不保证同一快照。

管理入口要求办理人当前有 `institution.corrections` 且机构等级严格高于对象；目标为本人或等级不低于办理人时按 404 处理，无职责为 403。目标没有当前账户时不比较等级，因此任一具备更正权的管理者均可读取其完整历史。这使“系统管理员”等目标注销后的历史可读范围大于在职时，是本用例的既定规则。曾经经办、持有相同证件号码或注销后再注册都不产生读取权。

管理投影中的前后姓名、身份证号均为完整值，另返回办理人的 `personId` 和更正当时姓名。本人入口只要求当前账户代表该人员，不比较等级；前后姓名完整，身份证号仅为 `idNumber: { suffix }`，不返回办理人，也不提供本人读取完整历史身份证号的入口。运维更正沿用本人与管理投影。人员不存在或不在管理范围返回 404；依赖失败不能伪装成空列表。响应与错误禁止缓存，日志不记录完整实名资料。

## “系统管理员”的运维更正

在职“系统管理员”的机构等级为 1000，没有等级更高的管理者，HTTP 管理入口对其返回 404。其实名资料由停机工具 `deployment operate-access correct` 更正，只接受当前机构角色仍为“系统管理员”的目标；此运维动作允许操作者更正自己。它不成为普通人员的备用更正入口。共同停机和计划协议见[停机运维协议](../operations/maintenance.md)。

`inspect --person <id> --revision <id> --values-file <path> --plan-out <path>` 的值文件含完整 `name` 和 `id_number`。动作检查目标角色、当前实名版本、规范输入、实际变化和当前号码占用。计划绑定操作者账户与版本、目标人员与期望版本、两项变化标志和值文件规范摘要；文件创建、确认码及输出遵守共同协议。

`apply --plan <path>` 锁后先按计划 Operation-Id 查原 Correction；已有原完成时核对原办理人、目标、原版本及新规范值，匹配才报告结果。未命中才重查当前前提和操作者绑定，同事务写入新 Revision、Correction、当前指针及适用账户查找值。当前状态或材料变化时拒绝，要求重新 inspect。

运维更正不改变手机号、政治面貌、会话、角色、授权或已确认工牌内容。未知提交、同计划重试及 journal 输出由[停机运维协议](../operations/maintenance.md)规定。

## 验收边界

以真实事务交错验证同一原操作并发重试、输入不匹配、权限或目标版本变化、同证件号码竞争、只改姓名、无账户人员、系统管理员运维自我更正、响应丢失及未知提交。核对新版本、当前指向、当前占用、更正事实共同提交；旧注册及旧业务记录保持原版本。历史读取分别验证管理与本人投影、注销前后范围、当时办理人、空页、失权及依赖失败；运维验证停机证明、计划材料绑定、锁后原结果首读与同计划恢复。
