# 备份与恢复

状态：上线前必须交付的目标，尚未实施或演练。本文拥有备份内容、执行、保留和恢复限制。适用约 1500 人的单实例部署，接受人工恢复和上次成功备份之后的数据损失。

## 备份内容

每天北京时间夜间备份一次。一份完整备份关联以下材料。

| 材料       | 内容                                                       |
| ---------- | ---------------------------------------------------------- |
| 数据库     | 完整业务库的 pg_dump 自定义格式导出，包含审计              |
| 持久文件   | 照片、工牌成品、背景、字体及其他实际引用的文件             |
| 程序与配置 | 对应程序制品或准确版本、网站版本、配置与数据库角色重建材料 |
| 解密材料   | 仍被数据引用的应用密钥及恢复所需凭据，独立受控保管         |

pg_dump 只备份单个数据库，不包含集群级角色或应用外部文件。角色通过已验证的部署材料重建，或保存所需全局对象。数据库导出本身不证明业务可恢复。[PostgreSQL 说明](https://www.postgresql.org/docs/18/backup-dump.html)

## 执行与保存

使用系统定时任务调用明确的备份流程，不建立应用内任务平台。

1. 停止应用及其他业务写入者，确认已停止。PostgreSQL 保持运行。
2. 导出数据库，复制文件与对应配置到本次独立备份目录。逐项检查结果；失败目录不标记完成。
3. 本地副本完成或备份失败后，都尝试恢复应用服务并检查就绪。停止失败时不能宣称取得一致备份。
4. 服务恢复后，加密本次副本并传到独立机器或备份盘。核对完整性及实际保存结果，成功才标记备份完成。
5. 新备份完成后按规则清理旧副本。失败不覆盖或删除上一份成功备份。

停应用是为了让数据库与本地文件对应。pg_dump 本身支持在线一致快照，不要求停止 PostgreSQL。停机时间由实际数据量和磁盘性能决定，通过演练测量。

起步保留最近 7 份每日备份和最近 4 份每周备份。每周副本从成功每日副本中选取。异机副本不与应用数据共用故障磁盘；同机副本只辅助误操作恢复。备份加密密钥另行安全保管，不能只放在原机器或用它自己加密的备份包。

备份、传输、清理及服务恢复失败均留下安全诊断并通知维护者。实施时绑定目的地、调度时刻和通知渠道；设计确认不授权向任意外部位置上传单位数据。

## 恢复与限制

在空恢复环境准备对应程序、角色和密钥，用 pg_restore 恢复数据库，再还原对应文件与配置。恢复失败不开放业务。先在隔离环境确认，再按实际生产恢复授权切换。

上线前完整演练一次，以后每季度抽查恢复。检查登录、权限、申请快照、审计，以及照片和工牌实际可打开。校验和或导出成功不代替恢复演练。演练默认禁止真实短信外呼。

每日成功备份时，损失窗口约为一天；连续失败时窗口增长。恢复耗时以演练结果说明。不提供自动切换、持续复制或任意时间点恢复。恢复点之后已实际发放的工牌由维护者核对并受控补记，不伪造原审批或原操作时间。

恢复数据库也会恢复旧会话和短期认证材料。重新开放前，使恢复出的旧登录会话、验证码和注册凭据失效，要求重新认证；保留短信去重及额度依据，不重新执行旧发送请求。这一步随恢复工具和演练交付，不能任意删表。

## 验收

验证数据库和文件来自同一停写窗口，角色和密钥足以恢复。验证导出、复制、传输、磁盘不足及启动失败均可见，旧成功副本仍可用。恢复后核对权限、快照、审计、文件与短期认证失效，记录实际耗时和恢复点。真实数据上线前完成主机验收。
