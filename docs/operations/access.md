# Access 系统初始化与管理员指派

本文拥有初始化及指派的资格、输入、结果与原事实。两个动作遵守[停机运维协议](maintenance.md)。系统管理员实名更正使用同一 `deployment admin correct` 入口与执行器，业务规则归[系统管理员的停机实名更正](../identity/correction.md#系统管理员的运维更正)。更正不改变本文的初始化与指派契约。

## 运维身份与命令

命令为 `deployment admin initialize --input FILE --operation UUID [--dry-run]` 与 `deployment admin appoint --input FILE --operation UUID [--dry-run]`，没有 HTTP 运维入口。`--operation` 必填，新办理使用新的 UUID，核对原结果时沿用原 UUID 与原输入。`--dry-run` 预检后回滚业务事务，不保存业务变更或新的完成记录。实例代次与可信时间仍按共同协议推进。

输入文件仅运维操作系统用户可读，文件权限与读取边界见[维护协议](maintenance.md)。文件用于归属和追责，不是独立的防冒充凭据。命令以应用运行身份连接数据库，装载运行凭据、密钥材料与网站 AppId。配置来源见[部署设置](../settings.md)与[凭据文件](../platform/credentials.md)。命令持有实例锁，执行与在线相同的完整启动核验，再通过同一应用内核办理。初始化使用引导主体，指派使用系统主体。

| 动作       | 输入文件字段                                              |
| ---------- | --------------------------------------------------------- |
| initialize | `mobile`、`name`、`idNumber`                              |
| appoint    | `operator.mobile`、`accountId`、`revisionId`、`selection` |

输入拒绝未知字段。手机号、姓名与身份证号沿各自的受控构造规则校验，秘密临时缓冲清零。命令行只传操作标识与文件路径，结果按[共同协议](maintenance.md)输出脱敏摘要。

## 初始化

initialize 在没有账户与角色的业务库办理。操作者提交本人完整实名资料。出生日期按数据库可信时间对应的 Asia/Shanghai 日期校验。新办理在事务锁内重查空库前提；任一步失败整笔回滚。

初始化建立 Person、首个实名 Revision、Account 和默认头像。机构角色为“普通账户”和“系统管理员”。Workforce 角色为“普通成员”和“管理员”。四个角色及完整创建历史与身份事实共同提交。操作者的首条机构指派为“系统管理员”，同时建立已封印的 Holder。以上事实在同一事务保存。全部办理人版本为本次首个实名版本，原操作标识取 `--operation`。

首条指派固定所选角色的创建版本，Holder 自有序号从 1 开始。Person 首次建立也占自身顺序的首位；后续机构指派只推进 Holder。系统角色的等级、权限全集和当前用权见[角色与指派](../access/roles.md)。

初始化完成后，操作者通过普通短信认证登录。工具只建立正式账户，不签发 Session。相同原输入重跑返回原完成。库内已有账户或角色时，新初始化返回 `state_conflict`，不复用旧人员或覆盖原事实。

## 指派与换下

appoint 新办理时，用 `operator.mobile` 精确定位操作者当前正常账户，取其当前实名版本。找不到、已暂停或已注销均拒绝。目标必须是已有正式账户，当前实名版本与 `revisionId` 相同。工具以 `accountId` 和实名版本固定目标，不为不存在的账户预授权。

`selection` 为下列两个封闭形状之一：

| 输入                                  | 结果                                           |
| ------------------------------------- | ---------------------------------------------- |
| `{"action":"grant"}`                  | 将目标的机构角色更换为“系统管理员”             |
| `{"action":"revoke","roleId":"UUID"}` | 将目标从“系统管理员”换为明确指定的现存机构角色 |

换下所选角色不能是“系统管理员”。目标已是“系统管理员”时，grant 返回 `state_conflict`。目标已不是“系统管理员”时，revoke 返回 `state_conflict`。两者均不写空指派。目标实名版本变化返回 `target_changed`。目标可以是本次操作者，停机指派允许办理本人。

成功在同一事务追加永久指派并前移 Holder。指派固定前驱、所选角色的具体变更版本、双方实名版本和原操作。指派只推进 Holder 自有序号，不推进个人顺序。角色后续修改不重写已经固定的选择。当前权限仍取 Holder 所指角色的当前有效状态。规则归[角色与指派](../access/roles.md)。

### appoint 当前实现

`deployment admin appoint` 以同一命令完成预检与执行，`--dry-run` 只预检。目标及所选角色均在锁内按当前事实判断。初始化、在线指派和系统指派使用共同的 Holder 状态迁移、封印及完成记录机制。

## 原操作与恢复

完成记录绑定原操作家族、动作、目标、规范输入和真实办理人。同一 UUID 与输入重跑只返回原结果，不追加第二条指派；异输入返回 `request_mismatch`。初始化与机构指派是不同家族，允许复用 UUID。原完成依赖永久事实，换号、注销及后续角色变化保留原结果与固定身份。

提交结局不明时，沿[共同恢复协议](maintenance.md#共同屏障与未知提交)核对原操作。使用相同 UUID 与输入重跑，不另建新操作来推断原提交失败。命令收尾或结果输出失败保留原业务结论。

注销为 Holder 追加由原注销驱动的投影，将 Holder 前移为永久墓碑。墓碑与原指派继续保留，历史读取和原操作回放按固定版本解释。Grant 与 Identity 的其余状态迁移仍沿所属能力现有协议。规则见[授权生命周期](../access/grants.md)与[注销](../identity/cancellation.md)。

## 验收

隔离验收核对完整身份、默认头像与四角色历史。首条指派、Holder 及原完成必须共同成立。初始化后没有 Session，个人顺序保持 0；预检不写业务事实。验收覆盖输入变化、办理日、空库重查和运行身份权限。还应核对本人指派、空指派拒绝及所选角色限制。

原操作验收要求先独立读取持久后果，再验证相同输入重放和异输入拒绝。提交故障覆盖回执丢失、确认回滚和未知后晚提交。首次原结果读取与收尾失败也按共同恢复边界核对。重启核验覆盖固定角色版本、Holder 自有序号、注销投影墓碑和完整完成记录。隔离证据不代替真实部署演练。
