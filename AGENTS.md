# Repository Instructions

## Working in This Repository

- Apply [design and implementation boundaries](docs/engineering/delivery.md#设计与实施边界) and [development collaboration and handoff](docs/engineering/delivery.md#开发协作与交接) as mandatory instructions for implementation work, including the implementation-slice rules. Documentation changes follow [the documentation maintenance rules](docs/README.md#文档维护).
- Before implementation, documentation edits, investigation, or review, read [model selection and collaboration](docs/engineering/models.md). It owns model selection, escalation, delegation, result acceptance, and continuity across model or session changes. Apply it within the task's existing authorization.
- Inspect the current source and working tree to establish delivered behavior. Preserve unrelated edits, including unfinished work. Do not restore removed implementations or use historical layouts as the target design.
- Project rules and their required references live in this repository and take precedence over personal preferences within their declared scope. If a required source is unavailable, report the gap and pause only work that depends on it.

## Required Reading by Task

- Before domain decisions, read [the capability overview](docs/overview.md), the architecture's [application kernel](docs/architecture.md#应用内核) and [threat model](docs/architecture.md#威胁模型), then the affected owner documents listed in [the documentation index](docs/README.md). Read other architecture sections when the change touches them; the architecture owns shared transaction, construction, recovery and runtime targets. Scheduling work also requires [Schedule's authority and reading order](docs/engineering/capacity.md#schedule-接入依据).
- Before designing, changing or reviewing Rust, read the applicable [Rust rules](docs/engineering/rust.md). For SQL or database behavior, read the applicable [SQL rules](docs/engineering/sql.md); before changing migrations, also read [migration rules](docs/engineering/sql.md#migrations).
- Before running database commands, follow [database operation safety](docs/database.md#操作安全).
- Before selecting, implementing or reviewing repository development tools, follow [tool selection](docs/engineering/verification.md#工具选型).
- Before designing, changing or reviewing client pages, follow [user-facing copy](docs/client/pages.md#用户可见文案). Apply it to prototypes and implemented pages.
- Follow the affected contracts for [settings](docs/settings.md), [identifiers](docs/identifiers.md), [HTTP](docs/http/api.md), [avatars](docs/identity/avatar.md) and [local files](docs/storage/files.md). Read their required references within the stated scope.
- Before validation, apply [check scope and execution boundaries](docs/engineering/verification.md#检查范围). Use the applicable commands from [documentation maintenance](docs/README.md#文档维护), [Rust workspace validation](docs/engineering/rust.md#workspace-validation), and [database verification](docs/database.md#交付验证). Reuse [design evidence](docs/engineering/evidence.md) only for the sources and claims it covers.

## Commits and Review

- Execute commits, pushes, PRs, merges and deployments covered by the Human's valid [delivery authorization](docs/engineering/delivery.md#连续交付与授权). Authorization may cover a project goal, a batch or one slice. Resolve concrete branches, PRs and revisions within that scope without asking again for covered actions. A request to edit or review alone does not authorize publication or merge.
- Use signed atomic Conventional Commits such as `docs(instructions): clarify implementation scope`, with short imperative subjects. Preserve available authoring-model and session trailers. Stage only the intended slice, including its documentation and validation; keep intermediate states runnable.
- Follow [the branch and promotion workflow](docs/engineering/delivery.md#分支测试与提升): implementation PRs target `dev`; promotion PRs target `main`. Describe the outcome, reason, checks and remaining limitations; link relevant issues. Preserve a PR-number suffix when assembling its merge commit.
- For merges into `dev` or `main`, follow [the delivery workflow](docs/engineering/delivery.md#审查关卡与证据复用). The legacy CI and admission code is removed; do not restore its controllers or treat historical checks as current admission. Complete local validation, current-candidate review and finding dispositions before an authorized ordinary merge, then read back the actual result. The [retired gate contract](docs/engineering/review-gate.md) points to historical recovery versions and records; it does not authorize reactivation.

## Code Review Rules

- Judge a change only against the business rules and public contracts of the affected owner documents and the kernel invariants of [the architecture](docs/architecture.md#应用内核), applying the applicable local Rust/SQL sections. Flag violations of the selected outcome, required invariants or failure recovery, with a concrete trigger and consequence. A mismatch between documentation narration and code, or a missing per-read-site verification that the types already guarantee, is not a blocking finding.
- Apply [implementation slices](docs/engineering/delivery.md#实施切片) when reviewing component and integration PRs, including consumer eligibility and safeguards for intermediate versions. Flag a PR that combines independently acceptable outcomes, builds facilities without a consumer established under that rule, or omits database protections, recovery or acceptance evidence required by its advertised outcome. Promotion PRs follow the coverage and acceptance requirements in the branch workflow.
- Review `design/` prototypes only against [the design review scope](docs/engineering/verification.md#设计稿审查). Do not flag preview-script mechanics such as history, back-forward cache, reload restoration, local material lifetime, timer precision or demo-tool consistency; those belong to client implementation slices. The visible states, copy, concealment, applicable state coverage, layout and user-facing navigation between screens remain reviewable.
- Check safe error reporting and controlled construction against [types and queries](docs/architecture.md#类型构造与查询). Apply [operation recovery](docs/architecture.md#原操作与恢复) only within its declared consumer scope: SMS retains deduplication, ordinary new writes use state refresh, and existing consumers keep their contracts until migrated. Do not require retired seals, version chains or recovery frameworks for the simplified badge flow. Formatting and lint checks follow [local validation scope](docs/engineering/verification.md#检查范围). Report coverage limits and unrelated existing defects separately from blockers introduced or affected by the candidate.
